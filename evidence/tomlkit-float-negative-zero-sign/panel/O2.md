# O2: SHIP (high)

Role: security. Slug: tomlkit-float-negative-zero-sign. Reviewed `0001-*.patch`, `PR.md` and `tomlkit/items.py` at `HEAD` (b05050c) and `HEAD~1` (0518af2).

## Blind verdict (written before reading CONFIRMATION.md, dup-search.out, pr-ref-scan.md)

SHIP, confidence high. The change neither adds nor removes anything I would call security behaviour, the text does not dress it up as security, and I found no security consequence the text misses. One optional text change (finding 5).

### Findings

1. **No new attack surface.** The patch touches one condition in the writer path, `Float._new` (`tomlkit/items.py:879-880`). The parser is untouched, so the set of documents tomlkit accepts is unchanged. The new clause `not raw.startswith("-")` reads `raw = str(result)`, where `result` comes from `float.__mul__` and friends (or `int.__truediv__` on the `Integer` path, `items.py:830,836`), which return a built-in `float`. A caller cannot route text into `raw` through an operand. I ran a `float` subclass with a hostile `__str__` as the operand; output is `x = +6.0` on base and fixed (row "float subclass" below).

2. **What the fix removes is a robustness fault, not a vulnerability.** On base the writer emits `+-0.0`. Both parsers I could run reject it, so the fault fails closed (a load error, not a silently different value). After the fix both read back `-0.0` with the sign intact, so the fix does not trade the crash for a value change. Run in my copy (`o2/claims.py`), verbatim:

(Base rows 7-13 are identical to the fixed rows and omitted here.)

3. **Nothing else moves.** Sweep in `o2/probe.py`: 22 source literals x (4 unary ops + 11 binary ops x 16 operands) = 3960 rows, base against fixed, each output re-read with tomlkit and stdlib `tomllib` and compared for value and zero sign. Verbatim diff summary:

```
    148 < a = +-0.0 | TOMLKIT-REJECT:InvalidNumberError;TOMLLIB-REJECT:TOMLDecodeError
    148 > a = -0.0 | ok
```
The other 3812 rows are byte-identical. Exceptions (315 ZeroDivisionError, 78 TypeError, all from `**`, 13 OverflowError) are the same count on both sides. The one `**` case I looked at individually, a complex result from `-1.5 ** 0.5`, raises at `result >= 0` before the new clause is evaluated, so its message is unchanged. Six further rows are `Integer ** negative`, which goes through `Integer._new` (`items.py:653`), not the changed line, and are identical on both sides. That is a separate matter and should stay out of this PR.

4. **The text frames it correctly.** Neither `PR.md` nor the commit message uses security language (grep for security/vulnerab/CVE/exploit/attack/denial: no hits). "tomlkit cannot parse its own output" is the true consequence and I reproduced the quoted error string exactly. I would not add a security angle: reaching the fault needs the application to do arithmetic on the value, and the result is a parse error. The repo has no `SECURITY.md`, so there is no private-report route this should have gone through instead. No local paths, tokens or third-party data appear in the patch or the PR text.

5. **Optional, not blocking: "The trigger is narrow" undersells the reach.** Every negative literal carries an explicit sign, so the fault is reachable from ordinary values, not only from `+0.0`: `round(doc["x"], 2)` on `x = -0.001`, `x = -1.5` times `0`, and `x = -0.0` times `1` all gave `+-0.0` on base (rows above). The two sentences in `PR.md` are true as written, so this is the operator's call. If he wants it, replace

   > The trigger is narrow. The source value must carry an explicit `+` or `-`, and the result must be negative zero.

   with

   > The source value must carry an explicit `+` or `-` (every negative literal does), and the result must be negative zero. `round(doc["x"], 2)` on `x = -0.001` and `x = -1.5` multiplied by `0` reach it too.

### Side-effect rule

No one is hurt. The only output that changes is `+-0.0`, which tomlkit and `tomllib` both refuse to load, so no working program can depend on it.

## After reading (CONFIRMATION.md, dup-search.out, pr-ref-scan.md)

Blind verdict stands: SHIP, high.

- CONFIRMATION.md's "Security angle: no" matches my finding 4. Its tomlkit and tomllib error strings are the same ones I got.
- Its repro lists further ordinary triggers (`-0.0 * 1`, `+x` on `-0.0`, `-1e-200 * 1e-200`, `+5.0 / -inf`). That supports finding 5: the reach is wider than the PR's "narrow" suggests. Still optional.
- It notes the alternative shape `if self._sign and not raw.startswith("-")` would turn a NaN result into `+nan`. The shipped three-clause condition keeps `nan` (my row "+1.0 * nan" is `x = nan` on both sides), so the patch makes no change to NaN output. Nothing to fix.
- dup-search.out and pr-ref-scan.md show no PR other than #345 touching this condition. Nothing there bears on security.
- I did not run the confirmer's `repro.py`; my own script covers the same cases against both trees.
