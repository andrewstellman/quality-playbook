## Blind verdict (written from patch, PR.md, source)
The fix is one condition in `Float._new` (`tomlkit/items.py:879-880`), shared by every Float operator and by `Integer.__truediv__`/`__rtruediv__` (`Float._new(self, result)`). So one correct condition covers all paths; the test only has to prove the condition, not each operator. It does.

## What I ran

Mutants against the two new/neighbouring tests (`-k "plus_sign or minus_sign"`, base of the fix applied):

## Findings (coverage, none blocking)
1. The new test does not parse its output back. The defect is "tomlkit cannot parse its own output"; the asserts compare strings only, which is fine and matches `test_no_extra_minus_sign` (`tests/test_items.py:1438-1451`), so I do not require a change. Optional, one line, only if the author wants the symptom pinned: after the first `as_string()` assert add `assert parse(doc.as_string())["a"] == 0.0`. Note `-0.0 == 0.0`, so that line would not pin the sign; the string asserts already do. Recommendation: leave as is, smaller PR.
2. Untested but covered by the same line: explicit `-` source (`-0.0` through unary `+` or `round`, 2 of the 7 confirmer cases), reflected ops, `divmod`. They go through the same `_new`, and the operator sweep shows them fixed. Adding them would pad a one-line fix; the unit under test is the condition, and `*=` plus Integer `/=` already exercise both entry points (`Float.__mul__` and `Integer.__truediv__`). Not required.
3. No negative control for an unsigned source (`a = 0.0` times -1 gives `-0.0`, unchanged). It was already correct on base, so it is not a regression guard for this change. Not required.
4. Implementation reliance: the fix keys on `str(result)` starting with `-`. CPython's `float.__repr__` always renders `-0.0` with the sign, and that is what the code already relies on for every negative value (`raw = str(result)`), so nothing new is assumed. I did not test PyPy; the CI matrix in POLICY.md is CPython 3.9-3.14 only.
5. Same pattern, different class: `Integer._new` at `tomlkit/items.py:655` has `if self._sign and result >= 0:` with no `str` check. Integers have no negative zero, so no bug. No change; mentioning only so no one assumes it was missed.
