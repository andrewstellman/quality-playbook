# O4: SHIP (high)

Role: not-a-bug. Slug: tomlkit-float-negative-zero-sign. Fix `b05050c` on base `0518af2`.

## Blind verdict (written before CONFIRMATION.md, dup-search.out, pr-ref-scan.md)

SHIP, confidence high. I argued the maintainer's side on six grounds. Five fail on the source or the project's own history, and the sixth is a matter of taste that does not block.

### The not-a-bug case, argument by argument

1. "Intended behaviour." Fails. The output is text tomlkit itself rejects. Run on base in my copy (`panel-...-O4-base`, `o4_probe.py`):

   ```
   *= -1                                  'a = +0.0'     -> 'a = +-0.0'      REPARSE FAILS InvalidNumberError
   /= -1 (int)                            'a = +0'       -> 'a = +-0.0'      REPARSE FAILS InvalidNumberError
   ```

   What forced the concession: the grammar has one optional sign, `dec-int = [ minus / plus ] unsigned-dec-int` (`reference_docs/cite/toml-spec-1.1.0__toml.abnf.txt:134`, and `float-int-part = dec-int` at :146), and the spec says "Float values `-0.0` and `+0.0` are valid and should map according to IEEE 754." (`toml-spec-1.1.0__toml.md:517`). No reading of either makes `+-0.0` a value.

2. "Documented or tested as is." Fails. Nothing in `README.md`, `docs/` or `CHANGELOG.md` describes a doubled sign. The only test near it, `test_no_extra_minus_sign` (`tests/test_items.py:1438`), was written by the maintainer to pin the opposite: no doubled sign after arithmetic. No test on base builds a negative zero result from a signed literal (base suite `1068 passed`, new test fails on base source with `AssertionError: assert 'a = +-0.0' == 'a = -0.0'`).

3. "Previously declined." Fails, and the history points the other way. The maintainer fixed this exact line for the same class of defect and shipped it the next day:

   ```
   bf01a25 Frost Ming Tue May 7 2024  fix: don't add sign if the float is negative (#345)   Fix #341
   990e325 Frost Ming Tue May 7 2024  fix: redundant minus sign added to negative integers when multiplie by -1 Fix #346
   CHANGELOG.md:116  - Remove the extra minus sign added to the float value after calculation. ([#341]...)   [0.12.5]
   ```

   `git show bf01a25 -- tomlkit/items.py` replaced `sign = "+" if result >= 0 else "-"; raw = sign + raw` with `if self._sign and result >= 0: raw = f"+{raw}"`. That is the line this PR edits, so the PR's sentence "This is the same line that #345 changed for #341" is true. Issue #341 (read through WebFetch, so the fetch tool's summary, not checked byte for byte) is titled "Sign change when doing math gives invalid number" and nobody in it mentions zero. I found no issue or PR declining a signed-zero fix.

4. "Already being fixed by someone else." Fails. I diffed every one of the 364 PR heads in `upstream-check` against its merge base for changes to `result >= 0`, `_sign`, `startswith("-")`, `copysign`, `+-0` or `-0.0` in `tomlkit/items.py`. Only `pr/345` (merged, above) and `pr/89` (the 2020 rename) match. `pr/628` adds `("-0E-2", -0.0)` to a parser test and touches `tomlkit/parser.py` only, so it does not overlap. A WebSearch for tomlkit plus "+-0.0" / "negative zero" returned nothing about tomlkit.

5. "Not worth the churn, nobody hits it." This is the strongest maintainer argument and it fails on the evidence. The PR's own repro (`x = +0.0` times -1) looks contrived, and a maintainer could fairly ask who writes `+0.0`. But the trigger does not need a zero or a `+` in the file. All run on base:

   ```
   -1.5 * 0                               'a = -1.5'     -> 'a = +-0.0'      REPARSE FAILS InvalidNumberError
   round(-0.4)                            'a = -0.4'     -> 'a = +-0.0'      REPARSE FAILS InvalidNumberError
   -0.0 * 1 (identity)                    'a = -0.0'     -> 'a = +-0.0'      REPARSE FAILS InvalidNumberError
   +(-0.0) unary                          'a = -0.0'     -> 'a = +-0.0'      REPARSE FAILS InvalidNumberError
   -1e-300 * 1e-300                       'a = -1e-300'  -> 'a = +-0.0'      REPARSE FAILS InvalidNumberError
   -0.0 // 1                              'a = -0.0'     -> 'a = +-0.0'      REPARSE FAILS InvalidNumberError
   -2.0 % -2                              'a = -2.0'     -> 'a = +-0.0'      REPARSE FAILS InvalidNumberError
   ```

   Any negative literal scaled by zero, rounded toward zero or underflowed writes a file that neither tomlkit nor the standard library can read back (`tomllib.loads('a = +-0.0')` gives `TOMLDecodeError Invalid value (at line 1, column 5)`), and it does so silently. The cost side is one changed condition and one 13-line test. With all 28 probe rows, the fixed tree reparses every output and differs from base only on the rows above (and the two in point 1 and `-(+0.0)`, `+0.0 * -0.0`, `round(-0.2, 0)`, `2.0 * -0.0`).

6. "Better fixed elsewhere or differently." Partly stands as taste, does not block. After the change, `result >= 0` only does work for NaN (`raw.startswith("-")` already covers every negative and `-0.0`), so a maintainer may ask why both clauses are there, or prefer `math.copysign`. Dropping `result >= 0` would change `+1.0 * nan` from `nan` to `+nan`, which is a behaviour change the PR rightly avoids. The same defect cannot occur in `Integer._new` (`tomlkit/items.py:653`): ints have no negative zero, and on base `a = -0` times 1 gives `a = +0`, which reparses. So one line in `Float._new` is the right place, and it also covers `Integer.__truediv__` / `__rtruediv__`, which call `Float._new` (`items.py:830`, `:836`).

### Side-effect rule

No one is hurt. The only outputs that change are ones that were unparseable. A user relying on the old text would have to be consuming `+-0.0` with something other than a TOML parser; I could not construct such a user. Rows that were valid on base are byte-identical on the fix in my probe (`nan`, `+inf`, `-inf`, `+1.5`, `+0.0`, `+0`, `-3.0`, `-1.0`).

### Findings

1. Optional, text. `PR.md`, "The trigger is narrow. The source value must carry an explicit `+` or `-`, and the result must be negative zero." True, but together with the `+0.0` repro it hands the maintainer the "nobody writes that" objection. One added sentence removes it. Replacement:

   > The trigger is narrow. The source value must carry an explicit `+` or `-`, and the result must be negative zero. Ordinary negative values get there too: `x = -1.5` followed by `doc["x"] *= 0`, or `doc["x"] = round(doc["x"])` on `x = -0.4`, also gives `+-0.0`.

   Both examples were run on base (rows above) and give `-0.0` on the fix. Not required for submission.

2. No change required. `tomlkit/items.py:880`, `if self._sign and result >= 0 and not raw.startswith("-"):`. Be ready for the question in point 6. The one-line answer is that `result >= 0` keeps NaN rendering as `nan`, as before.

3. No change required. PR claims I ran and found true: `items.py:879` is the condition line on `0518af2`; `+0` then `/= -1` gives `+-0.0` on base; `+1.0 * nan` -> `nan`, `+1.0 * inf` -> `+inf`, `+1.0 * -inf` -> `-inf`, `-1.5 * -1` -> `+1.5`, `+0.0 + 0.0` -> `+0.0` on both trees; suite `1068 passed` on base and `1069 passed` on the fix.
