### Findings

1. **PR.md Summary is 239 words; the recently merged fix PRs are about 95** (#623 and #613 bodies, fetched from github.com; both merged by frostming without comment on content). Not blocking, but the maintainer's stated bottleneck is review time. The last paragraph (TOML spec quote plus ABNF) proves something the snippet already shows: tomlkit's parser rejects `+-0.0`. The "1069 passed" sentence repeats what CI reports. Recommended replacement for everything between `## Summary` and `## Agent Drafting Metadata` (each behavioural statement below was run by me on base and fixed):

   ````
   Arithmetic on a float written with an explicit sign renders `+-0.0` when the result is negative zero, which tomlkit's own parser rejects.

   ```python
   import tomlkit

   doc = tomlkit.parse("x = +0.0")
   doc["x"] *= -1
   print(doc.as_string())          # actual: x = +-0.0    expected: x = -0.0
   tomlkit.parse(doc.as_string())  # InvalidNumberError: Invalid number at line 1 col 9
   ```

   `Float._new` (`tomlkit/items.py:879`) adds `+` when `self._sign and result >= 0`. `-0.0 >= 0` is `True`, and `str(-0.0)` is already `"-0.0"`. This is the line #345 changed for #341. `x = -0.0` followed by `doc["x"] *= 2`, and `n = +0` followed by `doc["n"] /= -1`, give the same output.

   The fix adds the `+` only when `str(result)` does not already start with `-`. Other results render as before. I checked `nan`, `+inf`, `-inf`, `+1.5` and `+0.0` before and after the change.
   ````

   This also swaps in the trigger a maintainer will recognise fastest: a file that already contains `-0.0` and is scaled by any positive number (`x = -0.0`, `*= 2` gives `x = +-0.0` on base, `x = -0.0` fixed; run above as `*1` and separately as `*2`). The current text only shows `+0.0 * -1` and calls the trigger "narrow", which undersells it slightly.

6. **Out of scope, for the operator's awareness only (do not add to this PR).** `+-0.0` is still reachable on the fixed tree through a different defect: `Integer.__pow__` wraps a float result in `Integer._new`.

   ```
   == base
   x = -10 ** -401 -> 'x = +-0.0' Integer
   x = +2 ** -1 -> 'x = +0.5' Integer
   == fixed
   x = -10 ** -401 -> 'x = +-0.0' Integer
   x = +2 ** -1 -> 'x = +0.5' Integer
   ```

   The PR text does not claim every `+-` path is closed, so nothing in it is false. If the maintainer asks "why not `Integer._new` too?", the answer is that `str()` of a non-negative `int` never starts with `-`; the only float that reaches `Integer._new` comes from the negative-exponent `__pow__` path, which is its own bug (an `Integer` holding `0.5`).
