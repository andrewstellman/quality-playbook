# S6: SHIP (high) on performance; no cost found

Scope: performance only, per the S6 charter. Not a full review of correctness, text or process.

Blind verdict (patch, PR.md and source read first; CONFIRMATION.md read afterwards).

## What the patch changes on a hot path

One line, `tomlkit/items.py:879`:
`if self._sign and result >= 0:` becomes `if self._sign and result >= 0 and not raw.startswith("-"):`

- It sits in `Float._new`, which runs only when arithmetic is done on an already-parsed Float (and on Integer true division, which returns a Float). Parsing, `as_string()` and plain reads do not call it.
- `raw = str(result)` was already computed on the line above. The patch adds no loop, regex or extra allocation.
- The new `startswith` is the last operand of a short-circuit `and`. It runs only when the source had an explicit sign and `result >= 0`. Unsigned floats and negative results skip it.
- The cost when it runs is one method call on a short string (tens of nanoseconds).

## Measurement

Copy: `/work/t2/scratch/panel-tomlkit-float-negative-zero-sign-S6/` (bench.py, b2.py). Python from `/work/t2/venv`. `Float._new(2.5)` called 500000 times, best of 5, on a signed-positive (`+1.5`), an unsigned (`1.5`) and a signed-negative (`-1.5`) Float. The first row is the patched tree and the second is `tomlkit/items.py` restored to `HEAD~1`.

```
FIXED  a(+1.5) 1367 ns/call   b(1.5) 1152 ns/call   c(-1.5) 1313 ns/call
BASE   a(+1.5) 1420 ns/call   b(1.5) 1116 ns/call   c(-1.5) 1327 ns/call
```

- The difference is inside run-to-run noise: the patched signed-positive case came out faster than base, and the unsigned case slower, with nothing changed on that path. The only case that executes the new `startswith` is `a`, and its delta is not measurable above noise.
- Parse benchmark (1000 lines of `k = +N.5`, `tomlkit.parse`): 21.8 ms per parse on the patched tree. I did not run it on base, because `_new` is not on the parse path (the grep of `_new` call sites shows Integer/Float operator methods only). Treat that number as a baseline, not a comparison.
- Each call is about 1.1 to 1.4 microseconds, so `_new` is dominated by `str(result)`, the `Float(...)` constructor and the trivia copy. An added `startswith` cannot matter.

## Findings

1. None required on performance. No change requested.
2. Optional and not recommended: `raw[0] != "-"` or `math.copysign` would be marginally different in cost. Neither is worth the review time. The current `startswith` form is the clearest.

## Side-effect rule (performance angle)

No memory, latency or complexity change for any existing user. No output change for any input other than negative zero from a signed source, which is the bug being fixed.
