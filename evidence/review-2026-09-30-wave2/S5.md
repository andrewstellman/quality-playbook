### st-024
Verdict: FIX-REQUIRED
Confidence: high
Findings:
1. Large, undisclosed widening for existing MANIFEST.in files. Experiment with setuptools.glob on a tree (data/a.txt, data/x/b.txt, data/x/y/c.txt, .hid/z/h.txt, node_modules/q/n.txt), non-recursive -> recursive:
   - `**/*.txt`: [data/.dot.txt, data/a.txt]  ->  all six files, including `.hid/z/h.txt` and `node_modules/q/n.txt`
   - `data/**`: direct children only -> entire subtree
   - `**`: [] -> every file in the tree
   setuptools' own glob copy does NOT skip hidden files/dirs (module docstring: "Hidden files are not ignored"), unlike stdlib glob. So `include **/*.py` etc. now walks and ships `.git`, `.tox`, `venv`, `node_modules`, build output; sdist size and `egg_info` time can jump sharply, and unintended files (secrets in dotdirs) can enter an sdist. The PR text says only "matches all three, like exclude". It must say existing `include` lines containing `**` will now match at every depth, including hidden directories, and note the walk cost; the newsfragment should too.
2. The cited doc sentence (miscellaneous.rst:113-114) is "`**` matching zero or more characters including forward slash, backslash, and colon" - about characters, not directories. It supports the claim but the PR should quote it exactly rather than paraphrase "matches zero or more directories".
3. Existing suite passes on the fixed tree: `test_manifest.py` 70 passed.

### addr-011
Verdict: FIX-REQUIRED
Confidence: high
Findings:
1. REGRESSION (new exception). Target whose last segment contains a colon: `Addressable::URI.parse("http://example.com/a:b").route_from("http://example.com/a:b?x=1")`. Base returns `""` (wrong but no error); fixed raises `Addressable::URI::InvalidURIError: Cannot assemble URI string with ambiguous path: 'a:b'` (uri.rb:2133 -> :2348). RFC 3986 4.2 requires `./a:b`. Must fix: prefix `./` when the segment contains `:` (the code already has `"./"` handling for the empty case), and add a spec. Otherwise this PR converts a silent wrong answer into a crash for existing callers.
2. Other cases now round-trip (verified): `/dir/` -> `./`; `/f#frag` -> `f#frag`; `/f` from `/f?x=1` -> `f`.
3. Pre-existing, not fixed and not claimed: `http://example.com/f` from `http://example.com/f?` still returns `#` (join -> `/f?#`). Fine to leave, but "base.join(route_from(base)) == uri holds" (PR text) is not true in general; soften to "for this case".
4. Return value for existing callers changes from `""` to `file.txt`/`./` in that scenario; the PR shows this in the example. OK.

### jav-011
Verdict: FIX-REQUIRED
Confidence: medium (not built; static-file code read)
Findings:
1. Silent behaviour change for anyone who already set `precompressMaxSize = 0`: it used to disable precompression; it now precompresses and caches every static file in memory, with no cap (`compressedFiles`/`precompressCache` ConcurrentHashMaps, computeIfAbsent of full `ByteArray`). A large file or many files can now exhaust heap. The PR states the code change but not this consequence; say it, e.g. "this makes 0 unbounded, as the docs describe".
2. In-repo docs disagree with the docs-site line the PR relies on: `StaticFileConfig.kt:41` "(default: -1, disabled)" and `:52` "-1 means disabled, otherwise set the max size". The fix leaves those KDoc lines un-updated (0 now means "all sizes"); update :52 or the PR is internally inconsistent. Also the Jetty oversize warning is skipped at 0 (intended).
3. Default (-1) and positive limits are unchanged; only the value 0 changes.

### express-issue
Verdict: FIX-REQUIRED
Confidence: high
Findings:
1. Factual error in the proposal paragraph: "`maxAge: 0` and negative values would still send `Max-Age=0`". Negative values do not send 0 today: `Math.floor(-500/1000)` is -1, and serializing gives `Max-Age=-1` (run against the `cookie` serializer: 500 -> `Max-Age=0`, 0 -> `0`, -500 -> `-1`, 999 -> `0`, 1000 -> `1`). Change to "`maxAge: 0` and negative values would be unchanged".
2. The idiom compat is not mentioned: apps that delete a cookie with a tiny positive `maxAge` (e.g. `maxAge: 1`) rely on today's `Max-Age=0`; after the fix that sends `Max-Age=1` (cookie lives about a second). Say so, and say whether `maxAge: 1` should keep deleting; a maintainer will ask. Related: #7287 deflection.
3. Repro and header shape (`Max-Age=0; Path=/; Expires=<now+0.5s>`) match the pinned code (response.js:764-769). `res.clearCookie` uses `expires: new Date(1)` with maxAge deleted (response.js:714-720), so "same result as clearCookie" is right in effect. Not verified: the RFC section numbers (S7 job).
4. Note package.json says `cookie ^0.7.1`; I could only test serialization with cookie 1.1.1 found on disk (same outputs for these inputs); not run end to end against the pinned express (no node_modules).
