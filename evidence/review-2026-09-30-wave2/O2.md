# O2 SECURITY — wave 2 review (2026-09-30)
Scope: does each fix add or remove security-relevant behaviour; does any text overclaim security or leave out a consequence that matters. None of the 11 texts uses security framing; that is correct for all of them. Three items leave out a consequence (jav-011, addr-032, st-024), and one adds a new exception path (addr-011).
Initial verdicts were written before I read CONFIRMATION.md. "After reading" notes are labelled. Experiments were run in /tmp/w2review/scratch/O2 (deleted afterwards). I built nothing for pydantic or javalin; those findings come from reading the source.

### cobra-016
Verdict: SHIP

### pyd-033
Verdict: SHIP
Confidence: medium
Findings:

### pyd-006
Verdict: SHIP
Confidence: high
Findings:
1. This is a mild hardening of a validation bypass: `multiple_of` was the only float constraint that let NaN/inf through. le/lt/ge/gt already reject NaN using `partial_cmp` (float.rs:127-170), and decimal.rs:200 rejects non-finite values for `multiple_of`. The fix brings floats in line with both. The text correctly avoids the word "security". No change needed.

### st-024
Verdict: FIX-REQUIRED
Confidence: medium
Findings:
1. The fix changes what goes into published sdists, and the text doesn't say so. `setuptools.glob` (setuptools/glob.py:142-160 `_rlistdir`) does two things: it matches hidden directories, and it follows directory symlinks with no cycle check. I tested on a tree with `.hid/`, `venv/` and a `loop -> ..` symlink. `glob('**/*.txt', recursive=True)` returned 84 paths, including `.hid/z.txt` and `venv/lib/secret.txt`, and the longest path was 289 characters before ELOOP stopped it. `prune_file_list` (egg_info.py:388-410) only removes build/, the release dir, and VCS dirs. `.venv`, `.tox`, `node_modules` and editor or secret dot-dirs stay in. So an existing `include **/*.cfg`-style line can silently pull deeper files, including anything in a local venv, into the next release.
2. This is consistent with existing behaviour: `recursive-include` already passes recursive=True and `graft` already walks everything. So the fix is not a new capability. The missing piece is disclosure.
3. Required change: add one clause to the newsfragment, e.g. "``include`` lines using ``**`` may now add files from deeper directories to the sdist; check the sdist contents after upgrading." No code change.

### st-004

### addr-032
Verdict: FIX-REQUIRED
Confidence: medium
Findings:
1. This changes which bytes a downstream server will decode, and the text doesn't say so. Base vs fixed, measured:
   `{+v}` "%2e%2e%2fetc%2fpasswd" => base `%252e%252e%252fetc%252fpasswd` / fixed `%2e%2e%2fetc%2fpasswd`
   `{+v}` "a%0D%0ASet-Cookie=x" => base `a%250D%250ASet-Cookie=x` / fixed `a%0D%0ASet-Cookie=x`
   `{+v}` "a%00b" => base `a%2500b` / fixed `a%00b` (same for `{#v}`, `/files/{+v}`; `partial_expand` changes too)
   Lone or malformed `%` (`%`, `%2`, `%zz`, `100%`) are encoded the same before and after. `{v}` is unchanged.
2. Raw `../` and `/` already passed through `{+}`. Before this fix, though, encoded CR/LF/NUL and encoded `/` (%2F) could not reach a decoding server through `{+}`/`{#}`, and now they can. The behaviour is RFC-correct. RFC 6570 §4 (cite/rfc6570-uri-template.txt:1499-1503): "it might be possible to craft unanticipated URIs if an attacker is given control ... over the variable values within an expression that allows reserved characters". It is still a change for callers who feed untrusted values into `{+}`.
3. Required change: add one sentence to the PR body, e.g. "Values containing `%XX` now reach the URI unchanged (e.g. `%2F`, `%0A`), so callers passing untrusted input to `{+}`/`{#}` should be aware." No code change. Do not frame it as a security fix.

### addr-011
Verdict: FIX-REQUIRED
Confidence: high
Findings:
1. The new branch (uri.rb:2109-2112) returns the last segment as a relative-path reference. If that segment contains `:`, `to_s` raises (fixed tree, measured):
   `URI("http://example.com/a/foo:bar").route_from("http://example.com/a/foo:bar?x=1")` => `InvalidURIError: Cannot assemble URI string with ambiguous path: 'foo:bar'` (base: returned `""`)
   `.../javascript:alert(1)` from `...?x=1` => same raise (base: `""`).
   Addressable's ambiguous-path guard prevents the worse result, a scheme-confused `javascript:` relative reference. But the fix newly reaches an unhandled exception with a path an attacker can supply. The fixer's notes acknowledge this; I don't think it should ship that way. RFC 3986 §4.2 prescribes the remedy: prefix with "./".
2. Required change (tested): `components[:path] = "./" + components[:path] if components[:path].empty? || components[:path].include?(":")`. Results: "./javascript:alert(1)" joins back to `http://example.com/javascript:alert(1)` and "./foo:bar" joins back correctly. uri_spec.rb: `1070 examples, 0 failures, 5 pending`. Add a spec for the colon case. The same raise in the existing `else` branch is out of scope.

### jav-011
Verdict: FIX-REQUIRED
Confidence: high
Findings:
1. Changing 0 from "disabled" to "no limit" switches on an unbounded in-memory cache. `getCachedResourceBytes` (JettyPrecompressingResourceHandler.kt:50-58) reads the whole file into a `ByteArray` and keeps it forever in a `ConcurrentHashMap`, once per encoding. That includes the uncompressed variant when the client sends no Accept-Encoding. With 0, any unauthenticated GET loads any static file, whatever its size, into heap. Large media gives OOM or heap exhaustion. Files over 2 GB can't fit a ByteArray at all, so they throw.
2. Who gets hit by the behaviour change: the docs config block lists `staticFiles.precompressMaxSize = 0;` (cite/javalin.io_docs.md:1566, :1581). Anyone who copy-pasted that block has precompression off today and would get the unbounded cache on upgrade. The in-repo KDoc (StaticFileConfig.kt:41, :52) says "-1 means disabled, otherwise set the max size" and never promises "0 = all sizes".
3. Required change, Andrew's choice: (a) keep the code fix and state the consequence in the PR body ("0 now caches every static file in memory regardless of size"), or (b) send a docs-only fix instead (javalin.io: make 0 mean disabled, or show the -1 default). I lean (b) as the lower-risk change, but this is arguable: the maintainer may prefer the documented semantics. If (a), the KDoc at StaticFileConfig.kt:52 should mention 0.

### jav-025
Verdict: SHIP
Confidence: medium
Findings:
1. The fix reduces exposure. Before, a non-root app redirected out of its context, to another app on the same origin. After, the Location starts with `ctx.contextPath()`, which comes from server config (Util.normalizeContextPath, JettyServer.kt:73), not the request.
2. The risk would be `contextPath()` returning "/" at root, which gives `//users/John`, a protocol-relative open redirect. It doesn't, by inference: JavalinJettyServlet.kt:56 and JettyResourceHandler.kt:63 both do `requestURI.removePrefix(req.contextPath)`, and routing would break if root returned "/". The existing root-context tests in the class must pass on the fixed tree; executors should confirm. Not run by me.
3. Not checked: whether a request segment like `\evil.com` can reach the Location at root (that would be a pre-existing issue, not caused by this fix).

### express-issue
Verdict: SHIP
Confidence: high
Findings:
1. The code claim matches the pinned source (lib/response.js:764-770: `opts.expires = new Date(Date.now() + maxAge)`; `opts.maxAge = Math.floor(maxAge / 1000)`). Version 5.2.1 and HEAD 9a34acf match. I did not run the repro (the pinned tree has no node_modules).
2. Security: the proposal extends the lifetime of sub-second cookies by at most 1 s, which is negligible. The issue rightly doesn't frame it as security. "The same result as `res.clearCookie`" is about effect, and is fair: clearCookie (:714-719) uses an epoch Expires with no Max-Age.

## Overall
None of the texts overclaims security, and none of the fixes opens a hole. pyd-006 and jav-025 slightly harden behaviour.
Must fix: jav-011 (0 = unbounded heap cache; disclose it or fix the docs instead), addr-011 (new InvalidURIError on ":" segments; tested "./" fix), addr-032 (one sentence: %XX now passes through `{+}`/`{#}`).
st-024 needs one newsfragment clause (sdists may gain deeper files, including in hidden dirs and venvs). Everything else: SHIP from a security standpoint.
