### pyd-033
Verdict: SHIP
Confidence: medium (not built)
Findings:
1. The logic is sound. pydantic always emits `config=core_config` on typed-dict schemas (_generate_schema.py:1521), and for a TypedDict without its own config that is the parent's config pushed through. So for generated schemas the fix only changes TypedDicts that have their own config. The `None` fallback only affects hand-built core schemas.
2. The code comment and PR say "as the validator does", but that is only partly true. The typed-dict validator (validators/typed_dict.rs:56-58) ignores the parent config entirely, while this patch falls back to it. Reword to "uses its own config if set, otherwise the parent's".
3. Compat (for S5): a TypedDict with any own config (e.g. `with_config(extra='forbid')`) inside a model with `ser_json_bytes='base64'` now serializes with its own defaults instead of the parent's settings. The docs require this, but the PR doesn't say it.

### addr-011
Verdict: FIX-REQUIRED
Confidence: high
Findings:
1. New exception (lib/addressable/uri.rb, new `elsif` branch). If the target's last segment contains `:`, `route_from` now raises:
   - `URI.parse("http://example.com/a:b").route_from("http://example.com/a:b?x=1")` → `InvalidURIError: Cannot assemble URI string with ambiguous path: 'a:b'`
   - same for `http://example.com/dir/a:b` and `urn:a:b` from `urn:a:b?q`
   - Base returned `""` (wrong but no raise).
   The differing-paths branch already raises for `a:b`, but this patch adds a new raising path. Fix: `seg = "./#{seg}" if seg.include?(":")` (or always use `./` when the segment has a colon), plus one spec.
2. Minor: for a scheme with an empty path (`foo://host` from `foo://host?x=1`), the route `./` joins to `foo://host/`, not `foo://host`. Rare; acceptable to leave.
3. Verified working: `file.txt`, `./` for a directory, `f.txt#frag`, `//` path, `foo:bar`, `file:///tmp/x`. uri_spec: 1070 examples, 0 failures.

### jav-011
Verdict: FIX-REQUIRED
Confidence: medium (not built)
Findings:
1. The in-source doc now contradicts the code. StaticFileConfig.kt:41 ("default: -1, disabled") and :52 ("-1 means disabled, otherwise set the max size for pre-compression") don't mention 0. Update the KDoc in the same commit so the source and javalin.io agree.
2. Behaviour change the PR should state: with 0, every static file, however large, is read fully into a heap ByteArray and cached forever (`computeIfAbsent`). It is also served from the cached-bytes path, which never looks at Range. Existing configs that set 0 (which previously meant "off") will start doing this on upgrade. Files of about 2 GB or more cannot fit in a ByteArrayOutputStream. This is what the docs promise, but say it in one line.
3. Values below -1 still disable, as before. The size guard `precompressMaxSize > 0 && ...` is correct in both handlers.
