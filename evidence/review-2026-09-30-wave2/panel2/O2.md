# O2 SECURITY: focused re-review (2026-10-01)
Experiments in /tmp/w2review2/scratch/O2 (now deleted). I compared base (HEAD~1 source) with the fixed tree. None of the texts frames anything as security, which is correct.

### cobra-016
Verdict: SHIP
Side effects:
- In completion after `--`, or with interspersed off, `ValidArgsFunction` now receives flag-named words (`--output`, `-o`), and `toComplete` is `--output=x` instead of `x`. This affects CLIs that complete positional args after `--` (exec/wrapper-style commands). They may show different TAB suggestions, and only TAB suggestions; Run is untouched. Likely to be noticed only by those CLIs. Acceptable: the args now match what Run gets.
Findings:
1. I ran 8 inputs × interspersed on/off against base and fixed (temp test). Only the intended rows differ. Examples: `c -- a -- --output ''` gives args `[a --]` on base and `[a -- --output]` on fixed, which is what Run sees. With an unknown flag (`c --bogus -- --output ''`), output is the same on both. `--tags a -- --tags ''` leaves tags=[a a] on both, so the third duplicate is gone. Pre-`--` flag completion (`c --output ''`, `c pos --output ''`) still returns the flag's values. `go test ./...` passes.
2. Not security-relevant: the output is suggestion strings only.

### st-004
Verdict: SHIP
Side effects:
- Builds that crashed now succeed. `readme`/`requires-python` are dropped, with the `_MissingDynamic` warning. No build that works today changes: on base, `_handle_missing_dynamic` (_apply_pyprojecttoml.py:133-137) always resets these fields and then crashes, so no existing build gets through.
- The resulting dist has no `Requires-Python`, so pip can install it on interpreters it doesn't support. Only authors who ignore the warning are affected, and this matches what happens today for `dependencies` (dropped, which is worse). Acceptable; PEP 621 requires it.
Findings:
1. I ran egg_info on pyproject (name, version) plus `setup(python_requires='>=3.8', long_description='hello', long_description_content_type='text/markdown')`. Base: `AttributeError: 'NoneType' object has no attribute 'get'`. Fixed: both `_MissingDynamic` warnings are emitted, and PKG-INFO has no Requires-Python and no body.
2. Minor, not blocking: PKG-INFO keeps `Description-Content-Type: text/markdown` with no description, because the content-type reset was dropped as the panel asked. It is harmless.

### addr-011
Verdict: SHIP
Side effects:
- `route_from` now returns the last segment (or `./…`) where base returned `""` (or `#f`). This affects code that computes relative links between URLs that differ only in the base's query. Base's `""` resolved back to the base *with* its query, which is a wrong link. Code that used `route.to_s.empty?` as an "is this the same resource" check now sees non-empty for these pairs. That is correct, since they are different URIs. Rare. Acceptable.
Findings:
1. My first-panel blocker is fixed. `/a/foo:bar` gives `"./foo:bar"` and `/javascript:alert(1)` gives `"./javascript:alert(1)"`. Both join back to the target, with no InvalidURIError and no scheme-confused reference.
2. 12 edge pairs (`/`, no path, `a//`, `%2F`, `b%3Ac`, `a/b?`, `#f`, mixed case host, `.`, `..`): fixed joins back to the normalized target in all 12; base mismatches in all 12. `b%3Ac` gives `./b:c`; the decoding of `%3A` comes from Addressable's existing normalization.
3. ReDoS is gone. With a 10k/30k-char segment, with and without a trailing slash: fixed 0.004 s / 0.011 s, base 0.004 s / 0.011 s. uri_spec: 1071 examples, 0 failures, 5 pending.

### addr-032
Verdict: SHIP
Side effects:
- Literal values containing `%XX` that the caller did not mean as an encoding now reach the server decoded. Measured: `{+v}` "p%41ss" gives base `p%2541ss`, fixed `p%41ss`, which the server decodes as "pAss". The same applies to `100%ABC`. This hits only callers putting raw non-URI text with `%`+2 hex digits into `{+}`/`{#}`. Unlikely, because `{+}` is the operator for values that are already URI text.
- If a caller screens `{+}` input for `/` or `..`, `%2F`/`%2e%2e%2f` now get past that check single-encoded (base double-encoded them). Rare, and RFC 6570 §4 already warns against untrusted values in `{+}`.
- Acceptable. The PR's behaviour-change line states the mechanism.
Findings:
1. **Correction to my first-panel O2 finding.** I wrote that encoded CR/LF "could not reach" a decoding server before. That was wrong. Base already emits raw `"\r\n"` as `%0D%0A` in `{+v}` (measured on both trees), so CR/LF/NUL reach the server either way. The only genuinely new outputs are encoded forms of characters base emitted raw (`%2F`, `%2e`). My requested sentence about untrusted input is not needed, and the current PR line is sufficient.
2. Unchanged: `{v}`, lone/bad `%` (`50%`, `%zz`, `a%2`, `%%41` gives `%25%41`), and raw `€`. template_spec: 330 examples, 0 failures.

### st-024
Verdict: DROP (side effect). I lean this way, and it is arguable (see 4).
Side effects:
- Existing `include **/…` lines that start at the project root now silently pull untracked files from any depth into the sdist. No build-time warning is printed (measured: 0 warnings).
- Measured on a realistic layout: src/ package, a mirror of a real venv in `venv/` (9056 files), a real npm `node_modules/` (1662 files), `.mypy_cache/`, and `.secrets/gcp/service-account.json`:
  - `include **/*.json`: base 12 files → fixed 291 (node_modules 256, venv/ 15, .mypy_cache 4, **.secrets/gcp/service-account.json 1**)
  - `include **/*.py`: 13 → 3073 (venv/ 3002); `**/*.txt`: 12 → 173; `**/*.html`: 12 → 132
  - Package-scoped `include src/mypkg/**/*.json`: 13 → 14 (the intended file only)
  - `.venv/`, `.tox/`, `.nox/` at the root are pruned (sdist.py:169), giving 0. A non-dot `venv/`, `node_modules/` and other dot-dirs are not pruned.
- Who is affected: grep.app finds 93 MANIFEST.in files with `include …**`. Of the 10 it shows, 8 are scoped to a package directory (the change is intended and harmless for them). 2 start at the root: primeqa `include **/*.cpp`/`**/*.cu`, and n64decomp rabbitizer `include **/*.h`. Root-anchored projects that build from a dirty local tree with `venv/` or `node_modules` present would ship bloated sdists, or in the worst case a nested credential file. A file published to PyPI can't be replaced, and yanking doesn't delete it. A CI clean-checkout build is safe unless CI runs `npm ci` first.
Findings:
1. The newsfragment and PR disclose this accurately. Disclosure only helps users who read release notes, though, and the harm is silent and possibly irreversible. Under Andrew's rule ("can hurt existing users in a way they would not expect"), that tips it to DROP.
2. Symlink loops: the PR sentence is accurate and matches `recursive-include`.
3. If kept as an issue instead, the evidence for it is: the docs (miscellaneous.rst:113-114) promise recursive `**`, `exclude` honours it, and `include` does not. The maintainers can decide whether to accept the sdist-content change.
4. Counterargument (why SHIP is defensible): the fixed `include **/*.json` gives exactly what base `global-include *.json` gives today (291 files, identical breakdown, measured). So no new class of exposure is created. The user wrote `**`, which the docs define as recursive. The affected population is small.

## Overall
- SHIP: cobra-016, st-004, addr-011 (blocker fixed, ReDoS gone), addr-032 (my first-panel CR/LF claim was wrong; no further text needed).
- st-024: DROP under Andrew's rule. The reason is a silent, possibly irreversible sdist-content change for root-anchored `include **` users, measured at 12 → 291 files including a nested secret. It is borderline, and it is Andrew's call.
