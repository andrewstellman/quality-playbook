### pyd-006
Verdict: SHIP
Confidence: high
1. float.rs:118 `!float.is_finite() || diff > tolerance`: `is_finite` is a bit test on an f64 already in a register, evaluated only when `multiple_of` is set. A few cycles per validate, below noise against `validate_float`. Short-circuit puts the cheap test first, fine.
2. Do NOT "optimize" to `!(diff <= tolerance)`: it would newly reject finite values whose `float / multiple_of` overflows to inf (e.g. 1e308 with multiple_of 0.5), changing behavior. Fix as written is the safer form. (Remaining non-finite-diff case for huge finite values is pre-existing and not perf; unverified whether anyone cares.)

### st-024
Verdict: SHIP
Confidence: medium
1. egg_info.py:448 `glob(pattern, recursive=True)`: `**` now really walks the subtree. Measured (Python 3.10, warm cache, 50,002-file tree, mostly a node_modules-style dir): `**/*.css` 0.058 s, `**/*.js` (50k hits) 0.083 s with recursive=True vs 0.000 s before (where `**` degenerated to `*`). Cost is O(tree) per `**` include line, not cached across lines. Dot-directories (.git, .tox) are skipped by glob by default; non-dot dirs (node_modules, venv, build) are walked. Cold-cache and large monorepo cost is higher. Same order as the `recursive-include`/`graft` walk users already pay.
2. Acceptable, but the newsfragment/PR could say that `include **/...` now scans the whole tree (that is the point of the fix). Optional; not required.

### addr-032
Verdict: SHIP
Confidence: medium
1. template.rb ~L782: the new regex literal has `#{...}` interpolation and no `/o`, so a Regexp is recompiled each time a `{+v}`/`{#v}` variable is expanded (the old code also rebuilt a String and then `encode_component` compiled `/[^#{...}]/` each time, so this is not a new category of cost). ### addr-011
Verdict: FIX-REQUIRED
Confidence: high
1. lib/addressable/uri.rb (new line in route_from): `components[:path] = normalized_self.path[/[^\/]*\z/]` is quadratic when the path ends with `/` (or a long segment precedes a trailing slash). The regex is unanchored at the start, so at each start position inside the last segment it scans to the next `/` and fails `\z`. Measured with real `route_from` (target `http://example.com/<n a's>/`, base same with `?q=1`):
   - base (HEAD~1): n=10000 0.004 s, n=30000 0.011 s (returns "")
   - fixed:        n=1000 0.015 s, n=10000 0.295 s, n=30000 2.685 s (returns "./")
   Microbenchmark alone: n=50000 7.5 s vs 0.000006 s for `rpartition`. This is a new super-linear path in a URI library that handles untrusted input (ReDoS-style).
   Change: replace with a linear form, e.g. `components[:path] = normalized_self.path.rpartition("/").last` (returns "" -> "./" via the next line; no-slash path returns the whole path). Re-run the two new specs; both expectations ("./" and "file.txt") are unchanged.
2. Text: PR need not mention performance once fixed. If left as is, the regression is a legitimate reviewer objection.

## Summary
- One item blocks on my lane: addr-011 introduces a quadratic regex (0.004 s -> 0.295 s at a 10k-char segment, 2.7 s at 30k, real route_from); swap in `path.rpartition("/").last`.
- Everything else is build-time, error-path, or noise-level on the hot path (addr-032 +7% on small expansions / -13% on large; st-024 `**` now walks the tree, 0.06-0.08 s on 50k files).
- jav-011 PR should note that `precompressMaxSize = 0` users go from "disabled" to unbounded in-memory cache.
