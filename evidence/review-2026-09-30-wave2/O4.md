### jav-011
Verdict: REJECT (as a code PR). Send a docs fix instead.
Confidence: high
Findings:
1. The code is self-consistent: StaticFileConfig.kt:41 says "(default: -1, disabled)" and :52 says "-1 means disabled, otherwise set the max size". The only conflict is the website comment "(-1 to disable, 0 for all sizes)".
2. Making 0 mean "unbounded" is a memory hazard for users who copy the docs. Precompression buffers the whole file into a `ByteArrayOutputStream` and caches it forever (`JettyPrecompressingResourceHandler.getCachedResourceBytes`, `compressedFiles.computeIfAbsent`). Files with non-compressible MIME types are cached raw as well. The docs example literally sets `precompressMaxSize = 0`, and people copy it verbatim. #2616 (2026-07-31) shows a user with exactly `staticFileConfig.precompressMaxSize = 0` serving 3.6 GB files and hitting OOM. Their stack trace goes through `handleResource` (the non-precompressed path, because 0 currently disables), and #2618 fixed it by streaming. With this patch, that same config would send 3.6 GB files into the in-memory cache, where they cannot fit in a byte array: OOM again. #2620 shows the same snippet pasted again.
3. Better fix: a PR to the javalin.io docs (javalin/javalin.github.io) changing the comment to "(-1 to disable)" or "(0 or less disables)". If a code PR is still wanted, the safe direction is a Kdoc note that 0 disables, not unbounded caching.
After reading: the confirmer flagged the same pushback risk ("maintainer may fix the docs instead"). #2616 turns that risk into a concrete regression.

### express-issue
Verdict: REJECT (if it is filed anyway, the fixes below are mandatory)
Confidence: medium
Findings:
1. Factual error: "Expires=<now + 0.5 s>" / "while `Expires` is still set half a second in the future". Expires is an HTTP-date with 1-second resolution. I ran `new Date(Date.now()+500).toUTCString()` three times; when parsed back it was 308/314/314 ms **in the past**. The wire value is the current second whenever the clock is under .500 into the second. Expires cannot express 500 ms either, so the "Max-Age contradicts Expires" framing does not hold.
2. The maintainer's best reply: a sub-second lifetime is below the resolution of both cookie attributes. Floor is one defensible choice. The proposed `Max-Age=1` doubles the requested lifetime, which also isn't what the caller asked for. The only realistic trigger is a computed remaining lifetime under 1 s, and there expiring now versus ≤1 s later makes no practical difference. The issue gives no use case, and it needs one.
3. Precedent: in #7287 (an Infinity/NaN `maxAge` PR, not a rounding change as the panel brief says), bjohansebas requested changes: "I know you like to push things to the limit ... if we were to support this, I think it would make more sense in the `cookie` package than in Express itself. Please open an issue first". That signals fatigue with `maxAge` edge cases.
4. If filed anyway: fix the Expires claim, add a concrete use case, and present floor/ceil/round as a question to the maintainers rather than proposing ceil. I did not verify the docs quote against expressjs.com.
