### addr-011
Verdict: FIX-REQUIRED
Confidence: high
1. Source reverted, both new examples fail (`expected: "./" got: ""`; the other likewise). 1070 examples, 0 failures on the fixed tree.
2. Style inconsistency, with a reason that is not written down. The `./` example uses `.route_from(...).to_s` while every neighbour uses `eq(Addressable::URI.parse(...))`. I verified why: `URI.parse("./") == URI.parse("")` is `true` (`==` normalises), so the neighbour idiom would pass on the bug. Add a one-line comment saying so, or the next maintainer will "fix" it to the idiomatic form and silently neuter the test.
3. Test description reads "should have a route of './' from 'http://...resource/?query=x'" in a context whose subject is `.../resource/`. It follows the neighbours' naming, so that is fine.
4. Untested new failure path. On a last segment containing `:` the fix now raises. Base returns `""`:
   `URI.parse("http://example.com/a:b").route_from("http://example.com/a:b?x=1").to_s`
   gives `Cannot assemble URI string with ambiguous path: 'a:b' (Addressable::URI::InvalidURIError)` on the fixed tree, and `""` on the base. The confirmer acknowledges it. No test pins it, and the PR text should state it (S5's concern); I mention it here because the tests are silent on a behaviour change.
5. Missing neighbouring case: the empty-last-segment path (`./` branch) is covered but the `/` root path case (`http://example.com/` vs `?x=1`) is not. Optional.
