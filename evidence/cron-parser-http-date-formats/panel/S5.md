## Compat analysis (side-effect rule)
Change: strings that used to throw `CronDate: unhandled timestamp` now parse if they match luxon fromHTTP (RFC 850, asctime).
Placed last in the `isValid ||` chain (src/CronDate.ts:54), so any input that parsed before is returned by an earlier call and never reaches it.
I checked this myself, not by reading the author's log. Differential script (old chain re-implemented vs new CronDate), 22 inputs x 4 zones
(undefined, UTC, Europe/Athens, America/New_York), in /work/batch/runs/cron-parser/scratch/panel-cron-parser-http-date-formats-S5/s5/diff.ts.
The only CHANGED rows were throw -> date, for these strings:
  CHANGED UTC "Sunday, 06-Nov-94 08:49:37 GMT" THROW 1994-11-06T08:49:37.000Z
  CHANGED UTC "Sun Nov  6 08:49:37 1994" THROW 1994-11-06T08:49:37.000Z
  CHANGED UTC "Sun Nov 06 08:49:37 1994" THROW 1994-11-06T08:49:37.000Z   (zero-padded day, not in the PR)
  CHANGED UTC "Sunday, 06-Nov-50 08:49:37 GMT" THROW 2050-11-06T08:49:37.000Z
  CHANGED UTC "Sun Mar 29 02:30:00 2026" THROW 2026-03-29T02:30:00.000Z
(the "" row also printed CHANGED, but that is my harness: CronDate('') takes the `!timestamp` branch and means "now". Ignore it.)
Still throwing: wrong weekday ("Mon Nov  6 ... 1994"), "Sun Nov 6 ..." (single space), lowercase, "Sunday, 06-Nov-94 ... UTC" and "... PST",
Date.toString() output, "Tue Feb 30 ...". Zone behaviour identical across all four zones: the instant is always read as GMT.
Wiring: CronExpression.ts:52-65 passes startDate/endDate/currentDate strings through this constructor, so the same strings are now accepted there.
`CronExpressionParser.parse('0 0 * * *', {currentDate:'Sun Nov  6 08:49:37 1994', tz:'America/New_York'}).next()` -> 1994-11-07T05:00:00.000Z.

Who is affected:
1. Callers who pass these strings today get an Error. Nobody can depend on a working result. Likelihood of anyone relying on the throw: very low.
2. Callers who use the constructor/parse error as a validator of user input ("reject anything that is not ISO/RFC2822/SQL").
   They now accept RFC 850 and asctime. Likelihood low; consequence is a loose validator, not wrong schedules. Acceptable.
3. Callers with asctime strings that are really local time (C ctime, Python time.asctime, `date`-like output, e.g. "Sun Mar 29 02:30:00 2026").
   They used to get a loud error; now they get a silent instant read as GMT, not as `tz`. A user who then sets tz:'Europe/Athens'
   gets a result off by the zone offset with no error. Likelihood: low to moderate, because asctime is the format of local-time tools.
   This is inside what the PR already discloses ("Zone: fromHTTP reads every HTTP date as GMT"), and luxon/RFC 9110 define asctime as GMT. Acceptable, but the text must say it
   turns an error into a silent value, and who is exposed.
4. Two-digit years in RFC 850 use luxon's pivot (06-Nov-50 -> 2050, 06-Nov-94 -> 1994). Not mentioned in the PR. Low impact, same "what luxon returns" basis.
Verdict on side effects: acceptable, no drop. Not breaking; `Breaking change` box correctly unticked.
