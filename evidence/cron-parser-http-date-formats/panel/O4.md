Role: not-a-bug. I argued the maintainer's side and could not make it stick. The README does list HTTP, and the fix touches only inputs that throw today. What remains is stale base text, an unforced semantic choice (asctime read as GMT) and a "docs only" risk the PR should make easier to accept.

## Blind verdict (written from patch, PR.md and source, before CONFIRMATION.md)

Maintainer-side arguments I tried:
1. "HTTP" means the RFC 1123 form only. That form already works through fromRFC2822. RFC 850 and asctime are obsolete forms that senders must not generate. Nothing in the repo contradicts this: README.md:85-89 gives no example strings, and tests/CronDate.test.ts:399-430 has no HTTP case.
2. Not worth the churn. Nobody has reported it. This is true as far as the repo shows. The tracker was not searched beyond known_open_bugs.md (a 2026-10-05 export of open items only; it says nothing about closed ones).
3. Declined before. I found no sign of that. `git log -S'fromHTTP' --all --oneline` in upstream-check printed nothing, so no commit or PR head ever added or removed a fromHTTP call. (`-S'HTTP and RFC2822'` finds only the README commits 9332e6b and ef172bd.) Closed issues and PRs were not checked.

What forced me to concede, with quotes:
- README.md:85 "When using string dates, the following formats are supported:" and README.md:88 "- HTTP and RFC2822". git show ef172bd (Dec 2021) shows the list was written as links to luxon: "- [`HTTP and RFC2822`](https://moment.github.io/luxon/#/parsing?id=http-and-rfc2822)". That luxon section covers both fromHTTP and fromRFC2822. So the README promise is the luxon HTTP section, not only the one form that happens to parse. This is a documented-but-missing behaviour, not an intended limit. (The link was later dropped from the README, so the maintainer will not see this unless the PR says it.)
- Experiment in my copy (fix applied, TZ=UTC, ts-node): `Wednesday, 06-Nov-24 08:49:37 GMT` gives 2024-11-06T08:49:37.000Z and `Wed Nov  6 08:49:37 2024` gives 2024-11-06T08:49:37.000Z. `Sunday, 06-Nov-94 08:49:37 PST`, `Sun Nov  6 08:49:37 1994 GMT`, `Sun Nov 6 08:49:37 1994` (single space) and `Mon Nov  6 08:49:37 1994` (wrong weekday) all still throw. So the new accepting set is exactly luxon's two extra HTTP forms and nothing looser.

Side-effect rule:
- Who is affected: only callers passing RFC 850 or asctime strings as currentDate, startDate, endDate or to includesDate/reset (src/CronExpression.ts:52,53,57,65,321,342). Today they get `CronDate: unhandled timestamp`. After the fix they get a date. Inputs that parse today never reach the new line (src/CronDate.ts:54 is the last in the chain), and sideeffect.log shows 13 inputs x 3 zones with only those two changed.
- What happens to them: an error becomes a value. For asctime with a non-UTC `tz` option the value is read as GMT, not in `tz`. A caller who expects zone-less strings to be local (as ISO, SQL and `Mon, 4 Jan 2021 10:00:00` are, per tests/CronDate.test.ts:405-408) would now get a silent shift instead of an error. Likelihood: low. Nobody can depend on it today because it throws, and asctime strings are rare as cron inputs. This is not a drop reason, but the PR must say it plainly (it does, in the Zone paragraph).
- Project limits (rules): not security, not a DST change, no CHANGELOG edit, one source line plus tests. Fine.
