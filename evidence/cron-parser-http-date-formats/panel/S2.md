## Side-effect rule
Before the change, the two formats throw; after, they return a date. Only callers that rely on catching that error for these exact strings are affected (e.g. validating user input with try/catch and rejecting RFC 850 or asctime). That is unlikely and the input is obsolete. The asctime input has no zone, so it is read as GMT, not in `tz`. A caller who then passes `tz` expecting local reading would get a time shifted by their offset. This is named in PR.md with an offer to change; the semantic is pinned by the asctime test (mutation 4), so it would need updating if the maintainer prefers `tz`. Likelihood low. Not a drop.
