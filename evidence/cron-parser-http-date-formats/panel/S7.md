## Side-effect rule

- Only strings that threw "unhandled timestamp" before now parse. Anything that parsed before is untouched, because the new call runs last.
- Who could be affected: a caller who relies on the throw to reject RFC 850 or asctime strings, for example `currentDate` or `startDate` validation in a wrapper. That is very unlikely, and the README promises HTTP.
- The asctime form is read as GMT, not in `tz`. This is disclosed in the PR and gives a different instant than a "local time" reading. I ran it, and it only affects inputs that threw before.
- No security angle.
