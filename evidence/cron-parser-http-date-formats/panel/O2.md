# O2: SHIP (medium)

Role: O2 security. Blind verdict written from the patch, PR.md and src/CronDate.ts before CONFIRMATION.md was opened.

## Blind verdict

The fix adds no security-relevant behaviour and removes none. PR.md frames nothing as security. I found no ReDoS, no hang and no non-Error throw introduced by the new line. Two text points (findings 1 and 2) should be fixed before submission. Neither is a security issue.

### What I checked (all in my own copy, not the fix clone)

- Luxon 3.7.2 `parseHTTPDate` (node_modules/luxon/src/impl/regexParser.js:237-245, 283-291): the three regexes are anchored (`^...$`), fixed-width, with no nested quantifiers. No catastrophic backtracking is possible. No ReDoS added.
- Ran `new CronDate(x, 'Europe/Athens')` on 20 inputs through ts-node (script x.ts in `scratch/panel-cron-parser-http-date-formats-O2/`), including a 1,000,000-character `AAAA...` string and a 1,000,000-space prefix before a valid asctime string. Verbatim:
  `AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA THROW true CronDate: unhandled timestamp: AAAAAAAA...`
  `                                         THROW true CronDate: unhandled timestamp:   ...`
  The script prints "slow ms" for any call over 50 ms. Only the first two valid inputs printed it (250 ms and 58 ms, module warm-up). Neither big input printed it.
- Non-string input (`{}`, `[]`, `123n`, a Symbol, an object with toString) throws an Error (`s.replace is not a function`, `Cannot convert a Symbol value to a string`). That throw comes from the existing `fromRFC2822` step, before the new line. The new line adds no non-Error crash. The `typeof` guard is unchanged.
- Bad HTTP strings still throw `CronDate: unhandled timestamp`: weekday mismatch (`Mon Nov  6 08:49:37 1994`), `Feb 30`, hour 25, zone `PST`, one-digit day with a single space (`Sun Nov 6 ...`).
- Because `fromHTTP` runs only when ISO, RFC 2822, SQL and the `fromFormat` step are all invalid (`src/CronDate.ts:54`), every input that parses today gives the same result. No existing valid input can change.
- Applied the patch to today's upstream tip with `git am` (clone `scratch/panel-cron-parser-http-date-formats-O2-tip`, base 5033a31). It applies cleanly. `run-tests`: `Tests:       348 passed, 348 total`.
- End to end: `CronExpressionParser.parse('0 0 * * *', {currentDate:'Sun Nov  6 08:49:37 1994', tz:'Europe/Athens'}).next()` gives `Sun Nov 06 1994 22:00:00 GMT+0000`. That is midnight in Athens, so the string was read as GMT as PR.md says.
- Citations: README.md:85 and :88 match the cited README. `src/CronDate.ts:50-54` matches the patched file.

### Side-effect rule

Who is affected: callers whose string `currentDate`, `startDate`, `endDate` or `parse()` date argument is in RFC 850 or asctime form. Before, they got `CronDate: unhandled timestamp`. Now they get a date. Anyone who used that throw as validation (a try/catch that rejects non-ISO input) would now accept these two obsolete formats. Likelihood: very low. No test, doc or changelog in the repo says the throw was intended.

The one realistic way to be hurt is asctime without a zone. C `ctime()` and Python `time.ctime()` print asctime format in LOCAL time. A caller who pipes that output into `endDate` used to get a loud error. Now the string is read as GMT and the bound is silently shifted by the caller's UTC offset. This is a correctness issue, not security (SECURITY.md out of scope: "Incorrect schedules ... with no security impact"). It is not enough to drop the fix, because the HTTP spec and luxon both define asctime as GMT. PR.md does name the zone choice and offers to change it, but not this consequence.
