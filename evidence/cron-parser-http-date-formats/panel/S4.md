## Side-effect rule
Who is affected: callers passing an RFC 850 or asctime string as currentDate/startDate/endDate or to CronDate. Before: they got
`CronDate: unhandled timestamp`. After: a date read as GMT. Anyone catching that error to fall back to another parser would now
get a date instead; I think this is very unlikely (the formats are obsolete, no report in ~5 years per CONFIRMATION). Inputs
that parse today are unchanged (sideeffect.log: 13 inputs x 3 zones, only the two target strings changed).
Risk that an asctime string was meant as local time: real but only for inputs that threw before. Not a reason to drop.
