# S6: SHIP (high)

Charter: performance. Cost on hot paths the fix touches. Role limited to that; no view on whether the bug is worth a PR.

## Blind verdict (from patch, PR.md, source)

The change is one line in the string branch of the `CronDate` constructor (`src/CronDate.ts:54`, `this.#date.isValid || (this.#date = DateTime.fromHTTP(timestamp, dateOpts));`). That branch runs only when `timestamp` is a string.

Hot-path check:
- The iteration hot path (`next()`, `prev()`, `#findSchedule`) copies dates with `new CronDate(cronDate)` (`src/CronExpression.ts:132,135,521`), which takes the `instanceof CronDate` branch. String dates are only seen for `startDate`, `endDate`, `currentDate` options and `reset()` (`CronExpression.ts:52,53,57,65,321,342`), once per call, not per iteration. The new line is not reached from the iteration loop.
- The new call is short-circuited by `isValid`. Every input that parses today never reaches it. The only new work is on inputs that previously failed all four parsers and threw (or the two newly accepted formats).
- `fromHTTP` uses three anchored regexes in luxon (`node_modules/luxon/src/impl/regexParser.js:235-240`, `^...$`, fixed alternations, no nested quantifiers). No backtracking risk seen.

Initial verdict: SHIP on performance, high confidence.

## Measurements (my copy, ts-node, TZ=UTC, Node default; copy at scratch/panel-cron-parser-http-date-formats-S6)

Per-call cost of `new CronDate(s, 'UTC')` inside try/catch, microseconds, noisy machine (shared). NEW = patch, BASE = line removed.

```
NEW
garbage      256.77 us/call
fromFormat   213.40 us/call
iso          55.62 us/call
long         1187.46 us/call      ('Sun, ' + 100000 zeros, 100 iters)
BASE
garbage      260.58 us/call
fromFormat   156.69 us/call
iso          43.20 us/call
long         823.26 us/call
```
The `iso` row (never reaches the new line) moved from 43 to 55 us between runs, and an earlier run gave 42.6 and 48.0. So differences of this size are run noise, not the patch. The `garbage` row (the one case where the new call is added and the result is still a throw) is flat: 257 vs 261 us. Cost there is dominated by luxon invalid-DateTime construction and Error stack capture.

Direct cost of the added call (luxon `DateTime.fromHTTP`, zone UTC):
```
short      17.75 us/call      ('not a date', fails)
long100k   0.60 us/call       ('Sun, ' + 100000 zeros, fails at the anchored regex)
asctime    32.78 us/call      (valid, newly accepted)
```
So the worst added cost is about 18 us on an input that already throws, and a one-off 33 us for the newly accepted forms. Long non-matching input is rejected in under 1 us, so no input-length amplification.

An earlier 10-case run (iso, rfc2822, sql, fromFormat, rfc850, asctime, garbage, three long garbage strings) did not finish inside the 2 minute limit on its second pass; the first pass printed all rows (garbage 271 us, 10k-char garbage 243 to 275 us, no length growth).

## Side-effect rule

Who is affected: anyone passing a string date to `startDate`, `endDate`, `currentDate`, `reset()` or `CronDate` that today throws `unhandled timestamp`. Strings that parse today are unchanged because the new call is last and guarded by `isValid`. Cost to existing working users: none measurable. Behaviour change: a caller that relied on catching the throw for RFC 850 or asctime input to reject it would now get a date. Likelihood: very low, such code would be validating a format the README says is supported. Not checked: whether any strings that were invalid before now parse as a different, unintended HTTP form (luxon's anchored regexes require the exact day-name/GMT shapes, so I expect none, but I did not fuzz it).
