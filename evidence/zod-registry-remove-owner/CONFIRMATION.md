BUG-012: registry.remove() deletes an id entry that now belongs to another schema. Verdict CONFIRMED.
Claim: r.add(a,{id:"x"}); r.add(b,{id:"x"}); r.remove(a) → _idmap no longer has "x" although b still owns it and has(b) is true; z.toJSONSchema(r) returns {schemas:{}} instead of {schemas:{x:{type:"number"}}}.
Mechanism: registries.ts:51-58 remove() does this._idmap.delete(meta.id!) with no owner check; add() (39-41) sets _idmap unconditionally (later schema owns the id). Pinned: registries.test.ts:210-220 "re-registering same id silently overwrites" asserts _idmap.get("shared-id") is b. Commit adf65cde "Drop id uniqueness enforcement at registry level (#5574)" justifies overwrite with HMR / test re-import — exactly the flows where a stale remove() of the old schema happens. Fix: `if (this._idmap.get(meta.id) === schema) this._idmap.delete(meta.id)`. Note metadata.md:42 (docs say duplicate id throws) is stale relative to #5574; cite the test and #5574, not the doc. No upstream issue (adjacent #4145, #4834, #6611). No security angle. Severity LOW.
