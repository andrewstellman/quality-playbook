# S2 READABILITY-TESTS

Method: for each fix I applied only the test hunk to a copy of base (/tmp/adonw) and read the failure text; read neighbouring tests in base; ran small probes in /tmp/adonreview/scratch/S2. I did not read CONFIRMATION.md or other reviewers' output. All eight new tests fail on base for the claimed reason.

### uuid-matcher
Verdict: SHIP  Confidence: high
1. Base failure (verbatim): `AssertionError: expected true to be false ... at tests/router/matchers.spec.ts:41`, i.e. the `zzzz...` uuid was accepted. Right reason.
2. Test would catch a revert of the char class. `g` is the first out-of-range letter, so the boundary is covered. Good pair of inputs.
3. Optional nit: the two all-same-letter strings only prove that each of the five groups can't be all non-hex. A real uuid with one `g` (e.g. `randomUUID().replace(/^./, 'g')`) would pin each group separately. Not required.
4. Style: separate test rather than extending `get matcher for a uuid` (line ~28). Fine and arguably cleaner; name `uuid matcher rejects non-hex characters` matches the slug neighbour's descriptive style.

### redirect-qs-separator
Verdict: FIX-REQUIRED (small)  Confidence: medium
1. Base failure: `expected '/foo?username=virk?age=28' to equal '/foo?username=virk&age=28'`. Right reason; the assertion text shows the bug.
2. Probe on fixed tree (verbatim): `/foo? => /foo?&b=2`, `/foo#x => /foo#x?b=2`, `/foo?a=1#x => /foo?a=1#x&b=2`, `/foo?a=1& => /foo?a=1&&b=2`. The test only builds the clean `?a=1` case. A reader/maintainer will ask about the trailing `?` and fragment cases; either handle them or state in the PR they are out of scope. Test must not imply they work.
3. Test name `append query string to url that already has a query string` departs from the neighbours' `redirect to given url ...` pattern (src tests: `redirect to given url with custom query string`). Suggest `redirect to given url that already has a query string`.
4. Only `withQs(k, v)` is exercised; the forward-qs path (`withQs()` with no args, `forwardQueryString`) goes through the same `#sendResponse` but is not covered. One extra line in the same test is enough, or accept.

### cookie-maxage-zero
Verdict: SHIP  Confidence: high
1. Base failure: `expected undefined to equal 'Max-Age=0'` at serializer.spec.ts:139. Right reason.
2. Near-verbatim clone of `define max age in seconds` (same shape, same split/equal). Best possible consistency with neighbours.
3. Probe (base and fixed, verbatim): `MAXAGE "0" THROW Invalid duration expression "0"`, `0s` and `0min` also throw. So string zero is unsupported before and after. Test correctly only covers numeric 0; the PR text must not say "zero" generically (S7/S5 issue, not a test issue). Negative values already produce `Max-Age=0` on base.
4. Test name `define max age as zero` fits neighbours.

### toroute-qs-mutation
Verdict: SHIP  Confidence: medium

2. Test reads like the neighbour `redirect to given route and add qs via makeRoute` (same router setup, same `@ts-expect-error "Because RoutesList is empty"`). Idiomatic.

A direct `assert.deepEqual(options, { qs: { published: true } })` after one `toRoute` call would be shorter and fail on the mutation itself, but the current form mirrors the brisk-route scenario claimed in the PR. Optional.
4. Commit scope is `fix(response)` but the change is in `src/redirect.ts`; use `fix(redirect)`. Relevant to the conventional-commit history (#138 `fix(request)` matches its file).
5. Local name `route` holds a Router (copied from neighbours); leave it.

### send-error-object
Verdict: FIX-REQUIRED  Confidence: medium
1. Base failure: `expected "content-type" of "text/plain; charset=utf-8", got "application/json; charset=utf-8"`. Right reason, but it fails on the header expectation before `assert.equal(text, ...)` is reached, so on base the text assertion is never evaluated. Fine, but note the chained `.expect` is the real gate.
2. Missing test for a behaviour change the test cannot see. Probe `send(Object.assign(new Error('x'), {code:'E_X', errors:[1]}))`: on base (and the BUG-006 tree) it returns `application/json; charset=utf-8 "{\"code\":\"E_X\",\"errors\":[1]}"`; on the BUG-014 fixed tree it returns `text/plain; charset=utf-8 "Error: x"`. Errors with enumerable own properties previously serialized usefully and now lose them. The new test uses a bare `new Error('boom')`, so it cannot reveal this. Add a test documenting the intended outcome, or narrow the fix, and say so in the PR.
3. Only `Error` itself is tested; subclasses (`TypeError`) and `Exception` from @poppinss/utils are the realistic inputs. One more `send(new TypeError('boom'))` assertion would show the `instanceof` intent.
4. Name `get error in response` is a direct copy of `get regex in response`; OK.

### lookup-route-error
Verdict: SHIP  Confidence: medium
1. Base failure: `expected [Function] to throw 'Exception' but 'Error: Cannot lookup route "posts.show"' was thrown`. Right reason (class check), but the message is the japa class-name form; good enough.
2. Second assertion (method-specific message) is never reached on base, which is fine, and on a half-fix (only no-method branch) it would catch it. Good.
3. Test covers class and message only. It does not pin `error.code === 'E_CANNOT_LOOKUP_ROUTE'` or status 500, which the PR claims ("code, status or instanceof"). Add `assert.equal(error.code, ...)`/status via try/catch or `assert.throws` plus a second check, or trim the claim.
4. Name `raise E_CANNOT_LOOKUP_ROUTE exception when unable to lookup route` vs neighbour `raise error when unable to lookup route` (line 1622): acceptable; the older test is now subsumed but leaving it is harmless.
5. The src change mutates `error.message` after construction; test depends on substring match so it would pass if the template changed. Not a test defect.

### unknown-content-type
Verdict: FIX-REQUIRED (small)  Confidence: medium
1. Base failure: `expected "content-type" of "application/octet-stream", got "false"`. Right reason.
2. The test goes through `download()` and writes a file named `LICENSE` (cleaned by `group.each.teardown`, line 37, so no leak). The bug is in `type()`; existing tests call `response.type('plain/text', 'ascii')` directly (line 1109). A direct `response.type('unknown-type')`/header assertion would be 5 lines and independent of filesystem and of how `download` resolves types. Prefer that, optionally keeping the download case.
3. `.expect('content-length', '11')` and the `body.toString()` round trip are unrelated to the fix; drop them (supertest returns a Buffer for octet-stream, so `text` is empty, which is why the author used `body`; asserting only the header avoids needing it).
4. Name `download file with unknown extension as octet-stream` is descriptive and in style.

### reset-content-body
Verdict: FIX-REQUIRED  Confidence: medium
1. Base failure: `expected '11' to equal '0'` at response.spec.ts:1502, the content-length assertion. Right reason, but the test reaches `assert.equal(text, '')` only after that; all three assertions are coupled to the chosen remedy (Content-Length: 0, no Content-Type), not merely "no body". That is acceptable for this fix but means a maintainer who prefers omitting Content-Length would have to change the test.
2. Neighbouring 304 test is the model (`do not send body or calculate content-length for a 304 response`, `notProperty(header,'content-length')`). This test reads similarly; name `do not send body for a 205 response` fine.
3. Untested paths the fix touches: `send()` with no body on 205 (hits the new branch too), non-string bodies (object/JSON; the branch removes Content-Type and Transfer-Encoding), streams/download on 205, HEAD. The PR justifies the branch with keep-alive framing, which no test proves (a second request on the same connection). Either add one of these or drop the framing claim from the PR.
4. Existing test at line 1427 loops over `resetContent` and calls `send('')`; I did not run it separately.

## Overall
- All eight tests fail on base for the claimed reason; cookie, uuid, toroute and lookup read most like their neighbours.
- Main test gaps: send-error loses enumerable error fields untested; redirect-qs ignores `?`/`#` edge forms; unknown-content-type tests `download` not `type()`; 205 tests framing claim not at all.
- Fix commit scope for toroute (`fix(redirect)`, not `fix(response)`) and trim unrelated assertions in unknown-content-type.
