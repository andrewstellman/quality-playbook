Experiments: /tmp/adonreview/scratch/S5/ (copies of base and fix trees; outputs below are verbatim from those runs).

### uuid-matcher
Verdict: SHIP
Confidence: medium
1. Behaviour change: ids with g-z in UUID shape (custom/legacy "uuid-like" ids) used to route, now 404. Bug fix, nothing relied-on in docs, but the PR doesn't say "previously-matching non-hex ids now 404". Optional one sentence.
2. Upper-case A-F and `cast` (toLowerCase) unchanged. No other users of the regex in src (not exhaustively grepped beyond matchers.ts).

### redirect-qs-separator
Verdict: SHIP
Confidence: medium
1. Old output for a target with `?` was `/foo?a=1?b=2` (src/redirect.ts:132 in base), which servers parse as a=`1?b=2`. Nobody can sensibly depend on it. Only `toPath` is affected: `back()` passes `url.pathname` only (redirect.ts ~line 275), and `toRoute` strips qs into withQs.
2. Newly observable: with `forwardQueryString: true` (config default path) a `toPath('/x?y=1')` on a request that has a query now yields `/x?y=1&<forwarded>`; duplicate keys become repeated params. PR mentions the forwarding case; fine.
3. Residual (pre-existing, not worsened): `/foo#f` or `/foo?` still get `?`/`&` placed oddly (`/foo?&a=1`). Out of scope; don't claim completeness.

### cookie-maxage-zero
Verdict: FIX-REQUIRED
Confidence: high
1. Real compat exposure the PR omits: define_config.ts:101 only normalises `cookie.maxAge` when truthy, so a global `cookie: { maxAge: 0 }` is kept as 0. Before: every cookie written with the config default was a session cookie. After: every such cookie is `Max-Age=0` and is deleted by the browser immediately. Anyone who used `0` (or `Number(env.X || 0)`) to mean "no persistence" silently loses all cookies after upgrade. PR text mentions "config default maxAge also lost" only as a symptom, not as a migration hazard. Must add: "behaviour change: `maxAge: 0` (including in config) now means expire immediately, previously ignored", and suggest semver note (minor/patch is debatable; flag to maintainers).
2. Verified fixed output (scratch f6): `maxAge:0` -> `k=v; Max-Age=0`; base -> `k=v`. `undefined`, `null`, `NaN`, `false` still dropped (fix is narrow, as PR says).
3. Inconsistency worth a line: string forms `'0'`/`'0s'` throw `Invalid duration expression` in both base and fixed (verbatim: `Error: Invalid duration expression "0"`), so PR's "type number | string" docs quote overstates; number 0 is the only zero form that works.
4. clearCookie uses `maxAge = -1` (response.ts:1188), unaffected.

### toroute-qs-mutation
Verdict: SHIP
Confidence: high
1. Only effect on existing users is that the caller's options object is no longer mutated (old code set `options.qs = undefined`). Anyone reading `options.qs` after the call sees it intact; nobody plausibly relied on it being wiped.
2. `urlFor` now receives `{}` instead of `undefined` when no options given; createURL uses `options?.prefixUrl` / `options?.qs` (src/client/helpers.ts:164,171) so identical result. Also the merge `defaultOptions || options ? {...}` path (url_builder.ts) handles `{}`.
3. `qs` key is now absent rather than present-but-undefined in what urlFor receives; no consumer distinguishes.

### send-error-object
Verdict: FIX-REQUIRED
Confidence: high
1. Breaking for real apps. Error subclasses with enumerable fields serialize usefully today. Verified on base (scratch exp.ts): `class Val extends Error{code='E_VALIDATION';status=422;messages=[...]}` -> JSON `{"code":"E_VALIDATION","status":422,"messages":[{"field":"email","message":"required"}]}`; an Error with `toJSON()` -> `{"ok":false,"msg":"x"}`. After the fix both become `text/plain` `Error: bad`. `response.send(err)` with custom/ validation errors is a common pattern; the PR's "actual: {}" example is only the plain-Error case, and the PR doesn't disclose the Content-Type flip (application/json -> text/plain) for these.
2. Information exposure: plain `new Error('boom')` went out as `{}`; now the message text goes to the client. Apps that `send(err)` in production now leak internal messages (DB errors etc.). Not stated in PR. (Flag to O2.)
3. The cited docs sentence ("Regular expressions and error objects are converted to a string by calling the `toString` method.") supports the intent, but the PR should narrow the change: e.g. only use `String(content)` when the error has no `toJSON` and no own enumerable props, or else document the break. As written it is a silent behaviour change of a public API.
4. Subclass with overridden `toString`, or `Error`-like objects from other realms (`instanceof Error` false), are handled inconsistently; not covered by test.

### lookup-route-error
Verdict: FIX-REQUIRED
Confidence: high
1. Undisclosed side effect: `E_CANNOT_LOOKUP_ROUTE` is in `ignoreExceptions` (src/exception_handler.ts:94-99, check at :212). Every `findOrFail`/`makeUrl`/`signedUrlFor`/`redirect().toRoute()` miss that used to be a reported, logged 500 becomes unreported. A typo'd route name in production stops appearing in logs. PR says the exception is "listed in ignoreExceptions" but not that this silences existing reports. Must state it.
2. Identity changes: `error.name` becomes `Exception` (verified: `name Exception status 500 code E_CANNOT_LOOKUP_ROUTE instanceof Error true`), gains `.code`/`.status`/`.help`. Code matching `err.message` still works (messages kept), `instanceof Error` still true. Mention.
3. PR over-claims coverage: src/client/url_builder.ts:54-56 still throws `new Error('Cannot lookup route ...')` for the client `urlFor` (the thing the docs call "the URL builder", v6-docs_references_exceptions.md:140). Only the router-side builders go through `findOrFail`. Either fix both or scope the title/text to `Router.findOrFail`.
4. Code smell relevant to compat: constructing with the default template then overwriting `error.message` post-hoc; stack header was checked and follows the new message, but a second error class or `new Exception(msg,{code,status})` is cleaner.

### unknown-content-type
Verdict: SHIP
Confidence: medium
1. Old behaviour literally wrote the string `Content-Type: false` (mime.contentType returns `false` for '' , '.nope', '.LICENSE'; verified in scratch). No one can depend on that.
2. Changes `response.type()` for all callers, not just download: `type('')` and unknown extensions now yield `application/octet-stream`. Inputs with a slash (`plain/text`, `application/x-foo`) still pass through (verified). PR states both. Consider one sentence that this is a public-API header change.
3. Clients that sniffed the old `false` value: none plausible.

### reset-content-body
Verdict: FIX-REQUIRED
Confidence: medium
1. Verified on fixed tree (scratch f34): `send(null)`, `resetContent()`, `send({a:1})`, `send('x', true)` all give `205 content-length: 0`, no body, no etag/content-type (base: chunked for empty, full body + content-type + etag for content). PR describes content-type/chunked change accurately.
2. Incomplete and inconsistent: `status(205).stream(readable)` is unchanged and still sends the whole body, `transfer-encoding: chunked` (verbatim from run: body equals the stream's file text). Same for `download`. The PR title claims "do not send content with a 205" without scoping to `send()`.
3. Silently discards user-set `Content-Type`/`Transfer-Encoding` and any user-set `Content-Length`/ETag on 205 (etag shows absent in run). Mention; also `HEAD` output now includes `content-length: 0` where base had none for empty 205.
4. Behavioural difference for anyone using 205 with payload (e.g. HTMX-like "reset + message", nonstandard): body now dropped. Must be called out as behaviour change, even though RFC 9110 15.3.6 supports it.

## Summary
SHIP: uuid-matcher, redirect-qs-separator, toroute-qs-mutation, unknown-content-type (PR text fine on compat, optional one-line notes).
FIX-REQUIRED: cookie-maxage-zero (global maxAge:0 now deletes all cookies), send-error-object (breaks Errors with enumerable props/toJSON; leaks message), lookup-route-error (silences error reporting; client url_builder.ts not fixed), reset-content-body (stream/download still bypass).
No REJECT, but send-error-object is the closest: as written it is a silent regression for common patterns.
