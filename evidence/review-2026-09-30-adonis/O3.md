### redirect-qs-separator
Verdict: SHIP (optional improvement below)
Confidence: medium
Findings:
1. The claimed cases are fixed: `/foo?username=virk&age=28`, forwarded `withQs()` gives `/foo?a=1&b=2`, and absolute `https://ex.com/x?y=1&age=28`.
2. Fragment targets are still wrong. This was already broken in base, so it is not a regression:
   - `toPath('/foo?a=1#frag')` gives `/foo?a=1#frag&age=28`. Base gave `…#frag?age=28`. In both, `age` sits inside the fragment and never reaches the server.
   - `/foo#frag` gives `/foo#frag?age=28` in both trees.
   - Optional fix: insert the query before any `#` (for example `const i = url.indexOf('#')`). If not done, leave it out of the PR text.
3. Duplicate keys are kept rather than merged: `withQs('username','x').toPath('/foo?username=virk')` gives `…username=virk&username=x`. `back()` and the unused `appendQueryString` (src/helpers.ts:321) merge with Object.assign instead, and a maintainer may ask why this path doesn't. `appendQueryString` can't be used as-is: it keeps only the pathname, so it would drop the host of absolute URLs.
4. `/foo?` gives `/foo?&age=28`. That URL is harmless.

### cookie-maxage-zero
Verdict: FIX-REQUIRED (PR text only)
Confidence: medium
Findings:
1. Values checked, base vs fixed: 0 changes from no Max-Age to `Max-Age=0`. -1, null, undefined, '', NaN and '2h' are unchanged. '0', '0s' and 0.5 throw in both trees, which is outside this fix.
2. There is a behaviour change the PR doesn't mention. `defineConfig({ cookie: { maxAge: 0 } })` normalizes to 0 (src/define_config.ts:101 skips 0). Base then emitted a session cookie (`k=v; Path=/; HttpOnly; Secure; SameSite=Lax`); the fix emits `k=v; Max-Age=0; …`. So an app that set maxAge 0 app-wide, meaning "session cookie", would have every cookie (signed, encrypted, plain) deleted immediately. Add one line to the PR saying so. "Other falsy values keep their current behaviour" is accurate but doesn't cover this.

### send-error-object
Verdict: FIX-REQUIRED
Confidence: medium
Findings:
1. Errors that serialized to something useful before now lose it. The new `instanceof Error` branch (src/response.ts:307) runs before `serializeJSON`:
   - Error with `toJSON()`: base gave `{"ok":1}`; fix gives `Error: x`.
   - poppinss `Exception('bad',{code,status})`: base gave `{"name":"Exception","status":400,"code":"E_BAD"}`; fix gives `Exception [E_BAD]: bad`.
   - Error subclass with enumerable `messages` (validation style): base gave `{"messages":[…]}`; fix gives `Error: Validation failure`.
   - Minimum fix: skip the branch when `typeof content.toJSON === 'function'`.
   - The PR must also state the change for errors with enumerable properties, or narrow the branch to errors with no own enumerable keys.
2. `response.json(new Error('boom'))` now returns `text/plain`, because json() is send() (src/response.ts:892). A json() call answering text/plain is newly surprising.
3. `jsonp(new Error('boom'))` now emits `callback(Error: boom);`, which is a syntax error in the browser. Base emitted `callback({})`. Date has the same problem already, but this fix adds another case.
4. Nested errors (`send({ error: err })`) still give `{"error":{}}`. That's fine, but the PR shouldn't imply errors in general are fixed.

### lookup-route-error
Verdict: FIX-REQUIRED
Confidence: high
Findings:
1. The fix is incomplete for the path the PR quotes. The PR cites the doc "raised when you attempt to create a URL for a route using the URL builder". After the fix:
   - `router.urlBuilder.urlFor('posts.show')` still throws a plain Error (instanceof false, code undefined), because src/client/url_builder.ts:54-56 has its own throw.
   - `response.redirect().toRoute('nope')` goes through urlFor and also still throws a plain Error.
   - Only findOrFail, makeUrl and signedUrlFor changed (instanceof true, code E_CANNOT_LOOKUP_ROUTE).
   - Either fix the client builder too (it's a dependency-light, browser-safe module, so that's a design question for the maintainers) or drop the URL-builder doc quote and say only findOrFail-based paths change.
2. The PR doesn't mention a logging consequence. E_CANNOT_LOOKUP_ROUTE is in `ignoreExceptions` (src/exception_handler.ts:97). `shouldReport(findOrFail error)` was `true` in base and is `false` with the fix. A bad route name in a signedUrlFor or makeUrl call becomes an unlogged 500 in production. That may be intended, but the PR has to say so.
3. Setting `.message` after construction still gives the right stack line 0: `Exception: Cannot lookup route "users.show" for method "POST"`. Status is 500, as the PR says.
