### send-error-object
Verdict: FIX-REQUIRED
Confidence: high
Findings:
1. NEW SCRIPT INJECTION VIA JSONP. The Error branch (src/response.ts:307) runs before the JSONP wrapper (src/response.ts:~335), so `response.jsonp(err)` now splices `String(err)` raw into JavaScript. Probe, fixed tree: `const e = new Error('alert(1)//'); e.name = ''; r.jsonp(e,'cb')` -> body `/**/ typeof cb === 'function' && cb(alert(1)//);` (text/javascript). Base: `cb({"name":""})`. Any Error whose toString is attacker-influenced and not prefixed by a name (name '', custom toString) becomes executable JS; an attacker only needs `alert(1))//`. Ordinary Errors also break JSONP: fixed -> `cb(Error: x);` (SyntaxError), base -> `cb({})`. Must change: keep Error on the JSON path when jsonpCallbackName is set, or JSON-encode the string (`JSON.stringify(String(content))`) before wrapping. Add a jsonp test.
2. toJSON BYPASS / INFO DISCLOSURE. Error subclasses with a sanitizing toJSON lose it. Probe: `class ApiError extends Error { toJSON(){ return {code:this.code} } }` -> base `{"code":"E_X"}` application/json; fixed `Error: secret internals` text/plain. Must change: only take the toString branch when `typeof content.toJSON !== 'function'` (and test it).
3. BEHAVIOUR CHANGE NOT STATED. Plain Errors went from `{}` to their message (probe: `Error: db password=hunter2 at /srv/app`). Also reaches clients via `response.abort(errorObj)` (src/errors.ts:110 sends error.body). Stack is not included (good). PR must say in one line that apps currently sending Error objects will start exposing `err.message`.
4. Good: output is pinned to text/plain, not routed through the string branch that sniffs `<` to text/html (probe: `<script>` message -> text/plain). Keep it that way.
After reading CONFIRMATION.md: confirmer flagged "decide toJSON precedence" as pushback; the PR draft did not act on it. Unchanged.

### redirect-qs-separator
Verdict: FIX-REQUIRED
Confidence: medium
Findings:
1. No open-redirect change: '&' is only chosen when '?' already exists, so appended text never touches scheme/authority (probe `https://example.com?x=1` -> `...?x=1&a=1`). encodeUrl still applied.
2. NEW PARAMETER-POLLUTION SHAPE. With forwarding (`withQs()` or `forwardQueryString: true`, default false at src/define_config.ts:62), request-controlled params now become real duplicates of params the developer hard-coded in the target. Probe `withQs().toPath('/login?role=user')` on `GET /?role=admin`: base `/login?role=user?role=admin` (garbled single value), fixed `/login?role=user&role=admin`. Last-wins parsers downstream give `admin`. Low severity (opt-in forwarding), but the fix creates it. Must change one of: (a) parse the target's own query and merge into the `query` object so keys dedupe with explicit precedence (developer's inline/withQs values over forwarded ones); or (b) state the duplicate-key behaviour in the PR. (a) preferred.
3. Minor, pre-existing: `'?'` inside a fragment (`/foo#sec?x`) is treated as a query (-> `/foo#sec?x&a=1`); base equally wrong. Not a regression; optional.
After reading CONFIRMATION.md: confirmer notes an unused `appendQueryString` helper (src/helpers.ts:321) that merges with Object.assign; using it dedupes keys but makes forwarded values override the target's inline ones. If adopted, pick precedence deliberately; don't let request input win over developer-fixed params.

### unknown-content-type
Verdict: SHIP
Confidence: medium
Findings:
1. Security-positive. `download()` (src/response.ts:967) sets no Content-Disposition, so extension-less user files were served inline with `Content-Type: false` (probe: body `<script>alert(1)</script>`, ct `false`). An unparseable MIME type invites browser sniffing; octet-stream does not render inline. 3. Process note for Andrew: if anyone wants to claim XSS here, that belongs in a private advisory, not the public PR. As a plain bug fix it is fine publicly.

### lookup-route-error
Verdict: FIX-REQUIRED
Confidence: high
Findings:
1. LOGGING SUPPRESSION NOT DISCLOSED. E_CANNOT_LOOKUP_ROUTE is in `ignoreExceptions` (src/exception_handler.ts:97) and `shouldReport` returns false for it (:212). Today a failed lookup is a plain Error normalized to status 500 and logged at `error` level (:172, :405-413); after the fix those 500s are rendered but never logged. The PR cites the ignoreExceptions listing as supporting evidence without saying this. Must add one sentence: "Lookup failures will no longer be reported by the default exception handler, since the exception is in ignoreExceptions."
2. Client-visible output unchanged: non-debug render sends `{message}` / `<p>message</p>` with the same message text; the route identifier was already exposed.
3. Scope: `router.urlBuilder.urlFor` (src/client/url_builder.ts:54-56, used by `redirect().toRoute`) still throws a plain Error. The PR's "also covers makeUrl, the legacy builder and signedUrlFor" is accurate but reads as full coverage; say urlFor is unchanged.
After reading CONFIRMATION.md: confirmer calls the logging side-effect "by design". Plausible, but it's still a change for existing users and must be stated. Unchanged.

### cookie-maxage-zero
Verdict: SHIP
Confidence: high
Findings:
1. Security-positive: `maxAge: 0` (the usual "delete this cookie" idiom) produced a session cookie that persisted until browser close. Probe: base `k=...; Path=/; HttpOnly`, fixed `k=...; Max-Age=0; Path=/; HttpOnly`. The PR's actual/expected block shows this; no need for security framing.
2. No new surface: NaN still dropped (both trees); `'0'` throws `Invalid duration expression "0"` in both trees (pre-existing, out of scope); -1 -> `Max-Age=0` unchanged. clearCookie (src/response.ts:1185-1188) uses -1 and is unaffected.

### toroute-qs-mutation
Verdict: SHIP

Findings:
1. Removes shared mutable state across requests (brisk route options object mutated on first request). No security consequence beyond correctness; PR correctly doesn't claim any.

### reset-content-body
Verdict: SHIP
Confidence: medium
Findings:
1. Framing is safe: explicit `Content-Length: 0` (probe: `205 | cl=0 | body=""` for string and JSON bodies). Node doesn't treat 205 as body-less, and RFC 9112 §6.3 doesn't exempt it either, so ending with CL 0 keeps keep-alive framing unambiguous. Removes a small desync risk with intermediaries that assume 205 carries no body. No cache-poisoning angle found.
2. Not covered, not security: `status(205).stream(...)` still sends a body (probe: body `abc`, both trees), as do download paths. Optional note in the PR ("send() path only").

### uuid-matcher
Verdict: SHIP
Confidence: high
Findings:
1. Security-positive input validation: apps relying on the matcher to reject non-UUIDs before DB queries (e.g. Postgres uuid columns -> 500 on bad input) get a 404 instead. PR doesn't frame it as security; keep it that way.
2. Regex is anchored and fixed-length, so no ReDoS. `grep -rn "a-zA-F" src tests` found only this one site.

## Overall
Two fixes change security-relevant behaviour in ways the PRs don't handle: send-error-object opens JSONP script injection and bypasses toJSON (code change required), and redirect-qs-separator turns forwarded query params into real duplicate keys (dedupe or disclose).
lookup-route-error silently stops default-handler logging of lookup 500s; state it. None of the eight PRs overclaims security; unknown-content-type, cookie-maxage-zero and uuid-matcher are quiet security improvements and should stay unframed.
