### uuid-matcher
Verdict: SHIP
Confidence: high
Findings:
1. Probe on fixed tree: a valid UUID with `g` or `z` substituted at positions 0,9,14,19,24,35 gives `[false x6]` (base: `[true x6]`); valid lower/upper UUID still true; trailing "\n" false. Fix is correct.
2. Test gap (minor): the new test uses all-`z` and all-`g` strings, which would also pass for a regex that only checked the first char class wrongly in one segment. Better negative: a real UUID with one `g` in a single segment. Optional, not blocking.
3. No route-level test (`.where('id', router.matchers.uuid())` then 404); matcher-level is consistent with neighbouring tests, so fine.

### redirect-qs-separator
Verdict: FIX-REQUIRED
Confidence: medium
Findings:
1. Fragment case still wrong (probe, fixed tree): `toPath('/foo?x=1#frag')` + withQs({a:1}) -> `/foo?x=1#frag&a=1` (qs lands inside the fragment, browser never sends it); `/foo#frag` -> `/foo#frag?a=1` (same as base). The PR title/text claims general "append query string"; either handle `#` (insert before the fragment) or state the fragment limitation. Test does not build this input.
2. Trailing separator: `/foo?` -> `/foo?&a=1`, `/foo?x=1&` -> `/foo?x=1&&a=1` (base gave `??`/`&?`). Harmless but untested; decide intent (src/redirect.ts:132 `url.includes('?')`).
3. PR claims "the same happens with withQs() forwarding the current request's query onto such a target" (fixed-tree probe confirms `/foo?x=1&b=2`), but the new test only covers explicit `withQs('age', 28)`. Add a `redirect('/foo?x=1', true)` / `withQs()` forwarding test or drop the claim.
4. `includes('?')` also matches a `?` inside a fragment or an absolute URL's later parts; acceptable, but confirms finding 1.

### cookie-maxage-zero
Verdict: FIX-REQUIRED
Confidence: medium
Findings:
1. Undisclosed compat hazard (probe, fixed tree): server config `cookie: { maxAge: 0 }` (number 0 is not touched by define_config.ts:101 `if (normalizedConfig.cookie.maxAge)`) now emits `Max-Age=0` on EVERY cookie (`k=eyJ...; Max-Age=0`; base: no Max-Age). Anyone using `maxAge: 0` in config to mean "session cookie" silently gets cookies that expire immediately. PR must mention this and/or the maintainer must decide; no test covers config-level 0.
2. The user-facing scenario (per-call `maxAge: 0` overriding a config default like `'2h'`, via `response.plainCookie/cookie/encryptedCookie`) is untested; the test only calls `CookieSerializer.encode` (tests/cookies/serializer.spec.ts). Add a response.spec.ts test on `plainCookie(..., { maxAge: 0 })`. Probe: fixed -> `k=...; Max-Age=0; Path=/; HttpOnly`.
3. Inconsistency left behind: string `'0'` / `'0s'` still throw `Invalid duration expression` (both trees), while number 0 now works. PR says "other falsy values keep current behaviour" (true: '', null, undefined, NaN, false unchanged) but does not mention `'0'`.
4. Condition `options.maxAge || options.maxAge === 0` is fine for -0 (probe: Max-Age=0).

### send-error-object
Verdict: FIX-REQUIRED
Confidence: high
Findings:
1. Regression for Error subclasses with `toJSON` or enumerable props (probe): base `{"code":"E_X","m":"c"}` / `{"code":"E_Y","detail":{"a":1}}`; fixed `Error: c` / `Error: p` as text/plain. The `instanceof Error` check at src/response.ts:307 precedes the object/JSON branch. Users doing `response.send(validationError)` who get JSON today get text after this. PR doesn't mention it; no test. Options: narrow to errors without own enumerable keys / without toJSON, or state the break.
2. `response.json(new Error('boom'))` now returns `text/plain; charset=utf-8` `Error: boom` (probe) - json() returning non-JSON. Untested.
3. `jsonp(new Error('boom'))` now emits `callback(Error: boom);` (probe) - syntactically invalid JS, and message text is interpolated unquoted into a script (injection surface if message has user input). Same pre-existing pattern for Date/RegExp, but Error messages are far more likely to carry input. Test needed at minimum; maintainer/security decision.
4. Info-disclosure behaviour change: `{}` (hid message) becomes `Error: <message>` in the body; PR frames it as pure bug fix. Mention.
5. Test covers only plain `new Error('boom')`; add subclass (TypeError) and empty-message cases (probe: `new Error('')` -> body `Error`). Also status/etag untouched, fine.
