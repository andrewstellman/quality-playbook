# S6 PERFORMANCE

Method: read each fix.patch and the touched base code (helpers.ts, response.ts, redirect.ts, router/main.ts, errors.ts). I did not read CONFIRMATION.md or any other reviewer's output. I ran two checks of my own.
- A microbenchmark of the added `instanceof Error` (`node /tmp/b.mjs`).
- A look at the `findOrFail` error message and stack (`node /tmp/s6.mts`).

No PR-DRAFT makes a performance claim. `grep -i "perf|fast|alloc|hot"` over all eight PR-DRAFT.md files returned nothing. The performance findings below are for the record and none of them needs to appear in any PR text.

### uuid-matcher
Verdict: SHIP
Confidence: high
1. src/router/matchers.ts:31. A class-range swap (`A-F` to `a-f` inside `[0-9a-fA-F]`). The regex has the same shape, anchors and fixed quantifiers, so there is no backtracking or ReDoS surface and no measurable match-time change. The literal is still created once per `uuid()` call, as before.
2. Nothing to change for performance.

### redirect-qs-separator
Verdict: SHIP
Confidence: high
1. src/redirect.ts:129-134. Adds one `url.includes('?')`, and only when a query string is non-empty. It is an O(len) scan on a short string, on a redirect path that also runs `encodeUrl` and `send`, so the cost is noise.
2. The no-qs path is cheaper than before: no template string is built when `stringified` is empty. The `if` replaces the ternary without adding an allocation.
3. Nothing to change for performance.

### cookie-maxage-zero
Verdict: SHIP
Confidence: high
1. src/helpers.ts:245-246. `options.maxAge || options.maxAge === 0` only evaluates the second operand when maxAge is falsy, so the common case (undefined or a positive value) costs one extra comparison at most. `string.seconds.parse(0)` is now called for 0, which is the intended behaviour and is not hot.
2. Nothing to change for performance. The formatting is Prettier-wrapped and lint belongs to S1 and S8.

### toroute-qs-mutation
Verdict: SHIP
Confidence: medium
1. src/redirect.ts:309. `const { qs, ...urlOptions } = options || {}` allocates a fresh object on every `toRoute` call, including when no options were given (`{}`). Before, nothing was allocated. `urlFor` previously received `undefined` and now receives `{}` (possibly an empty copy). This is a per-redirect allocation measured in tens of bytes, next to `urlFor`, `qs.stringify`, `encodeUrl` and the response write, so it is irrelevant. It is also the price of removing the mutation.
2. Not a performance issue, but for S3 and O3 to confirm: `{}` versus `undefined` reaching `urlFor`. I did not verify that `urlFor` treats them identically. If the existing suite passes (EXEC's job), there is nothing to change.
3. Nothing to change for performance.

### send-error-object
Verdict: SHIP
Confidence: high
1. src/response.ts:307. The added `|| content instanceof Error` sits before the `Date` and generic-object branches. Every JSON object or array body now pays one extra prototype-chain `instanceof Error` check on the hottest send path. Microbenchmark (/tmp/b.mjs, 5e7 iterations, node):

   ```
   false 6.29 ns/iter   (no Error check)
   true  7.83 ns/iter
   false 5.46 ns/iter
   true  6.92 ns/iter
   ```
   That is about 1.5 ns per call, which is invisible next to `serializeJSON` (`JSON.stringify`), `Buffer.byteLength` and the etag. Do not mention it in the PR.
2. The Error branch itself does `String(content)`, which is cheaper than the old `JSON.stringify` of an Error, so the error path gets slightly faster.
3. Nothing to change for performance.

### lookup-route-error
Verdict: SHIP
Confidence: high
1. src/router/main.ts:545-550. All new work is on the not-found path, which already throws. The success path is unchanged: `this.find(...)` and `return route`.
2. On the failure path the old code built a template string and a plain Error. The new code builds an `E_CANNOT_LOOKUP_ROUTE` through `createError`, which formats with `%s`, and then reassigns `message` when a method is given. The extra cost is microseconds at most, on an exceptional path. I checked with `findOrFail('a', undefined, 'POST')`. It prints `Cannot lookup route "a" for method "POST"`, and the first stack line carries the updated message as well. Nothing is hidden by the post-construction reassignment.
3. `findOrFail` is reached from `urlFor` (main.ts:766 and :794) and from signed_url_builder.ts:61. A not-found route is a programmer error there, not a steady-state request path, so the error cost does not matter.
4. Nothing to change for performance. Non-perf point for others: mutating `error.message` after construction is slightly unusual, and a dedicated message format would be cleaner.

### unknown-content-type
Verdict: SHIP
Confidence: high
1. src/response.ts:768. `mime.contentType(type) || 'application/octet-stream'` adds a falsy test and no allocation (the literal is interned). `type()` is called on every redirect (`type('text/plain; charset=utf-8')`), on download, and in the stream and text paths (response.ts:430, 504, 551). Cost is unmeasurable.
2. The normal send path in `writeBody` sets Content-Type from `CONTENT_TYPES` directly and does not go through `type()`, so the hot path is untouched.
3. Nothing to change for performance.

### reset-content-body
Verdict: SHIP
Confidence: medium
1. src/response.ts:287-298. The new guard `statusCode === ResponseStatus.ResetContent` runs on every non-empty, non-1xx/204/304 response. It is one integer compare, which is negligible. The branch body (two `removeHeader` calls, one `header('Content-Length', 0)`, `#endResponse`) runs only for 205.
2. The 205 branch is placed before `if (hasEmptyBody)`, so a bodyless `status(205)` response now also takes it. Before, it fell into the empty-body branch, which removed Content-Length and ended the response. Now it sends `Content-Length: 0`. This is not a performance cost. It is a behaviour change that the test does not cover (the test only sends a body). S4 and S5 should own it. From a framing standpoint it is arguably better, since Node would otherwise fall back to chunked framing on a 205, and the PR draft's own rationale says so.
3. Nothing to change for performance.

## Summary
- All eight changes are performance-neutral. The only hot-path additions are one `instanceof Error` (about 1.5 ns, measured) on JSON sends and one integer compare on body writes. The rest is on error, redirect or cookie-set paths.
- No regex redesign, no new per-request allocation on routing or cookie hot paths, and no PR text makes performance claims, so nothing needs to be added or removed on performance grounds.
- Caveats: I measured with a synthetic microbenchmark only and did not profile the real server. I did not verify the `{}` versus `undefined` handling in `urlFor`, and I did not run the test suites.
