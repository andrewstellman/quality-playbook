## Process gaps common to all 8 (the real risks)
1. CONTRIBUTING.md "Creating pull requests": "we highly recommend you to kick off a discussion ... before starting any new work"; "PRs for bugs are mostly accepted once the bug has been confirmed." No issue/discussion exists for any of the 8. The PR template (org .github) has "Linked issue: Please ensure there is an open issue and mention its number" and checklist "I have linked an issue or discussion." Opening 8 PRs with that box unticked invites "please open an issue first" closure.
2. The PR-DRAFT text ignores the org PR template (Linked issue / Type of change / Description / Checklist). GitHub pre-fills the template, so the draft must be placed inside it; otherwise maintainers see empty sections plus your text. Tick "Bug fix" for all; "Breaking change" needs a deliberate decision on 205, send-error, unknown-content-type, cookie-maxage-zero, lookup-route-error (see S5).
3. The template asks "I have updated the documentation accordingly." No PR touches docs; drafts do not say "no docs change needed" (true for most, since the fixes bring code in line with docs).
4. AI disclosure: line "Found by Quality Playbook, an AI code-review tool, with Claude; I reviewed the change." adonisjs has no AI policy (checked GOVERNANCE.md and CONTRIBUTING.md; grep for AI/LLM/generated/agent found nothing), so disclosure is not required, and what you have is honest. It is also the only place the tool is named; commit messages carry no trailer, which is acceptable. Note "with Claude" plus "I reviewed" is a claim you must make true per PR.
5. Batch flood: 8 PRs at once from a first-time contributor, all touching overlapping files (response.ts x4, redirect.ts x2). Recent merged outside fixes are single PRs. Process risk, not a rule violation. Stacked apply is conflict-free, so sequencing is possible.
