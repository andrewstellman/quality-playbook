### reset-content-body
Verdict: FIX-REQUIRED   Confidence: high
1. RFC quote verified verbatim (rfc9110 s.15.3.6): "Since the 205 status code implies that no additional content will be provided, a server MUST NOT generate content in a 205 response." Section number correct.
2. "writeBody drops content only for 1xx, 204 and 304": verified (response.ts ~268-285).
3. "resetContent() previously sent Transfer-Encoding: chunked with an empty chunk": I ran it against base; on the wire: `HTTP/1.1 205 Reset Content ... Transfer-Encoding: chunked\r\n\r\n0\r\n\r\n`. Verified.
4. "Node doesn't treat 205 as body-less, and plain header stripping would leave a keep-alive response unframed" is overstated. Bare Node `res.statusCode=205; res.end()` yields `content-length: 0` (I ran it); `write('')` then `end()` yields chunked. So the unframed claim is false in the bare case; the real problem is the chunked-empty-chunk path. Reword to what was observed: "Node sends Transfer-Encoding: chunked for a 205 with no Content-Length; an explicit Content-Length: 0 is cleaner." Also the inline comment repeats the claim.
5. "expected: ... no content-type": consistent with code (removeHeader('Content-Type')).
