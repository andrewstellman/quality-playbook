# O4: FIX-REQUIRED (medium)

Role: not-a-bug advocate. I tried to find a reason the maintainer would call this intended, declined or not worth it. I found none for the bug itself. I found one real weakness in the patch (finding 1) and two text points.

## Blind verdict (written from the patch, PR.md and source, before CONFIRMATION.md)

The defect is real and not intended. Run in my own copy (/work/batch/runs/cronstrue/scratch/panel-cronstrue-list-step-separator-O4) at HEAD~1 (c08a7d6):
```
0 9 * * 5,0-4/2 => At 09:00 AMonly on Friday and , every 2 days of the week, Sunday through Thursday
0 9 * * 5,*/2 => At 09:00 AMonly on Friday and , every 2 days of the week
0 9 1,*/5 * * => At 09:00 AMon day 1 of the month and , every 5 days in a month
```
At HEAD (fix): `At 09:00 AM, only on Friday and every 2 days of the week, Sunday through Thursday`.

Arguments for "not a bug" that I tried and why they fail:
- Documented/intended: README:17 only says "Supports all cron expression special characters including * / , - ? L W, #". No test, comment or README line pins "AMonly" or " , ". 286434e (#374, Fixes #194) added the strip to remove double commas for `0 9 * * 0-4/2,5,6`; the glue at the first member is a side effect of a missing `i > 0`.
- Previously declined: no unmerged PR head touches the multiple-values loop (only pr/374 and pr/370, both about #374, merged). known_open_bugs.md lists only #384 and #387 (W offsets). Closed issues and PRs were not searched (forge unreachable).
- Invalid input: `5,0-4/2` and `1,3-9/2` are valid Vixie-cron lists of value and range/step. In scope.
- Better fixed elsewhere: no. The loop is the only place that composes list members.
- Rare shape: true, but the output is visibly garbled, not merely awkward.

Side-effect rule. Who is affected: anyone whose list has a step member in day-of-month, month, day-of-week or year and the step is not first, in any locale, plus anyone who snapshot-tests the old garbled string. What happens: "AMonly ... and , every" becomes "AM, only ... and every". Likelihood: low (mixed list with a step is rare). Nobody can sensibly depend on the old text, so I do not call this a harmful change. Changed-output scope in my own sample (860 expression/verbose pairs, en): 606 lines differ, all in lists with a step member; none got worse.

Checks I ran:
- `/work/batch/runs/cronstrue/bin/run-tests` on my copy: `406 passing`.
- `prettier --check src/expressionDescriptor.ts test/cronstrue.ts`: warns on test/cronstrue.ts. Same warning on the base file (I formatted-checked HEAD~1's copy: `[warn] test/_b.ts`), so not caused by the patch. Matches lint.log.

## Findings

1. FIX-REQUIRED (scope of the fix, src/expressionDescriptor.ts:594-595). PR.md "Not covered" says `0 9 * * 1-3,*/2` still prints "AMMonday through Wednesday and every 2 days of the week" and was left out "to keep this change small". That is the same root cause in the same loop: the first member's leading ", " is removed (`replace(", ", "")` runs for i = 0), so the first member runs into the time. It is also the commoner shape (range first). I ran the one-condition change on my copy and it fixes it:
   ```
   if (isSegmentRangeWithoutIncrement && (i > 0 || !doesExpressionContainIncrement)) {
   ```
   Output after that change (my copy only, not saved):
   ```
   0 9 * * 1-3,*/2 => At 09:00 AM, Monday through Wednesday and every 2 days of the week
   0 9 * * 1-3,5-6/2 => At 09:00 AM, Monday through Wednesday and every 2 days of the week, Friday through Saturday
   0 9 * * 1-3,5 => At 09:00 AM, only on Monday through Wednesday and Friday
   ```
   and `run-tests` still gave `406 passing` (I did not run the 849,660-combination comparison on this variant, and did not add a test for it). Either (a) add this condition plus one test case `0 9 * * 1-3,*/2` to the same PR, or (b) keep the PR as is but expect the maintainer to say "the same list still glues AM". With the patch as is, the PR text and the title ("plain first value") are accurate, so this is a judgement call, not a falsehood. I lean to (a) because it is one token and the same function. If the operator wants the minimum change, state in PR.md that the range-first case is the same cause (it already says so) and offer a follow-up.

2. PR.md claim that cannot be checked from the packet: "I compared old and new output over 849,660 list combinations in every locale, verbose on and off." I did not re-run that. Check suite.log or the script that produced the number exists; if it does not, replace the sentence with what was run. Suggested replacement if only a sample was run: "I compared old and new output for a sample of list expressions in every locale, verbose on and off. Output changed only when a later list member has a step."

3. PR.md vi/sw sentence: "In `vi` and `sw` the step text starts with its own comma phrase that was stripped with the comma before; it now stays". The new vi text "mỗi ngày 2 tháng" literally reads "every day 2 month", which looks like a pre-existing locale wording problem now visible in a list. The PR already says "I did not judge that wording", which is fine. Keep it, but under the locale-wording rule do not expand it.

The patch is 2 source hunks, +11/-1 with test, no locale file edited. It changes output in all locales through shared code, not locale wording. I rate it trivial. The operator could still open an issue first, but I do not require it.
