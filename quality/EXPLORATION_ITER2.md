## Gap-1 (CONFIRMED → BUG-006): Greedy JSON-array extraction in the Council Layer-2 parser

- **Location:** `bin/council_semantic_check.py:319` (`_JSON_ARRAY_PATTERN = re.compile(r"\[[\s\S]*\]")`) consumed by `_extract_first_json_array` (`:322-343`) and `parse_member_response` (`:252-316`).
- **Trace across functions:** `parse_member_response` (`:268`) calls `_extract_first_json_array`; the fast path (`:330-335`) only handles a response that is a *pure* JSON array; the fallback (`:337-343`) applies the greedy regex (first `[` → last `]`) and does a single `json.loads(match.group(0))`. The docstring (`:322-328`) promises the "first `[...]` balanced block" / "outermost `[...]` that parses" — the implementation delivers neither (greedy, not balanced, single attempt).
- **Bug hypothesis → confirmed by execution:** a valid Council member response whose trailing prose contains any `]` (e.g. `[{...valid...}]\nNote: see item [2].`) extends the greedy match past the array → `json.loads` fails → `None` → `parse_member_response` raises `SemanticCheckError` ("response does not contain a JSON array"). A control without the trailing `]` parses. Both runs executed (see `quality/results/BUG-006.{red,green}.log`).
- **Consequence:** on a with-docs run (Tier 1/2 REQs present), a dropped reviewer → `<3 reviews` for that REQ → gate FAIL (schemas.md §9.4 / §10 invariant #17) — a *false audit failure*. No-op on Spec-Gap runs (this self-audit had 0 Tier 1/2 REQs, so the semantic check is skipped — which is exactly why the baseline missed it).
- **Candidate → promoted:** BUG-006 (MEDIUM, REQ-010), TDD-verified, fix `quality/patches/BUG-006-fix.patch`.

## Gap-2 (candidate, not promoted): Tier-vs-bool inconsistency in the Layer-2 collector

- **Location:** `bin/council_semantic_check.py:134-135` (`tier = rec.get("tier"); if tier not in (1, 2): continue`).
- **Finding:** `True in (1, 2)` is `True` in Python (`True == 1`), so a malformed REQ with `tier: true` would be treated as Tier 1 and reviewed. The sibling check at `:154` (`isinstance(line, int) and not isinstance(line, bool)`) deliberately excludes `bool` for the `line` locator — the `tier` check does not. A within-function inconsistency.
- **Why not promoted:** `tier` originates from `requirements_manifest.json`, which the gate validates as an integer member of the tier enum (schemas.md §3.1) — a `bool` tier cannot survive manifest validation. So the inconsistency is a robustness/defensive-coding smell with no reachable real-world trigger. Recorded as a hypothesis, not a confirmed bug.

## Gap-3 (candidate, not promoted): Batch/parse contract for >15 Tier-1/2 REQs

- **Location:** `build_prompts_for_member` (`:209-238`, batches of 5 when `>15` REQs) vs `parse_member_response` (`:310-314`, requires EVERY `expected_req_ids` member in one response).
- **Finding:** if a caller passes the full REQ-id set as `expected_req_ids` while sending batched (partial) prompts, the parser raises "missing review(s)". Whether this is reachable depends on the LLM-driven caller (Layer-2 is operator-driven per SKILL §9.2, one prompt per member), which is not in the code under audit. Recorded as a hypothesis for a future with-docs run with >15 Tier-1/2 REQs.
