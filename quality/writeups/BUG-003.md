# BUG-003 — Relaunched PENDING entry keeps state=PENDING

> Generated by [Quality Playbook](https://github.com/andrewstellman/quality-playbook) v1.5.7 — Andrew Stellman
> Date: 2026-05-30 · Project: quality-playbook

## 1. Summary
`_launch_one_run_detached`'s returned manifest-entry dict (`bin/harness/plan_runner.py:1844-1872`) has no `state` key, so the `_retry_pending_runs_once` merge (`:2538`) leaves the prior `state="PENDING"` even though the run is now live with a pid.

## 2. Spec reference
Tier-3. `CONTRACTS.md` C-05/C-06 + REQ-003: *"after a successful retry relaunch, the manifest entry's state must reflect RUNNING (not remain PENDING)."*

## 3. The code
The return dict starts `{"index": ..., "pid": spawn.pid, ...}` with no `"state"`. The merge `{**e, **update}` preserves the existing `"PENDING"`. Nothing downstream re-sets it to RUNNING.

## 4. Observable consequence
Status/grouping surfaces show a live retry-spawned run as PENDING. The collect loop still processes it (it has a pid), so today the consequence is observability drift — but any future code that filters the collect loop on `state != "PENDING"` would silently skip the run.

## 6. The fix
```diff
--- a/bin/harness/plan_runner.py
+++ b/bin/harness/plan_runner.py
@@ _launch_one_run_detached return dict
     return {
         "index": plan_run.index,
+        # BUG-003 fix: mark the spawned run RUNNING so a relaunch over a
+        # PENDING manifest entry transitions it out of PENDING.
+        "state": "RUNNING",
         "description": plan_run.description,
```
Full patch: `quality/patches/BUG-003-fix.patch` (applies cleanly).
