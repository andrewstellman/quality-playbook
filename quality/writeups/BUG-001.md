# BUG-001 — Collector grades still-PENDING (un-launched) runs as FAILED

> Generated by [Quality Playbook](https://github.com/andrewstellman/quality-playbook) v1.5.7 — Andrew Stellman
> Date: 2026-05-30 · Project: quality-playbook

## 1. Summary
`collect_harness_run` grades a starved run that has not yet acquired a provider slot (`state="PENDING"`, `pid=None`) as **FAILED** on the first collector sweep (`bin/harness/plan_runner.py:2606` submit loop → `:2123-2146` orphan-poll). This defeats the `ABANDONED_STARVED` deadline (instruction 165, default 3600s) that exists to give starved runs time to acquire a slot across passes.

## 2. Spec reference
Tier-3 (no external spec). Contract `CONTRACTS.md` C-01/C-03/C-07 + REQ-001: *"collect_harness_run must not assign a terminal state to a manifest entry with state=PENDING and pid is None that is within its _pending_deadline_s() window."*

## 3. The code
`_collect_one_run_detached` has no PENDING/pid=None guard; with `pid = entry.get("pid")` = None, the orphan-poll loop enters the "process gone" branch (`plan_runner.py:2123`) and, with no `gate-report-latest.json` and no `quality/` dir, sets `terminal = TerminalState.FAILED` (`:2146`). `runner._classify_stream_terminal` returns `(None,"")` for the missing stream (`runner.py:1043-1044`), so nothing prevents it. A never-launched run is treated identically to a crashed one.

## 4. Observable consequence
A run that is legitimately queued (provider cap full) gets a `grading.json` sentinel with `terminal_state=FAILED` within seconds of the collector starting — long before the 3600s deadline. The 165 retry/abandon mechanism never gets a chance; benchmark numbers undercount completed work and overcount failures.

## 5. Depth judgment
The bug only manifests under starvation (provider cap < number of queued runs) — exactly the condition instruction 161/165 added PENDING manifest entries to handle. On an unconstrained run no entry is ever PENDING at collect time, which is why the unit test (`test_collector_retry_165.py`) — which exercises `_retry_pending_runs_once` in isolation — never caught it.

## 6. The fix
```diff
--- a/bin/harness/plan_runner.py
+++ b/bin/harness/plan_runner.py
@@ _collect_one_run_detached, after the ABORTED_PREP block
         _release_slot()
         return outcome
 
+    # BUG-001 fix: a still-PENDING entry with no pid has not launched yet
+    # (starved, awaiting a slot). It is NOT a crashed run — leave it ungraded
+    # for the next collector pass / _retry_pending_runs_once.
+    if (entry.get("state") == "PENDING" and entry.get("pid") is None
+            and not grading_path.is_file()):
+        return RunOutcome(
+            index=plan_run.index, description=plan_run.description,
+            repo=plan_run.repo, runner=plan_run.runner.value,
+            model=plan_run.model, phase_yn={f"P{i}": "-" for i in range(7)},
+            gate_verdict="N/A", result="PENDING", terminal_state="PENDING")
+
     # ----- ORPHAN POLLING: wait for the AI-CLI to terminate -----
     pid = entry.get("pid")
```
Full patch: `quality/patches/BUG-001-fix.patch` (applies cleanly).
