# BUG-005 — pid=0 reservation with malformed started_at is active forever

> Generated by [Quality Playbook](https://github.com/andrewstellman/quality-playbook) v1.5.7 — Andrew Stellman
> Date: 2026-05-30 · Project: quality-playbook

## 1. Summary
`_entry_is_active` (`bin/harness/inflight_registry.py:343-345`) returns `True` immediately for a `pid=0` entry whose `started_at` fails to parse, so such a reservation never ages out and permanently consumes one unit of the per-provider cap.

## 2. Spec reference
Tier-3. `CONTRACTS.md` C-10 + REQ-005: *"a pid=0 registry entry must always carry a parseable started_at so the 300s age-out applies; or _entry_is_active must age out malformed-timestamp reservations."*

## 3. The code
```
pid = entry.get("pid", 0)
if pid == 0:
    started = _parse_iso_utc(entry.get("started_at"))
    if started is None:
        return True            # <-- active forever, no upper bound
```
The comment defends this as "never mass-reap on a parse failure" (`:339-340`) — sound for transient glitches, but it gives an unbounded lifetime to a malformed `pid=0` reservation.

## 4. Observable consequence
A single `pid=0` entry with a bad `started_at` permanently reduces the provider's effective cap by one. Current spawn paths write a valid `started_at`, so this is **latent** (hence MEDIUM): it requires a future or alternate reservation site to omit/corrupt the timestamp.

## 6. The fix
Proposed (inline only — apply decision deferred to the maintainer, see below):
```diff
--- a/bin/harness/inflight_registry.py
+++ b/bin/harness/inflight_registry.py
@@ _entry_is_active, pid==0 branch
     if pid == 0:
         started = _parse_iso_utc(entry.get("started_at"))
         if started is None:
-            return True
+            # BUG-005: a well-formed reservation always writes a parseable
+            # started_at; a malformed one on a pid=0 entry is stale, not fresh.
+            return False
```
**No separate `.patch` file / confirmed-open:** the current `return True` is a documented intentional choice ("never mass-reap on a parse failure"). The fix trades the phantom-slot risk for a mass-reap-on-transient-glitch risk; that tradeoff is a maintainer judgment call (Human Gate, see `quality/challenge/BUG-005-challenge.md`). The bug is real and executed; the apply is deferred.
