## Pass 1: Structural Review

Read the code and report anything incorrect or suspicious. Do not use requirements yet.

### Guardrails

- Line numbers are mandatory.
- Read function bodies, not just names.
- If unsure: mark the item `QUESTION`, not `BUG`.
- Grep before claiming a behavior is missing.
- Do not suggest style changes or refactors.

### Required scrutiny areas

#### 1. Input validation and boundary handling

Check every trust boundary where repository state enters helper logic:

- Documentation-tree classification in `bin/run_playbook.py`
- Filesystem walking in `bin/reference_docs_ingest.py`
- Archive parsing in `bin/archive_lib.py`
- JSON loading and normalization in `bin/role_map.py`

#### 2. Resource lifecycle

Check tempfile, atomic-write, and file-rewrite paths:

- `bin/role_map.py:normalize_role_map_for_gate()`
- manifest writers in `bin/reference_docs_ingest.py`
- any archive write helpers in `bin/archive_lib.py`

If no leak or cleanup hazard exists in a reviewed function, say so explicitly.

#### 3. Concurrency and state management

QPB is mostly single-threaded, but state transitions still matter. Review:

- phase-boundary state in `bin/run_state_lib.py`
- documentation-state transitions in `bin/run_playbook.py`
- direct vs runner-driven role-map lifecycle in `bin/role_map.py`

If there is no true concurrent mutation in a reviewed slice, document that and focus on state-machine completeness instead.

#### 4. Unit and encoding correctness

Check any code that interprets lines, headings, byte counts, timestamps, or UTF-8 text:

- heading regexes in `bin/archive_lib.py`
- text decoding and tier handling in `bin/reference_docs_ingest.py`
- line-count thresholds in `bin/run_state_lib.py`

#### 5. Enumeration and whitelist completeness

Review every closed set or exact-list contract in scope:

- recognized doc extensions / skipped names
- required Phase 1 headings
- valid role names and role buckets
- canonical BUG heading representation

For each such set, extract the code-side list and compare it to the documented list in `quality/REQUIREMENTS.md` or `SKILL.md`.

### Project-specific scrutiny areas

1. Do all documentation-state surfaces classify cite-only, README-only, binary-only, and plaintext-top-level repos consistently?
2. Can nested `reference_docs/` archival folders silently enter Tier 4 ingest?
3. Does bootstrap mirroring preserve `reference_docs/cite/` content?
4. Can a structurally shallow `EXPLORATION.md` still pass the Phase 1 mechanical validator?
5. Does archive counting understand the canonical `### BUG-NNN: Title` form?
6. Do direct-mode and runner-driven role-map paths converge before gate validation?
7. Does `playbook-output` remain isolated from intrinsic surface accounting?

### Output

For each file reviewed:

#### `path/to/file.py`
- **Line NNN:** `BUG` / `QUESTION` / `INCOMPLETE` Description. Expected vs actual. Why it matters.

## Pass 2: Requirement Verification

Verify each requirement in `quality/REQUIREMENTS.md` against the code. This pass is requirement-by-requirement, not a general review.

### REQ checklist

- `REQ-001` / `REQ-002`: `bin/run_playbook.py`
- `REQ-003`: `bin/reference_docs_ingest.py`
- `REQ-004`: `bin/bootstrap_self_audit_docs.py`
- `REQ-005`: `bin/run_state_lib.py` and the matching gate prose in `SKILL.md`
- `REQ-006`: `bin/archive_lib.py`
- `REQ-007` / `REQ-008`: `bin/role_map.py`

### Output

For each requirement:

#### `REQ-NNN: Title`
**Status**: `SATISFIED` / `VIOLATED` / `PARTIALLY SATISFIED` / `NOT ASSESSABLE`  
**Evidence**: `file:line` — quote or summarize the exact code behavior  
**Analysis**: explain why the code satisfies or violates the REQ  
**Severity**: required when status is `VIOLATED` or `PARTIALLY SATISFIED`
