## Parallel group 1: ISO-8601 timestamp parsers (8 sites)

Enumerated: `inflight_registry._parse_iso_utc:303`, `archive_lib._parse_iso:357`, `archive_lib:212`, `plan_runner:2482` (inline), `metrics_reconstruction:220`, `qpb_validate:1263`, `validate_phase_artifacts:164`, plus `run_state_lib` parsing. These all parse the harness's `%Y-%m-%dT%H:%M:%SZ` shape via `datetime.fromisoformat` with various `Z`→`+00:00` handling.

**Comparison — tz-awareness parity:** `_parse_iso_utc` normalizes naive→aware (`:318-319`); `archive_lib._parse_iso` returns naive for a bare ISO string and aware for a `Z`-suffixed one. A naive−aware subtraction would `TypeError`.

**Determination: NOT A BUG (already fixed).** `archive_lib._duration_seconds` (`:364-379`) explicitly normalizes BOTH operands to UTC-aware before subtracting (comment: "v1.5.6 fix-up 071: ... Mixing naive and aware raises TypeError ... Normalize both"). The parity gap I hypothesized was closed by a prior fix. The remaining inline parsers (`plan_runner:2482`) only ever receive `Z`-suffixed harness timestamps, so they produce aware datetimes and subtract against an aware `now`. Parity holds.
