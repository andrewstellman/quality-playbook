## Open Exploration Findings

Eight concrete findings, ranked. Each cites file:line; ≥3 trace across 2+ functions.

1. **F1 — Still-PENDING (never-launched) runs are graded FAILED on the same collect sweep, defeating the 3600s starvation deadline** `[HIGH]`
`collect_harness_run` (`bin/harness/plan_runner.py:2599`) calls `_retry_pending_runs_once`, then submits `_collect_one_run_detached` for **every** entry in `manifest["runs"]` with no state filter (`:2606-2611`). A starved entry that could not acquire a slot stays `state="PENDING"`, `pid=None`. In `_collect_one_run_detached` there is no PENDING guard (`:2014-2079` go straight to orphan-polling); with `pid is None`, the loop at `:2123` immediately enters the "process gone" branch and, with no `gate-report-latest.json` and no `quality/` dir, sets `terminal = FAILED` (`:2146`) and writes a `grading.json` sentinel (`:2230`). `_classify_stream_terminal` returns `(None, "")` for the missing stream (`runner.py:1043-1044`), so nothing prevents this. Net effect: the 165 `ABANDONED_STARVED` deadline (default 3600s, `:2336`) — meant to give a starved run an hour to acquire a slot across collector passes — never gets a chance; the first collect sweep grades the waiting run FAILED within seconds. **Traces across 3 functions** (`collect_harness_run` → `_collect_one_run_detached` → `_classify_stream_terminal`). The 165 test (`test_collector_retry_165.py`) only exercises `_retry_pending_runs_once` in isolation, never this integrated path.

2. **F2 — Collector's retry-launch path never calls `update_pid`, leaving a phantom `pid=0` slot that ages out at 300s and breaks the per-provider cap** `[HIGH]`
`_retry_pending_runs_once` acquires a slot (`plan_runner.py:2509`, reserving a `pid=0` placeholder) and spawns via `_launch_one_run_detached` (`:2530`), then merges the returned dict into the manifest (`:2538`). It **never calls `_inflight.update_pid`**. The only `update_pid` call site is the *orchestrator's* normal launch path (`:3078`, with the comment "Update the registry with the real PID now that we have it from launch"). So a retry-spawned run's registry entry stays `pid=0`. `_entry_is_active` ages out a `pid=0` entry older than `_PID_ZERO_MAX_AGE_S = 300s` (`inflight_registry.py:341-348`). Real QPB runs take 30–90 min, so the slot is reaped ~5 min into a still-running retry-spawned run → `acquire_run_slot`'s per-provider count (`:458-460`) undercounts → the cap can be exceeded. **Traces across the launch asymmetry** (`_retry_pending_runs_once` vs orchestrator `_wrapped` at `:3064-3082`) and `inflight_registry._entry_is_active`.

3. **F3 — `_PHASE_ARTIFACTS` misattributes Phase-2 Generate artifacts to Phases 4/5, so a run that finished only Phase 2 is reported as Phase 5** `[MEDIUM]`
`status.py:_PHASE_ARTIFACTS` (`:285-316`) maps `COMPLETENESS_REPORT.md`→Phase 4 and `QUALITY.md`→Phase 5. But both are **Phase-2 (Generate) outputs**: the runner's own Phase-4 prerequisite gate lists them among the artifacts that must exist *before Phase 4 starts* ("run Phase 2 first", `run_playbook.py:1522-1523, 1531-1532`); SKILL.md's artifact contract also lists QUALITY.md and the COMPLETENESS_REPORT.md baseline as Phase-2 deliverables. `_infer_phase_from_artifacts` returns the **highest** phase with evidence (`:388 sorted(..., reverse=True)`), so once Phase 2 writes QUALITY.md, the status display reports Phase 5 — overstating progress by three phases, directly contradicting the function's own docstring ("never fabricate skipped progress", `:387`). The status.py comments even cite wrong source lines (`:304` cites "run_playbook.py:3309 — QUALITY.md is the reconciliation output"; line 3309 is the INDEX-payload stub). **Traces across** `_infer_phase_from_artifacts` → `_PHASE_ARTIFACTS` → the runner's authoritative phase-gate contract.

4. **F4 — `council_members()` does not enforce a 3-member roster** `[LOW]`
`council_config.py:107` returns any non-empty list of non-empty strings the operator configured, after only a non-fatal `validate_roster` warning. A 2- or 4-member roster passes through. The Phase-4 Layer-2 semantic-citation majority rule (schemas.md §10 invariant #17) groups verdicts by reviewer and requires "≥2 of 3" — a roster size ≠ 3 silently changes the majority arithmetic (a 2-member roster makes a single `overreaches` a tie; a 4-member roster shifts the threshold). Single-location suspicion.

5. **F5 — Role-map gitignore parser silently skips `!`-negation, dropping force-tracked files from non-git enumeration** `[LOW]`
`role_map.py:563` (`_read_ignore_file_patterns`) skips negation patterns ("Negation patterns require a layered match-state machine; out of scope") — see the `if line.startswith("!")` branch around `role_map.py:71`. QPB's own `.gitignore` excludes `.github/` and force-re-includes the quality_gate files via `!`-rules (see project memory `project_github_gitignored_force_tracked`). For a **non-git target** (provenance `filesystem-walk-with-skips`), `is_in_scope` would exclude `.github/skills/quality_gate/quality_gate.py` because the negation that re-includes it is dropped. Git targets are unaffected (enumeration uses `git ls-files`, which honors negations), so this is latent for the common case but real for non-git adopters.

6. **F6 — `_entry_is_active` treats a `pid=0` entry with missing/malformed `started_at` as permanently active** `[MEDIUM]`
`inflight_registry.py:343-345`: a `pid=0` reservation whose `started_at` fails to parse returns `True` (active) forever — it never ages out. The comment frames this as "never mass-reap on a parse failure", but combined with any code path that reserves a slot without writing a valid `started_at`, it produces a permanent phantom slot that permanently reduces the provider cap. The retry path does write `started_at` (`plan_runner.py:2513`), so it's latent today, but the invariant "every `pid=0` reservation carries a parseable `started_at`" is unenforced and unguarded.

7. **F7 — `archive_run` aborts the whole run on a same-second timestamp collision** `[LOW]`
`archive_lib.py:821-826`: if `quality/previous_runs/<timestamp>/` already exists, `archive_run` raises `ArchiveError`. Timestamps are 1-second resolution (`YYYYMMDDTHHMMSSZ`, `:168`). Two runs (or a re-run) started in the same UTC second collide and the second run aborts at archival rather than disambiguating (e.g., appending a counter). Rare but a hard failure.

8. **F8 — Verdict-explanation `_classify_fail` is coupled to exact FAIL substrings; drift silently misroutes operator advice** `[LOW]`
`quality_gate.py:387-419`: the FAIL→narration classifier matches literal substrings like `"tdd-results.json missing ("` (note the trailing ` (`). If a future edit to `check_tdd_sidecar`'s emit string drops that paren, the message falls through to the generic `missing_artifact` bucket. Presentation-only (never changes `exit_code`), but the "try a stronger model" recommendation is gated on these substrings, so a miss gives the operator wrong advice. The coupling is documented but unguarded by any test that asserts emit-string ⇄ classifier-key agreement.

## Quality Risks

Five ranked, domain-driven failure scenarios for a multi-process AI-orchestration harness. Each names a function/file/line and a concrete failure mechanism.

1. **Premature terminal grading of in-flight/waiting work (HIGH).** Because `_collect_one_run_detached` (`plan_runner.py:2123-2146`) treats `pid is None` as "process gone → FAILED" with no distinction between "never launched / still PENDING" and "launched then died", a harness that writes PENDING manifest entries for starved runs (161-A) will grade those waiting runs FAILED the instant the collector sweeps. This is the F1 mechanism: the dispatcher's terminal-state decision is wrong for the `pid=None ∧ state=PENDING` combination. A reviewer should construct a manifest with one PENDING/pid=None entry and assert `collect_harness_run` leaves it PENDING (or re-queues it), not FAILED.

2. **Concurrency-cap accounting drift under the slow path (HIGH).** Because the retry launch (`plan_runner.py:2530`) omits the `update_pid` the orchestrator path performs (`:3078`), the inflight registry's per-provider count (`inflight_registry.py:458`) will undercount any retry-spawned run after its `pid=0` reservation ages out (300s, `:341-348`). Under sustained starvation (the exact condition the retry loop exists to handle), this lets the provider cap be exceeded — the harness can spawn more concurrent AI-CLIs than the operator authorized, which on metered APIs is a cost/rate-limit incident. Check: after a simulated retry-launch, assert the registry entry carries the real pid, not 0.

3. **Status surface lies about progress, masking a stuck/aborted run (MEDIUM).** Because `_PHASE_ARTIFACTS` (`status.py:285-316`) maps Phase-2 artifacts to later phases, an operator watching the TUI sees "P5 reconciliation" for a run that actually wedged right after Generate. A run that hangs in Phase 3 (code review — the longest phase) but already wrote QUALITY.md in Phase 2 displays as Phase 5, so the operator won't intervene. Check: write only Phase-2 artifacts to a fixture `quality/` and assert `_infer_phase_from_artifacts` returns phase 2, not 4/5.

4. **Lock-scope gap across the manifest/registry/status triangle (MEDIUM).** The inflight registry uses a file lock (`_locked_registry`, `inflight_registry.py:233`), but `manifest.json` (`_update_manifest_entry_atomic`, `plan_runner.py:2374`, write-tmp+rename, no lock) and `status.json` are written under *separate* atomicity domains. The collector reads the manifest while `_update_manifest_entry_atomic` rewrites it; the rename is atomic but a reader can act on a pre-update snapshot. Under the multi-pass retry + parallel collect (`ThreadPoolExecutor`, `:2606`), a run could be observed in inconsistent cross-file states (e.g., manifest says PENDING, registry says active, status absent). Check: the leftover `state="PENDING"` after a successful relaunch (F1/F2 root) is a concrete instance — the relaunch sets a pid but never flips `state` to RUNNING (the returned dict has no `"state"` key, `:1844-1872`).

5. **Resume / idempotency corruption from "trust artifacts over events" when artifacts are partially written (MEDIUM).** `run_state_lib.last_in_progress_phase` + the resume policy (SKILL.md "Resume semantics": trust artifacts more than events) re-runs a phase whose artifacts look incomplete. But `_collect_one_run_detached`'s idempotency check keys solely on `grading.json` presence (`plan_runner.py:2015`); a `grading.json` written then a crash mid-`facts.json` leaves an inconsistent receipt set that the idempotency short-circuit (`:2015-2052`) will trust on the next sweep, returning a stale/half outcome. Check: a `grading.json` present with a corrupt/absent `facts.json` should re-collect, not short-circuit — the `except (json.JSONDecodeError, KeyError)` fallback (`:2050`) only catches grading.json corruption, not facts.json inconsistency.

## Pattern Deep Dive — Dispatcher Return-Value Correctness

Target: `_collect_one_run_detached` (`plan_runner.py:1937-2244`) — dispatches a run to a `TerminalState` and writes receipts.

Input combinations for the orphan-poll dispatch (`:2100-2168`):
- **stream has terminal `result` event** → `terminal = stream_state` (COMPLETED/BLOCKED). Correct.
- **pid alive, no terminal event, within deadline** → keep polling (`:2168 sleep`). Correct.
- **pid alive, deadline exceeded** → kill + re-check stream; `TIMED_OUT` if still no event (`:2148-2167`). Correct.
- **pid dead, no terminal event, gate-report present** → COMPLETED (`:2141`). Correct (113/137 rationale).
- **pid dead, no terminal event, no gate-report** → FAILED (`:2146`). Correct for a launched-then-died run.
- **`pid is None` (never launched / still PENDING)** → falls into the same "process gone" branch (`:2123`) → **FAILED**. **INCORRECT** — a never-launched, within-deadline PENDING run is being treated identically to a crashed run. This is the F1 defect: the dispatcher does not distinguish "no process because it hasn't started yet" from "no process because it died." The fix is a guard at the top of `_collect_one_run_detached` (or in `collect_harness_run`'s submit loop) that skips/requeues `state=="PENDING" ∧ pid is None` entries instead of polling them to FAILED.

Cross-function trace: `collect_harness_run:2606` (submits all entries, no state filter) → `_collect_one_run_detached:2082` (`pid = entry.get("pid")` → None) → `:2123` (`pid is None` → True) → `:2146` (FAILED). `runner._classify_stream_terminal:1043` returns `(None,"")` for the missing stream, removing the only escape. **REQ candidate:** the collector MUST NOT assign a terminal state to a `state="PENDING" ∧ pid is None` entry that is within its starvation deadline.

## Pattern Deep Dive — Cross-Implementation Consistency

Operation: "spawn a detached AI-CLI run and register its real PID in the inflight registry." Implemented twice.

- **Implementation A (orchestrator):** `_execute_one_run` path's `_wrapped` (`plan_runner.py:3064-3082`). Steps: (1) `acquire_run_slot` reserves `pid=0` (called earlier at `:2999`/`:3030` region), (2) `_launch_one_run_detached` spawns, (3) **`update_pid(real_pid)`** (`:3078`), (4) on failure `release_run_slot` (`:3087`).
- **Implementation B (collector retry):** `_retry_pending_runs_once` (`:2506-2545`). Steps: (1) `acquire_run_slot` reserves `pid=0` (`:2509`), (2) `_launch_one_run_detached` spawns (`:2530`), (3) **MISSING** — no `update_pid`, (4) on failure `release_run_slot` (`:2560`).

Step 3 is mandatory: without it the registry holds a `pid=0` reservation for a process that has a real, different pid. `_entry_is_active` (`inflight_registry.py:341-348`) ages out `pid=0` after 300s, so the slot is freed while the run is still alive (runs last 30–90 min). The provider cap (`acquire_run_slot:448,458`) then undercounts and over-admits. This is exactly the bug class the pattern targets: the same logical operation, written twice, with one path omitting a step the other performs. **REQ candidate:** every path that spawns a detached run after `acquire_run_slot` MUST call `update_pid` with the real PID before returning. **Caller compensation does not excuse it** — no caller of `_retry_pending_runs_once` compensates.
