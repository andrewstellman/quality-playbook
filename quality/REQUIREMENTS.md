These requirements are derived from `quality/EXPLORATION.md` and rendered from the Phase 2 baseline manifest. Because the active repo has no populated `reference_docs/cite/` corpus for this run, every REQ in this baseline is treated as Tier 3 and grounds its authority in explored code and playbook behavior rather than formal citations.

## Documentation State and Intake

This functional area covers how the playbook decides whether a run is docs-backed, what it ingests as Tier 4 context, and how operator-visible warnings stay synchronized with those decisions.

### REQ-001: Treat cite-only docs as docs-backed input

**Tier**: 3  
**Source type**: `code-derived`  
**Functional section**: Documentation State and Intake  
**Use cases**: `UC-01`  
**Pattern**: `parity`

**Requirement**  
Any startup path that decides whether a run is docs-backed or code-only must treat plaintext files under `reference_docs/cite/` as valid documentation input, so cite-only repos are not downgraded to code-only mode or warned as such.

**Conditions of satisfaction**
1. A repo with only `reference_docs/cite/spec.md` is classified as docs-backed.
2. No code-only warning is emitted for a cite-only documentation tree.
3. Operator-visible startup messaging agrees with the stored documentation state.

### REQ-002: Use one recognized-docs predicate for warnings and state evaluation

**Tier**: 3  
**Source type**: `code-derived`  
**Functional section**: Documentation State and Intake  
**Use cases**: `UC-01`, `UC-02`  
**Pattern**: `parity`

**Requirement**  
Operator-visible warnings, documentation-state evaluation, and the formal-doc banner must share the same recognized-plaintext rules so README-only, binary-only, cite-only, and top-level plaintext trees produce one consistent classification.

**Conditions of satisfaction**
1. `reference_docs/README.md` alone does not suppress a code-only warning.
2. `reference_docs/spec.pdf` alone does not count as docs present.
3. `reference_docs/design.md` and `reference_docs/cite/spec.txt` count as recognized docs.
4. The three helper surfaces agree across cite-only, README-only, binary-only, and plaintext-top-level cases.

### REQ-003: Limit Tier 4 ingest to the documented reference-docs surface

**Tier**: 3  
**Source type**: `code-derived`  
**Functional section**: Documentation State and Intake  
**Use cases**: `UC-03`  
**Pattern**: `whitelist`

**Requirement**  
Only top-level plaintext files under `reference_docs/` may be treated as Tier 4 context unless the documented contract is explicitly widened; nested archival folders outside `reference_docs/cite/` must not silently join Phase 1 context.

**Conditions of satisfaction**
1. `load_tier4_context()` returns only top-level Tier 4 files.
2. Nested non-`cite/` subdirectories are skipped or rejected deterministically.
3. Tier 4 file ordering is stable across repeated runs.

## Bootstrap and Install Parity

This section captures parity expectations between the repo-root bootstrap corpus and the `reference_docs/` tree that later phases actually read.

### REQ-004: Preserve citable-vs-context placement during bootstrap mirroring

**Tier**: 3  
**Source type**: `code-derived`  
**Functional section**: Bootstrap and Install Parity  
**Use cases**: `UC-04`  
**Pattern**: `parity`

**Requirement**  
The bootstrap self-audit helper must mirror both top-level context docs and `cite/` formal docs into `reference_docs/` while preserving their placement, so self-audit runs keep the same evidence tiers as the source bootstrap corpus.

**Conditions of satisfaction**
1. A source-side `docs_gathered/cite/spec.md` lands in `reference_docs/cite/spec.md`.
2. Top-level contextual docs stay at `reference_docs/<name>.md`.
3. The helper does not leave `reference_docs/cite/` as empty scaffolding when source-side citable docs exist.

## Phase Gates and Role Map Integrity

These requirements define the mechanical boundary between exploration and later phases, plus the accounting rules that keep historical output from distorting the repo's intrinsic surface.

### REQ-005: Enforce the full Phase 1 exploration gate mechanically

**Tier**: 3  
**Source type**: `skill-section`  
**Skill section**: `Phase 2: Generate the Quality Playbook`  
**Functional section**: Phase Gates and Role Map Integrity  
**Use cases**: `UC-05`  
**Pattern**: `whitelist`

**Requirement**  
Phase 1 validation must reject `quality/EXPLORATION.md` files that omit the exact mandatory sections and minimum analytical content named by the playbook's Phase 2 gate, so later phases cannot proceed on structurally shallow exploration artifacts.

**Conditions of satisfaction**
1. A 120-line file with only one findings section is rejected.
2. Validation checks the required exploration headings, not just file existence and line count.
3. Mechanical validation stays aligned with the stronger Phase 2 entry gate.

### REQ-007: Normalize direct Phase 1 role maps before gate validation

**Tier**: 3  
**Source type**: `code-derived`  
**Functional section**: Phase Gates and Role Map Integrity  
**Use cases**: `UC-07`  
**Pattern**: `parity`

**Requirement**  
A freshly written Phase 1 role map must either validate directly or be normalized automatically on every execution path before validation runs, so direct skill-mode and runner-driven paths converge on the same canonical role-map schema.

**Conditions of satisfaction**
1. A raw Phase 1 role map containing `files[]` and `provenance` can be normalized into the canonical shape.
2. After normalization, `validate_role_map()` accepts the result without schema errors.
3. Breakdown and summary are derived from `files[]`, not handwritten.

### REQ-008: Keep historical playbook output out of intrinsic surface accounting

**Tier**: 3  
**Source type**: `code-derived`  
**Functional section**: Phase Gates and Role Map Integrity  
**Use cases**: `UC-08`  
**Pattern**: `whitelist`

**Requirement**  
Phase 1 inventory and downstream reasoning must continue to classify prior `quality/` artifacts as `playbook-output` and bucket them into `other_share`, so historical output never inflates the repository's apparent code or skill surface.

**Conditions of satisfaction**
1. `playbook-output` remains part of the closed role taxonomy.
2. `compute_breakdown()` keeps `playbook-output` out of `code_share`, `skill_share`, and `tool_share`.
3. Repositories dominated by prior `quality/` output still report intrinsic code/skill percentages accurately.

## Archive and Reporting Integrity

This section covers archive rendering and count accuracy after a run has already produced canonical BUG artifacts.

### REQ-006: Parse canonical titled BUG headings in archive summaries

**Tier**: 3  
**Source type**: `code-derived`  
**Functional section**: Archive and Reporting Integrity  
**Use cases**: `UC-06`  
**Pattern**: `whitelist`

**Requirement**  
Archive and index rendering must count bugs from the canonical heading form `### BUG-NNN: Title`, so archived severity and disposition totals remain aligned with the `BUGS.md` format the rest of the playbook requires.

**Conditions of satisfaction**
1. `_extract_bug_counts()` recognizes titled bug headings.
2. Severity totals reflect canonical `BUGS.md` files.
3. Archive output does not silently drop bugs because a title suffix is present.
