## Overview

The Quality Playbook (QPB) is a specification + Python tooling that drives a six-phase, AI-run quality-engineering audit of *other* codebases. Adopters install it into a target repo; an AI agent (Claude Code, Cursor, Copilot, Codex) walks Phases 1–6, and a **Test Harness** (`bin/harness/`) benchmarks runs at scale by spawning per-phase AI-CLI subprocesses, reaping them with a detached collector, capping concurrency per provider, and grading the results against a quality gate. The actors are AI agents (the reasoning loop), benchmark operators (researchers replicating numbers, who care about cost/concurrency/correct grading), and adopters (who install and validate QPB into their repo).

This requirements set was derived **code-first** (Tier 3): `reference_docs/cite/` is empty, so there are zero Tier 1/2 formal-spec citations (a Spec-Gap run). The highest-risk surface — and the focus of these requirements — is the harness's **run-lifecycle accounting**: the `manifest.json ⇄ inflight_registry ⇄ status.json` triangle, three independently-written files with no lock spanning all three, where a state-tracking error silently mis-grades runs or over-admits concurrency. Every requirement names a specific function, file, and line.

Requirements are grouped by functional section. Each section opens with a one-line description, then lists its REQs. Traceability is one-way REQ → UC; the use cases are listed first for context.

## Use Cases

- **UC-01** — Adopter installs QPB into a target repo and validates the install (actors: adopter, AI agent).
- **UC-02** — Operator runs a Mode-B benchmark plan and the detached collector reaps and grades every run (benchmark operator, AI agent).
- **UC-03** — Operator caps concurrency per provider and the harness honors it under starvation (benchmark operator).
- **UC-04** — Operator watches live status to decide whether to intervene in a run (benchmark operator).
- **UC-05** — Adopter overrides the Council roster (adopter).
- **UC-06** — A new run archives the prior run's `quality/` as reference and starts clean (benchmark operator, AI agent).

## Detached collector lifecycle

The detached collector (`collect_harness_run` → `_collect_one_run_detached`) reaps orphaned AI-CLI runs, infers a terminal state, and writes grading receipts. This section governs how it classifies and records run outcomes.

### REQ-001: Collector must not terminally grade un-launched starved runs
[Tier 3 · specific] `collect_harness_run` must not assign a terminal state to a manifest entry with `state="PENDING"` and `pid is None` that is within its `_pending_deadline_s()` window. **Source:** `bin/harness/plan_runner.py:2606` (submit loop, no state filter) and `bin/harness/plan_runner.py:2082-2146` (`_collect_one_run_detached`, where `pid is None` routes to `FAILED`). **Conditions of satisfaction:** a manifest with one PENDING/pid=None within-deadline entry, run through `collect_harness_run`, leaves that entry PENDING (or re-queues it) — it is NOT graded `FAILED`. **Use cases:** UC-02.

### REQ-003: A relaunched PENDING entry must transition out of PENDING
[Tier 3 · specific] After a successful retry relaunch, the manifest entry's `state` must reflect RUNNING (not remain `PENDING`). **Source:** `bin/harness/plan_runner.py:2538` (merge) + the returned dict at `bin/harness/plan_runner.py:1844-1872` (`_launch_one_run_detached`, no `state` key). **Conditions:** after `_retry_pending_runs_once` relaunches an entry, its manifest `state` ≠ `"PENDING"`. **Use cases:** UC-02.

### REQ-007: Collector idempotency must require a consistent receipt set
[Tier 3 · specific] The `grading.json`-present short-circuit must also verify `facts.json` consistency for COMPLETED runs before returning a cached outcome. **Source:** `bin/harness/plan_runner.py:2015-2052`. **Conditions:** a `grading.json` present alongside a missing/corrupt `facts.json` for a COMPLETED run triggers re-collection, not a cached short-circuit. **Use cases:** UC-02.

### REQ-008: Supervisor terminal-status writes must win over collector inference
[Tier 3 · specific] When `status.json` already carries a `terminal_state`, the collector must not overwrite it. **Source:** `bin/harness/plan_runner.py:2306-2312` (`_write_terminal_status`, currently compliant — must stay so). **Conditions:** `_write_terminal_status` returns early (no write) when the on-disk `status.json` has a truthy `terminal_state`. **Use cases:** UC-02.

## Per-provider concurrency registry

The inflight registry (`inflight_registry.py`) enforces per-provider concurrency caps across processes via a locked JSON file. A run reserves a `pid=0` slot, then `update_pid` records the real PID, then `release_run_slot` frees it on terminal.

### REQ-002: Every detached-spawn path must record the real PID
[Tier 3 · specific] Any code that calls `acquire_run_slot` then spawns a run must call `update_pid` with the launched PID before returning. **Source:** `bin/harness/plan_runner.py:3078` (`_wrapped`, compliant) vs `bin/harness/plan_runner.py:2530` (`_retry_pending_runs_once`, non-compliant — omits `update_pid`). **Conditions:** after a retry relaunch, the registry entry for that run carries the real PID, not `0`. **Use cases:** UC-02, UC-03.

### REQ-005: `pid=0` reservations must not become permanent phantom slots
[Tier 3 · specific] A `pid=0` registry entry must always carry a parseable `started_at` so the 300s age-out applies; or `_entry_is_active` must age out malformed-timestamp reservations. **Source:** `bin/harness/inflight_registry.py:343-348` (`_entry_is_active` returns `True` forever when `started_at` is unparseable). **Conditions:** a `pid=0` entry with malformed `started_at` does not remain active indefinitely. **Use cases:** UC-03.

### REQ-006: Per-provider concurrency cap must be honored across all spawn paths
[Tier 3 · specific] The count of active runs per provider must never exceed `max_per_provider[provider]` (or `plan_pool_cap`). **Source:** `bin/harness/inflight_registry.py:448-470` (`acquire_run_slot`). **Conditions:** with N concurrent acquirers and cap C, at most C entries per provider are active at once — across BOTH the orchestrator launch path and the collector retry path. **Use cases:** UC-03.

## Run status reporting

The live status surface (`status.py`) resolves a run's current phase from sentinels, the Mode-B stream, or (last resort) on-disk artifacts.

### REQ-004: Phase inference must report the highest phase actually completed, never higher
[Tier 3 · specific] `_infer_phase_from_artifacts` must key each phase on an artifact the runner treats as that phase's *exclusive* boundary marker. **Source:** `bin/harness/status.py:285-316` (`_PHASE_ARTIFACTS` maps Phase-2 outputs QUALITY.md/COMPLETENESS_REPORT.md to Phases 5/4) vs `bin/run_playbook.py:1522-1523` (Phase-4 prerequisite gate listing both as Phase-2 outputs). **Conditions:** a fixture `quality/` containing only Phase-2 artifacts resolves to phase 2, not 4 or 5. **Use cases:** UC-04.

## Install validation

`qpb_validate.py` is the Mode-A Phase-0 gate that confirms a canonical install before any phase runs.

### REQ-009: Install validator must require an explicit AI tool on ambiguity and a fresh marker for a populated quality/
[Tier 3 · specific] The validator must block when multiple AI-tool markers exist without `--ai-tool`, and must treat a populated `quality/` with no recent `run_start` as stale. **Source:** `bin/qpb_validate.py:1272` (`check_stale_quality_dir`) + marker resolution. **Conditions:** ambiguous markers → `status=blocked`; populated `quality/` + `run_state.jsonl` with a `run_start` within 24h → `status=ok`. **Use cases:** UC-01.

## Council roster

`council_config.council_members()` resolves the Phase-4 Council-of-Three roster with an adopter override.

### REQ-010: Council roster resolution must degrade safely and target three members
[Tier 4 · architectural-guidance] `council_members()` must fall back to `DEFAULT_COUNCIL_MEMBERS` on any malformed config; per the Council-of-Three design, the effective roster should comprise three members so the Layer-2 2-of-3 majority is well-defined. **Source:** `bin/council_config.py:47-110`; `reference_docs/22_council_of_three.md`. **Conditions:** a non-list/empty/blank-entry override falls back to defaults with a WARN. **Use cases:** UC-05.

## Run archival

`archive_lib.archive_run` snapshots a prior `quality/` into `previous_runs/<ts>/` so a new run starts clean without losing history.

### REQ-011: Archival must not silently overwrite or hard-abort on a recoverable collision
[Tier 3 · specific] `archive_run` must refuse to overwrite an existing archive (compliant) but should disambiguate a same-second timestamp collision rather than aborting the run. **Source:** `bin/archive_lib.py:821-826`. **Conditions:** two archives requested in the same UTC second both succeed (disambiguated), and neither overwrites the other. **Use cases:** UC-06.

## Source-edit guard

`run_state_lib.validate_no_source_edits` is the run-end post-condition that catches any mutation outside `quality/`.

### REQ-012: Source-edit guard must flag any non-`quality/` mutation at run end
[Tier 3 · specific] `validate_no_source_edits` must report any tracked or untracked path outside the allowed prefixes as a violation at run end. **Source:** `bin/run_state_lib.py:976`. **Conditions:** a dirty file outside `quality/` → `(False, [path])`; all changes under `quality/` → `(True, [])`; `-z` rename destination-first parsing verified correct. **Use cases:** UC-02.
