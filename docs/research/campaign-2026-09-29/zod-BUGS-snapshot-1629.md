### BUG-001: Compiled object accepts a missing key when its optional is wrapped by an intersection or z.success

- Severity: MEDIUM
- Source: Code Review (Pass 1 area 5 + Pass 2)
- Primary requirement: REQ-013
- Location: `packages/zod/src/v4/core/compile.ts:1453-1457`
- Covers: [REQ-013/cell-INTERSECTION-COMPILED, REQ-013/cell-SUCCESS-COMPILED]
- Consolidation rationale: Both cells fail through the same `case "optional"` arm of `fastPathAcceptsAbsence`; one line fixes both.
- Spec basis: compile.md:9 — "Results and errors are identical." A compiled schema must accept and reject exactly what the runtime parser accepts and rejects.
- Divergence type: code-spec · Disposition: code-fix · Fix type: code

**Code behaviour.** `fastPathAcceptsAbsence` (compile.ts:1453-1457) answers `fastPathAcceptsAbsence(innerType)` for `optional`, but `generateOptionalCheck` (compile.ts:1379-1390) accepts `undefined` whatever the inner is. For `z.object({a: z.intersection(z.string().optional(), z.string().optional())})` the intersection answers false, `requiresPresenceCheck` (compile.ts:1398-1400) emits no `in` guard at compile.ts:1250-1252, and the generated code accepts `{}`. The runtime rejects it: the intersection declares no `optin`, so `handlePropertyResult` (schemas.ts:1994-2003) pushes `invalid_type` (`nonoptional`).

**Reproduction.**

```ts
z.compile(z.object({ a: z.intersection(z.string().optional(), z.string().optional()) })).safeParse({}).success  // true; uncompiled: false
z.validate(z.compile(z.object({ a: z.success(z.string().optional()) })), {})           // true; uncompiled: false
```

- Expected: success === false with `invalid_type` at ["a"], as the runtime reports
- Actual: compiled parse succeeds with `{}` / `{a: true}`; `z.validate` returns true without falling back
- Reachability: No guard: `requiresPresenceCheck` is the only presence gate for keys whose `optin` is undefined, and `validate()` (parse.ts:137-149) trusts a definite compiled answer without the runtime fallback. Reached unconditionally under `z.compile()` or `import "zod/compile"` for these compositions.
- Regression test: `test_regression.test.ts › BUG-001` · patch `quality/patches/BUG-001-regression-test.patch`
- Fix patch: `quality/patches/BUG-001-fix.patch`
- Writeup: `quality/writeups/BUG-001.md`

### BUG-002: Intersecting two z.map() or two z.set() schemas throws "Unmergable intersection" on every valid input

- Severity: MEDIUM
- Source: Code Review (Pass 1 area 5)
- Primary requirement: REQ-010
- Location: `packages/zod/src/v4/core/schemas.ts:2826-2884`
- Spec basis: api.md:2038 — "Intersection types (`A & B`) represent a logical \"AND\"." basics.md:114 — safeParse returns a result object.
- Divergence type: code-spec · Disposition: code-fix · Fix type: code

**Code behaviour.** `$ZodIntersection` (schemas.ts:2809-2821) parses the input with both operands; `$ZodMap`/`$ZodSet` each allocate a new container (schemas.ts:3458, 3569). `mergeValues` (schemas.ts:2826-2884; mechanical list in quality/mechanical/mergeValues_branches.txt) reconciles only `===`, `Date`, plain objects and arrays, so two equal Maps are `{valid:false}` and `handleIntersectionResults` throws `Error("Unmergable intersection")` at schemas.ts:2976-2979 — from `safeParse`.

**Reproduction.**


- Expected: `{ success: true, data: Map { a => 1 } }`
- Actual: `Error: Unmergable intersection. Error path: []` thrown out of safeParse, even for `new Map()`
- Reachability: No guard: every Map/Set intersection reaches `mergeValues` with two distinct containers; the throw at schemas.ts:2979 is skipped only when a sub-result was already aborted, i.e. only for invalid input.

### BUG-004: Exhaustive z.record() accepts a missing enum key when the value schema accepts undefined

- Severity: MEDIUM
- Source: Code Review (Pass 2 + Pass 3)
- Primary requirement: REQ-006
- Location: `packages/zod/src/v4/core/schemas.ts:3257-3300`
- Covers: [REQ-006/cell-ANY-RECORD, REQ-006/cell-UNKNOWN-RECORD, REQ-006/cell-UNDEFINED-RECORD, REQ-006/cell-VOID-RECORD, REQ-006/cell-UNIONUNDEFINED-RECORD, REQ-022/cell-ANY-JSONSCHEMA, REQ-022/cell-UNKNOWN-JSONSCHEMA, REQ-022/cell-UNDEFINED-JSONSCHEMA, REQ-022/cell-VOID-JSONSCHEMA, REQ-022/cell-UNIONUNDEFINED-JSONSCHEMA]
- Consolidation rationale: Every cell is the same missing `key in input` test in the exhaustive record loop; the JSON Schema cells disagree only because the runtime under-enforces what `required` already states, so the one runtime fix closes all ten.
- Spec basis: api.md:2134 — "Zod will exhaustively check that all enum values exist in the input as keys." api.md:2121 — only `.default()`, `.prefault()`, `.optional()` make a key optional, "the same as it does inside `z.object()`".
- Divergence type: code-spec · Disposition: code-fix · Fix type: code

**Code behaviour.** The exhaustive branch (schemas.ts:3257-3300) runs `def.valueType` on `input[key]` for every declared key and never tests `key in input` or `valueType._zod.optin`. **Reproduction.**

```ts

z.record(z.enum(["a", "b"]), z.unknown()).safeParse({ a: 1 })     // success: true
```

- Expected: `invalid_type` (`nonoptional`) issue at ["a"] / ["b"], matching z.object and the JSON Schema `required` list
- Actual: parse succeeds and invents `undefined`-valued keys
- Reachability: No guard: the loop has no presence check at all; any exhaustive record whose value schema accepts `undefined` (`z.any`, `z.unknown`, `z.undefined`, `z.void`, unions with `z.undefined()`) is reached unconditionally.

- Reachability: No guard: every schema part goes through `partPattern` → `source`.
