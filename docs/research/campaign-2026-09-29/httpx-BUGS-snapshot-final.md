### BUG-001: URL passwords are written to INFO logs, HTTPStatusError messages and Request repr

- Source: Code Review (Phase 3)
- Severity: HIGH
- Requirement: REQ-033
- File:line: httpx/_client.py:1025-1032, httpx/_models.py:808-829, httpx/_models.py:496-499
- Divergence type: code-spec
- Covers: [REQ-033/cell-password-log_line, REQ-033/cell-password-status_error, REQ-033/cell-password-request_repr]
- Consolidation rationale: All three surfaces render the URL via `str(url)`; one `URL._redacted()` helper used by all three closes every cell.
- Spec basis: Tier 3 — the masking contract implemented by `URL.__repr__` (`httpx/_urls.py:377-401`), `Headers.__repr__` (`httpx/_models.py:130-136`) and `Proxy.__repr__` (`httpx/_config.py:235-243`); log line format per `reference_docs/cite/docs_logging.md`.
- Documented intent: Diagnostic renderings of a request URL mask the userinfo password, as `URL.__repr__` does (`httpx/_urls.py:377-401`).
- Code behavior: `_send_single_request` logs `request.url` with `%s` (`URL.__str__`, `httpx/_urls.py:374-375`, includes `user:password@`); `raise_for_status` formats `{0.url}`; `Request.__repr__` renders `str(self.url)`.
- Minimal reproduction: `client.get('http://user:s3cret@example.com/p')` with httpx INFO logging, response 404, then `raise_for_status()`.
- Expected: `HTTP Request: GET http://user:[secure]@example.com/p ...`; exception text and `repr(request)` without `s3cret`.
- Actual: Log: `HTTP Request: GET http://user:s3cret@example.com/p "HTTP/1.1 404 Not Found"`; exception: `... for url 'http://user:s3cret@example.com/p'`; repr `<Request('GET', 'http://user:s3cret@example.com/p')>`.
- Reachability: no guard; `_send_single_request` logs every request unconditionally at INFO (`httpx/_client.py:1025`, async twin), and `raise_for_status` formats the URL for every non-2xx response.
- Regression test: `quality/test_regression.py::test_bug_001_url_password_masked_in_diagnostics` · patch `quality/patches/BUG-001-regression-test.patch`
- Fix patch: `quality/patches/BUG-001-fix.patch` (applies to clean HEAD with `git apply`; red→green validated in a disposable worktree)

### BUG-002: Multi-member gzip response bodies are silently truncated to the first member

- Source: Code Review (Phase 3)
- Severity: MEDIUM
- Requirement: REQ-014
- File:line: httpx/_decoders.py:92-99
- Divergence type: code-spec
- Covers: [REQ-014/cell-MultiMember-gzip]
- Spec basis: `reference_docs/cite/rfc9110-http-semantics.txt` §8.4.1.3 (gzip = RFC 1952 format); tier 3 REQ-014.
- Documented intent: The gzip content coding (RFC 9110 §8.4.1.3, RFC 1952) permits concatenated members; the decoded body is the concatenation of all members.
- Code behavior: `GZipDecoder` uses one `zlib.decompressobj(MAX_WBITS|16)` and never inspects `eof`/`unused_data`; bytes after the first member are discarded. `ZStandardDecoder` (`httpx/_decoders.py:186-189`) does loop over frames.

- Expected: `b'hello world'`
- Actual: `b'hello '` — no exception.
- Reachability: no guard; every gzip-encoded response body passes through `GZipDecoder.decode` (`httpx/_models.py:699-722`, `898`).
- Regression test: `quality/test_regression.py::test_bug_002_multi_member_gzip_fully_decoded` · patch `quality/patches/BUG-002-regression-test.patch`

### BUG-003: Content-Encoding chains that include zstd always fail with DecodingError

- Source: Code Review (Phase 3)
- Severity: LOW
- Requirement: REQ-015
- File:line: httpx/_decoders.py:180-192, httpx/_decoders.py:221-225
- Divergence type: code-spec
- Spec basis: `reference_docs/cite/rfc9110-http-semantics.txt` §8.4 (codings listed in order applied).
- Documented intent: Codings listed in Content-Encoding are decoded in reverse order of application (RFC 9110 §8.4); a body encoded `gzip, zstd` decodes.
- Code behavior: `MultiDecoder.flush` calls `child.decode(b'')` on each child; `ZStandardDecoder.decode` calls `decompress(b'')` on a finished decompressobj (ZstdError 'cannot use a decompressobj multiple times') and marks `seen_data` even for empty input.

- Actual: `httpx.DecodingError: cannot use a decompressobj multiple times`; empty body raises 'Zstandard data is incomplete'.
- Reachability: no guard; `_get_content_decoder` builds a `MultiDecoder` for any multi-token header (`httpx/_models.py:715-718`) and `iter_bytes` always calls `flush()` (`httpx/_models.py:901`); zstd is advertised in `Accept-Encoding` (`httpx/_client.py:120-122`).
- Regression test: `quality/test_regression.py::test_bug_003_multi_coding_with_zstd_decodes` · patch `quality/patches/BUG-003-regression-test.patch`
