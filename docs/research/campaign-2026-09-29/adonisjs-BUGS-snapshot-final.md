### BUG-001: uuid() route matcher accepts non-hexadecimal letters

- Source: Code review (quality/code_reviews/2026-09-29-code-review.md)
- Primary requirement: REQ-001
- File:line: `src/router/matchers.ts:31`
- Severity: MEDIUM
- Divergence type: code-spec
- Spec basis: `reference_docs/cite/v6-docs_basics_routing.md` line 161 — "// Validate id to be a valid UUID" (Inbuilt matchers)
- Documented intent: `router.matchers.uuid()` validates that the param is a valid UUID.
- Code behavior: The regex character class is `[0-9a-zA-F]` (src/router/matchers.ts:31), i.e. digits, every lowercase letter a–z, and uppercase A–F.
- Reproduction: `new RouteMatchers().uuid().match.test("zzzzzzzz-zzzz-zzzz-zzzz-zzzzzzzzzzzz")` → `true`; a route guarded by the matcher dispatches `/posts/gggggggg-gggg-gggg-gggg-gggggggggggg` to its handler.
- Expected: Non-hex values fail the matcher and the route does not match (404 / next route).
- Actual: 20 non-hex lowercase letters (g–z) are accepted; uppercase G–Z are rejected (case-asymmetric).
- Consequence: Handlers behind a "uuid" guard receive garbage ids; a database uuid column then raises a driver error (500) instead of the router returning 404.
- Reachability: no guard; `parseRoute` applies the matcher regex directly to every param value (src/helpers.ts:161-163), so the defective class is reached unconditionally for every uuid-guarded route.
- Disposition: code-fix (fix type: code) — The guide states the matcher validates a UUID and the tests only probe real UUIDs; the class `a-zA-F` is an evident typo for `a-fA-F`, so the code — not the documentation — is wrong. Not upstream-spec-issue: RFC 4122 text form is unambiguous hex.
- Regression test: `quality/test_regression.ts` › "BUG-001: …"; patch `quality/patches/BUG-001-regression-test.patch`
- Fix patch: `quality/patches/BUG-001-fix.patch` — Change the class to `[0-9a-fA-F]` in all five groups.
- Closure: TDD verified (FAIL→PASS)
- Writeup: `quality/writeups/BUG-001.md`

### BUG-002: Domain-less routes are unreachable on hosts that match a domain group

- Source: Code review (quality/code_reviews/2026-09-29-code-review.md)
- Primary requirement: REQ-002
- File:line: `src/router/main.ts:716-722`
- Severity: HIGH
- Divergence type: code-spec
- Spec basis: `reference_docs/cite/v6-docs_basics_routing.md` line 438 — "Routes that are resolved for any domain/hostname."
- Documented intent: Routes registered without a domain are resolved for any hostname; domain routes additionally match their own host.
- Code behavior: `Router.match` returns `this.#store.match(uri, method, …, {tokens: matchingDomain, …})` whenever `matchDomain(hostname)` recognises the host (src/router/main.ts:716-722); `RoutesStore.match` then looks only in that domain's table and returns `null` (src/router/store.ts:236-251, 253-265). There is no fallback to the `root` table.
- Reproduction: Register `router.get("/users")` and `router.group(() => router.get("/articles")).domain("blog.adonisjs.com")`; `GET /users` with `Host: blog.adonisjs.com` → 404; with any other host → 200.
- Expected: `GET /users` returns 200 on `blog.adonisjs.com`.
- Actual: 404 `Cannot GET:/users` on every host that matches a registered domain pattern.
- Consequence: Multi-tenant apps (`:tenant.app.com`) lose every shared route (login, health checks, webhooks) on every tenant host as soon as one domain route exists.
- Reachability: no guard; `routeFinder` passes the hostname whenever `router.usingDomains` is true (src/server/factories/route_finder.ts:46) and `Router.match` never retries without the domain — reached for every request on a domain-matched host. Both the linear and the tree matcher share this code path.
- Disposition: code-fix (fix type: code) — The guide is explicit that domain-less routes resolve for any hostname; nothing in the code or tests suggests an intentional "domain hosts are isolated" policy (the only related test checks a 404 on a *non*-domain host). Code-fix rather than spec-fix because the documented behaviour is the one multi-tenant apps need.
- Regression test: `quality/test_regression.ts` › "BUG-002: …"; patch `quality/patches/BUG-002-regression-test.patch`
- Fix patch: `quality/patches/BUG-002-fix.patch` — After a domain lookup that returns null, fall back to `this.#store.match(uri, method, shouldDecodeParam)`.
- Closure: TDD verified (FAIL→PASS)
- Covers: [REQ-002/cell-ROOTFALLBACK-LINEAR, REQ-002/cell-ROOTFALLBACK-TREE]
- Consolidation rationale: Both matcher strategies are selected inside `RoutesStore.match`, which is called from the single `Router.match` method; one fallback in `Router.match` closes both cells.
- Writeup: `quality/writeups/BUG-002.md`

### BUG-003: Signed URLs whose params need percent-encoding never verify

- Source: Code review (quality/code_reviews/2026-09-29-code-review.md)
- Primary requirement: REQ-014
- File:line: `src/request.ts:1111-1112`
- Severity: MEDIUM
- Divergence type: code-spec
- Spec basis: `reference_docs/cite/v6-docs_basics_routing.md` line 742 — "The signature is used to verify if the URL has been tampered after it was generated."
- Documented intent: A URL signed by the package verifies until it is tampered with.
- Code behavior: `createURL` percent-encodes params (src/client/helpers.ts:153) and `createSignedURL` signs that encoded string (src/helpers.ts:193-200); `hasValidSignature` compares the signed message with `this.url()` (src/request.ts:1111-1112), which is the pathname decoded by `safeDecodeURI` (src/utils.ts:254-276).
- Reproduction: `signedUrlFor("files", { name: "hello world" })` → `/files/hello%20world?signature=…`; requesting it gives `hasValidSignature() === false` (same route with `name: "plain"` → true).
- Expected: `hasValidSignature()` is true for the untampered URL.
- Actual: false for any param containing a space, non-ASCII letter or other character outside the reserved set kept encoded by `decodeComponentChar`.
- Consequence: Password-reset, email-verification and unsubscribe links for affected ids fail permanently with no log trail.
- Reachability: no guard; every request passes through `safeDecodeURI` at construction (src/request.ts:131) and `hasValidSignature` always compares the decoded pathname.
- Disposition: code-fix (fix type: code) — The producer and verifier are both in this package and disagree about encoding; the guide promises tamper detection, not rejection of untampered links. Not a mis-read: the probe shows ASCII params verify, encoded ones do not.

- Fix patch: `quality/patches/BUG-003-fix.patch` — Also compare against the raw (still encoded) pathname from `request.url`.
- Closure: TDD verified (FAIL→PASS)
- Covers: [REQ-014/cell-ENCODEDPARAM-SIGNEDURLFOR, REQ-014/cell-ENCODEDPARAM-MAKESIGNEDURL]
- Consolidation rationale: `signedUrlFor` and the legacy `makeSignedUrl` both produce URLs through `createSignedURL`/`createURL`; the defect is in the single verifier `hasValidSignature`, so one verifier change closes both producer sites.
