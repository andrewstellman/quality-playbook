### BUG-001: Atomic file writes replace the destination even when the write fails

- Severity: HIGH
- Source: Code Review
- Location: `src/click/_compat.py:466-471`
- Primary requirement: REQ-031
- Spec basis: reference_docs/cite/docs_handling-files.md line 99 (atomic mode: writes go to a separate file and are moved over the original upon completion)
- Documented intent: atomic=True writes to a temporary file and moves it over the destination only on completion
- Code behavior: _AtomicFile.close ignores its delete argument and always os.replace()s the temp file (_compat.py:466-471); the File parameter path closes through ctx.call_on_close / _LazyFile.close_intelligently (types.py:1001-1017, utils.py:186-192), so a failing command also commits
- Reproduction: Write 'PARTIAL' to open_file(p, 'w', atomic=True) inside a with-block that raises; or a command with click.File('w', atomic=True) that writes then raises.
- Expected: Destination still contains its original content; temp file removed.
- Actual: Destination contains the partial content 'PARTIAL'.
- Reachability: no guard; _AtomicFile.close reaches os.replace unconditionally on every close (with-block exit with exception, context teardown after a failed command).
- Divergence type: code-spec
- Disposition: code-fix (fix type: code) — code-fix rather than spec-fix: the documented/required behaviour is the one integrators rely on and the code path is a local defect with a small, test-covered fix; nothing in the docs or the project's tests endorses the current behaviour.
- Proposed fix: Honour close(delete=True) by unlinking the temp file; register atomic files (and lazy atomic files) with ctx.with_resource so the context teardown passes exception info; _LazyFile.__exit__ forwards exceptions to the wrapped file.
- Regression test: `quality/test_regression.py::test_bug_001_atomic_write_preserves_destination_on_exception`
- Patches: `quality/patches/BUG-001-regression-test.patch`, `quality/patches/BUG-001-fix.patch`
- Writeup: `quality/writeups/BUG-001.md`
- Challenge gate: CONFIRMED (quality/challenge/BUG-001-challenge.md)

## Reviewed and dismissed

- Withdrawn finding (numbered BUG #028 during Phase 4, removed at the Phase 5 challenge gate): The program name is interpolated unquoted into generated shell-completion scripts — `src/click/shell_completion.py:338-345`. Both challenge rounds concluded the program name is set by the tool's own author (completion is documented for installed entry points), so there is no trust boundary and no documented quoting contract; see the challenge record for that number under quality/challenge/. Its regression test and patches were removed; the grid cells it covered are recorded as downgrades in quality/compensation_grid_downgrades.json.

- Withdrawn finding (numbered BUG #030 during the gap iteration, removed at that iteration's challenge gate): UUID raises AttributeError instead of a usage error for a non-string value — `src/click/types.py:891-904`. The maintainer's-advocate round showed the expected behaviour is outside the ParamType.convert contract (strings and already-typed values only; UUID.convert is annotated uuid.UUID | str) and no realistic configuration delivers an integer UUID; see the challenge record for that number under quality/challenge/. Its regression test and patches were removed; the grid cells it covered are recorded as downgrades in quality/compensation_grid_downgrades.json.

- Withdrawn finding (numbered BUG #047 during the unfiltered iteration's spec audit, removed at that iteration's challenge gate): A non-string flag_value never matches its environment value exactly — `src/click/core.py:3708-3709`. The project's own test matrix (tests/test_options.py::test_envvar_string_flag_value, case (42, '42', None)) deliberately pins that a non-string flag_value is not matched against the raw environment string, and any truthy value still activates the flag; see the challenge record for that number under quality/challenge/. Its regression test and patches were removed; it covered no grid cells.

- Withdrawn finding (numbered BUG #064 during the adversarial iteration (re-promoted DC-002), removed at that iteration's challenge gate): INT silently truncates a non-integral float from a configuration file — `src/click/types.py:598-612`. Both rounds found truncation of Python-side float values deliberate: tests/test_arguments.py::test_good_defaults_for_nargs pins the default (1.1, 2.2) becoming (1, 2) for INT, and the docs' 'only accepts integers' concerns command-line input, which is still rejected; see the challenge record for that number under quality/challenge/. Its regression test and patches were removed; it covered no grid cells.

- Withdrawn finding (numbered BUG #065 during the adversarial iteration (re-promoted DC-006), removed at that iteration's challenge gate): Number types raise TypeError for a list or table from a configuration file — `src/click/types.py:598-612`. The maintainer's-advocate round showed a list for an INT option is outside the convert contract (the same data mismatch as default=[1] in code), consistent with the earlier withdrawal of BUG #030; see the challenge record for that number under quality/challenge/. Its regression test and patches were removed; it covered no grid cells.

- Withdrawn finding (numbered BUG #071 during the adversarial iteration, removed at that iteration's challenge gate): An EDITOR value with unbalanced quotes raises a raw ValueError instead of a Click error — `src/click/_termui_impl.py:725-741`. tests/test_termui.py::test_editor_unclosed_quote deliberately asserts that an unclosed quote in the editor command raises ValueError; see the challenge record for that number under quality/challenge/. Its regression test and patches were removed; it covered no grid cells.
