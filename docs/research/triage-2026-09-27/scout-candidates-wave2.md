## Candidate detail

### 1, 2, 4, 6, 7, 8. assertj/assertj (assertj-core) — six bugs, all confirmed present

- **Upstream:** https://github.com/assertj/assertj (module `assertj-core`)
- **Historical path:** `/sessions/.../QPB/repos/secbench2/sb2-15-assertj/quality/BUGS.md` — 6 confirmed bugs, "all TDD-verified (FAIL→PASS) against Maven 3.9.12 / OpenJDK 21 in a disposable git worktree," with a shared regression-test patch and per-bug fix patches (historical claim; not re-executed in this pass).
- **Fresh currency check:** `git clone --depth 1 https://github.com/assertj/assertj` → HEAD `7ca27151d9bc4ba86b7e789a327e2e6e96ae5ada`, committed **2026-09-27 (today)** — as current as it gets, very active repo.
- **Per-bug file:line, confirmed byte-for-byte against fresh HEAD:**
  - **BUG-001** — `assertj-core/src/main/java/org/assertj/core/util/DoubleComparator.java:35-36`: `compareNonNull` returns `x < y ? -1 : 1` when not `closeEnough`; for NaN, `closeEnough` is false and `x < y` is false, so `compare(NaN,1.0)`, `compare(1.0,NaN)`, and `compare(NaN,NaN)` all return `+1`, violating the `Comparator` antisymmetry/reflexivity contract (`sgn(compare(a,b)) == -sgn(compare(b,a))`, `compare(a,a)==0`). Sorting a `List<Double>` containing `NaN` with this comparator throws `IllegalArgumentException: Comparison method violates its general contract!` from `TimSort`. Fix: use `Double.compare(x, y)` for the non-close branch.
  - **BUG-002** — `FloatComparator.java:42-43`, identical shape. Fix: `Float.compare(x, y)`.
  - **BUG-003** — `ComparatorBasedComparisonStrategy.java`: `iterableContains` (lines 90-98) guards `element == value` and null before calling `comparator.compare`; `iterableRemoves` (112-124) and `iterablesRemoveFirst` (129-137) call `comparator.compare` directly with no null guard. `new ComparatorBasedComparisonStrategy(Comparator.<Integer>naturalOrder())` on `[1, null, 2]`: `iterableContains(list, 1)` returns normally, but `iterableRemoves(list, 1)` throws `NullPointerException` from inside the natural-order comparator. Fix (per historical patch): extract the contains-guard logic into a shared `elementMatchesValue` helper used by all three methods.
  - **BUG-004** — `StandardRepresentation.java:690-691`: `toStringOf(Float f)` returns `"%sf".formatted(f)` unconditionally, so `Float.NaN` renders as `"NaNf"` and `Float.POSITIVE_INFINITY` as `"Infinityf"`, while the parallel `Double` path renders `Double.NaN` as `"NaN"` (no suffix). Fix: append `f` only for finite values.
  - **BUG-005** — `Percentage.java:62-63`: `toString()` does `noFractionalPart() ? "%s%%".formatted((int) value) : ...`; `(int) 3_000_000_000d` saturates to `Integer.MAX_VALUE`, so `withPercentage(3_000_000_000d).toString()` returns `"2147483647%"` instead of `"3000000000%"`. Fix: cast to `long` instead of `int`.
  - **BUG-006** — `NumberGrouping.java:27`: `Pattern.compile("([0-9|A-Z]{4})")` — inside a character class `|` is a literal character, not alternation, so the class unintentionally also matches the pipe character. Intended: `[0-9A-Z]`. Currently latent (no in-repo caller emits `|` into a value being grouped).
- **Duplicate check:** GitHub REST search (`api.github.com/search/issues?q=repo:assertj/assertj+DoubleComparator+NaN`) surfaced exactly one hit: **issue #1390** ("isEqualToComparingFieldByField does not deal with Infinity", opened 2019-01-08, closed 2019-01-09 without an apparent code fix landing — the issue itself proposes almost the exact `closeEnough` fix needed for BUG-001/002 and it is still unaddressed in today's HEAD). This is not a literal duplicate of BUG-001/002 (different entry point — field-by-field comparison vs. direct comparator use — and it doesn't mention `compare(NaN,NaN)` reflexivity or `FloatComparator`), but it is strong corroborating evidence that the underlying defect is real, long-standing (7 years), and previously reported without being fixed. Searches for BUG-003 ("remove NPE"), BUG-004/005/006 were not run — time did not allow; treat those as **not checked for duplicates**.
- **Quick-merge signals:** `CONTRIBUTING.md` exists at repo root. HEAD commit is from today (2026-09-27) — extremely active. No CLA-bot check performed.
