### 1.2 Coherence: the generated spec is not a well-organized document

Direct reads of the three 2026-06-19 benchmark runs (`repos/chi-1.5.8/quality/REQUIREMENTS.md`, `repos/express-1.5.8/…`, `repos/virtio-1.5.8/…`) show seven recurring structural defects:

- **C-1 — Tool-process contamination.** Every product spec ends with ~8 REQs about QPB's own run layout ("Per-bug writeups are placed at `quality/writeups/BUG-<id>.md`" — chi:130-152, express:140-188, virtio:197-249). - **C-2 — Scrambled identifiers.** REQ IDs do not follow document order (chi sections run REQ-001/004/005, then 002, then 003/006; express runs 001/007, then 002…). `references/requirements_pipeline.md` Phase E.6 specifies a final sequential renumber; it demonstrably does not fire.
- **C-3 — Degenerate sections.** express has six functional sections holding one REQ each — the grouping does nothing, matching the degeneracy `schemas.md` (§6, functional_section notes) already warns about.
- **C-4 — Narrative inconsistency.** virtio rendered a Project overview + Cross-cutting concerns (Phase E.1/E.3 fired); chi and express rendered neither. The Phase E narrative pass — the pipeline's designed answer to "flat list → coherent document" (`requirements_pipeline.md` Phase E; lineage back to `QPB_v1.3.1_Design.md` "turn a pile of source code into a coherent set of testable requirements") — fires unpredictably, and nothing in the gate checks for it (the gate validates the manifest, never the rendered document — `schemas.md` §6).
- **C-5 — Pipeline internals leak into the render.** "Asymmetry-promotion: Finding 7 prose asymmetry … is promoted here" (chi:35); `<!-- cluster: heterogeneous -->` HTML comments on UCs (chi:182, virtio:285). Derivation metadata belongs in the manifest, not the adopter-facing spec.

A requirement should state intended behavior; the observed divergence belongs in BUGS.md. Sentence-length REQ titles (chi REQ-001's title is a full normative sentence) compound this.

## 5. Feature C — Spec organization & coherence (the headline)

**Problem.** §1.2: the rendered REQUIREMENTS.md is structurally incoherent in seven named, recurring ways, because (a) the document architecture is under-specified (one line in `references/phase2_generation_guide.md`: organized by `functional_section`, intro paragraph, ordered by REQ id), (b) the Phase E narrative pass is optional in practice and unchecked, and (c) the gate validates the manifest only and never the rendered document, so render defects are invisible to every mechanical check QPB has.

**Design principle.** *The manifest stays the source of truth; the rendered spec becomes a contract-checked presentation.* Two layers, matching QPB's house style: a mechanical **render contract** enforced by `quality_gate.py`, plus an LLM-judgment **coherence rubric** enforced by the Phase 4 Council charter. Wherever a defect class can be checked mechanically, it is; prose quality stays with the Council.

### 5.1 Separate the product spec from the tool contract (fixes C-1)

- The ~8 artifact-layout invariants move out of REQUIREMENTS.md into a new run artifact, `quality/RUN_CONTRACT.md` (name resolved per Decision Record #7), rendered from the same records. They remain gate-enforced per-run — they were never wrong as *invariants*, only mislocated as *product requirements*.
- Render-contract check: REQUIREMENTS.md contains **zero** REQs whose References point exclusively into `quality/` — mechanically checkable; mutation-bite by re-adding one.

### 5.2 Canonical document architecture (fixes C-3, C-4; argued)

Target shape — deliberately the shape of the Haiku benchmark (`Haiku QPB requirements analysis/REQUIREMENTS.md`, 2,129 lines, 95 REQs), which is the project's own "coherent document" reference standard (RM-014: it beat QPB's self-audit 3× on coverage *and* reads top-down):

1. **Header** — accurate generator stamp from the single version source (fixes C-7).
2. **Overview** — mandatory on every run regardless of size: what the system is, derivation scope and evidence base, tier distribution, and the F-1 coverage-and-gaps statement. (Phase E.1 becomes unconditional; the express-class omission becomes a gate failure.)
3. **Actors & roles** — who the requirements serve (Haiku-benchmark shape; also the natural organizer for Feature D's interview).
4. **Requirement sections — grouped by an organizing principle the derivation *chooses* per system** *(revised 2026-07-21; see "Choosing the organizing principle" below).* The sections are no longer required to be "functional." The derivation selects the organizing principle that best fits *this* system from the IEEE 830 §5.3 menu — by feature/capability, use case/journey, user class/stakeholder, mode/state, object/entity, stimulus-response/interface, or functional hierarchy — states which principle it chose and a one-paragraph rationale at the top of the section list, and orders the sections **most-relevant-to-the-primary-reader first** (the generalization of the old user-facing → infrastructure rule; for a functional grouping the two coincide). Each section carries a **section overview** stating the theme that unifies its requirements under the chosen principle (not a restatement of its REQ titles), and holds **≥2 REQs or a one-line singleton justification, else merged** (fixes C-3). Feature grouping remains the safe **default** when no principle clearly fits — but the choice, and its rationale, must be stated even then.
5. **Non-functional sections** — Feature A's NFR REQs grouped by `nfr_class`.
6. **Cross-cutting concerns** — Phase E.3, mandatory when >1 functional section.
7. **Use cases** — unchanged content, cleaned render (no HTML comments — C-5).
8. **Traceability appendix** — rendered reverse index UC→REQ, plus REQ→BUG links carrying final FP-audit dispositions. One-way REQ→UC in the manifest is unchanged; the appendix is render-time derivation, which `schemas.md` already sanctions.
9. **Glossary / definitions** — *advisory, added 2026-07-20.* Terms of art used by the requirements, defined once. Modeled on IEEE 830 §1.3 (superseded by ISO/IEC/IEEE 29148; cited as lineage, **not** as a conformance claim), which carries a glossary because terminology drift is a top requirements-defect class — and terminology stability is exactly what the readability rubric's *Consistent* dimension scores. **WARN only, never a gate FAIL**, on the F-1 precedent: a missing glossary is a signal, not a failure.

#### The render contract must fail closed on a manifest-vs-render marker mismatch *(added 2026-07-21)*

Every check above reads `### REQ-NNN:` headings in `REQUIREMENTS.md`. If the render carries **no** such headings, the contract currently goes inert (INFO, "not a contract-shaped render, render contract skipped"). That is **fail-open**, and a 2026-07-21 smoke test showed the consequence: two independent weak-model runs rendered requirements as `**REQ-NNN:**` (bold) instead of `### REQ-NNN:` headings, the whole contract skipped, and a document carrying the exact C-3 singleton-section defect Feature C exists to catch shipped **unflagged**.

The root cause was an instruction-architecture gap (the format rule lived in `requirements_pipeline.md` but the generator is routed to `phase2_generation_guide.md`, which never stated it — fixed separately). But the contract must not depend on the generator getting the marker right, because the manifest already proves whether requirements exist:

- **If `requirements_manifest.json` holds ≥1 product REQ records but `REQUIREMENTS.md` carries zero `### REQ-NNN:` headings, that is not "not applicable" — it is a render that failed to present its requirements in contract shape. FAIL, not INFO-skip.** This follows the contract's own existing precedent: an unterminated code fence already FAILs with "refuse to certify rather than pass by default." A populated manifest with an unparseable render is the same situation.
- The existing wrong-heading-*level* WARN (`## REQ-NNN:` etc.) stays. The new rule closes the remaining fail-open path: markers absent entirely while the manifest says they should exist.
- A genuinely empty manifest (zero product REQs) still skips — there is nothing to render, and that is correctly "not applicable."

**Two rows are deliberately unenforced and should stay visible rather than be quietly closed:** 4b (section ordering) is judgment the rubric scores, and 5 (NFR sections) lands with Feature A. Anything else appearing without a mechanism is a defect in this matrix.

*Why order most-relevant-to-the-primary-reader first:* the spec's first consumer is an operator deciding whether the derivation captured intent (Feature D); they recognize what matters to them before internals. Implementers, who prefer architectural ordering, read the References fields anyway. (The 2026-07-19 resolution fixed this as literal "user-facing → infrastructure"; the 2026-07-21 revision generalizes it — see §12 and the reversal record.)

#### Choosing the organizing principle (a Phase E reorganization pass)

*Added 2026-07-21. This is the substance of item 4 above.* A requirements document is only as legible as its grouping, and **there is no single right grouping** — IEEE 830 §5.3 lists a menu of organizing principles and states plainly that the best one depends on the system, not on a house style. The pre-2026-07-21 design imposed one principle (functional sections) on every target; a 2026-07-21 smoke test showed the cost — on `bus-tracker` the derivation mixed four grouping axes (functional, interface, cross-cutting, architectural) without ever *choosing* one, because it was slotting requirements into a mandated scheme rather than deciding how this system's requirements should be organized.

**The pass.** After the requirements exist but **before Phase 2 ends**, the derivation runs an explicit reorganization step (an enrichment of `references/requirements_pipeline.md` Phase E, ahead of the E.6 renumber):

1. **Assess the system** — what kind of thing is it? A workflow (favours use-case/journey grouping), a multi-actor system (user-class/stakeholder), a protocol or API surface (stimulus-response/interface), a capability library (feature), a stateful device (mode/state), a domain model (object/entity).
2. **Choose one organizing principle** from the IEEE 830 §5.3 menu (feature · use case · user class · mode · object · stimulus-response/interface · functional hierarchy · a justified combination). Default to **feature** only when no principle clearly fits.
3. **Regroup** the requirement records under that principle. Records do not change shape — only their `functional_section` assignment and the section grouping change (this is the same manifest-write-back the renumber already performs; extend it to the regrouping).
4. **Write a section overview per section** — one short paragraph naming the theme that unifies that section's requirements under the chosen principle. This is what Feature D's Stage 2 validates section by section.
5. **State the choice** — at the top of the section list, name the principle and give a one-paragraph rationale ("organized by *user journey* because this is a workflow system whose requirements cluster around the stages a user moves through").
6. **Order + renumber** — sections most-relevant-to-the-primary-reader first, then the E.6 sequential renumber.

**Mechanical vs. judgment.** The render contract (§5.3) checks only that a principle is *named*, that a *rationale* is present, and that each section carries a unifying *overview* — it does **not** judge whether the choice is optimal. Whether the derivation picked the *right* principle is a Feature D interview question (Stage 1 plays the choice back to the operator) and a Phase 4 Council *Well-organized* rubric item. Mechanical checks structure; judgment checks quality — the same division the rest of Feature C uses.

## 6. Feature D — The requirements validation interview (fitness-for-purpose)

**Problem.** QPB verifies that code conforms to derived requirements but never validates that the derived requirements are the right ones — the missing link in the Juran chain (§0 #4). Nothing confirms the derived requirements against what the operator actually intended. The 2026-05-02 worked example (`Reviews/QPB_v1.6.x_Requirements_Review_Worked_Example_2026-05-02.md`) proved a 10-minute interactive session surfaces real defects (projected-vs-measured mismatch, glossary drift, benchmark double-count, hardcoded-enumeration coupling) that no autonomous pass caught. The 8-dimension proposal (`QPB_v1.6.x_Requirements_Review_Proposal.md`) designed the full system but was repositioned out of v1.6.0; meanwhile a lighter walkthrough **already shipped** in v1.5.7 (`quality/REVIEW_REQUIREMENTS.md` + `REFINE_REQUIREMENTS.md`, guided/self-guided/cross-model modes, progress in `REFINEMENT_HINTS.md`) — which the proposal never acknowledges. v1.6.0 reconciles the two.

**Design — MVP slice of the 8-dimension proposal, superseding the shipped walkthrough.**

- **Shape — progressive, broad strokes first, drill-down on demand.** The Feature C document architecture is the interview's outline; the interview descends it:
  - **Stage 1 — validate the narrative *and the organizing principle*.** The agent plays back its understanding at the top of the document: "here's what I think this system is, who it serves, and what its major behavioral areas are — is that right?" (Overview, actors & roles, section themes, and the F-1 coverage-and-gaps statement: "here's what I believe I did not cover — intentional?"). **It also plays back the organizing principle it chose** (§5.2): "I organized these requirements by *user journey* because this is a workflow system — is that the right lens, or would grouping by *stakeholder* fit how you think about it?" The organizing choice is itself a high-yield fitness-for-purpose question — a wrong lens makes every section feel slightly off — and it is cheapest to correct here, before Stage 2 descends the sections. Most fitness-for-purpose defects (wrong system, wrong actor, missing area, **wrong organizing lens**) surface here.
  - **Stage 2 — validate sections and use cases.** Section by section, in reader-relevance order: the agent reads the section's **unifying overview** (§5.2 item 4) and asks whether that theme is a real, cohesive concern of the system — "this section groups everything about X; is X how you'd carve up the problem?" — then its use cases. "This section says the system guarantees X under Y — is that what it's *supposed* to do?" The section overviews exist precisely so this stage has a coherent unit to validate rather than a bare list.
  - **Stage 3 — per-REQ drill-down, operator-pulled.** Individual REQs are examined only where Stage 1/2 surfaced doubt or where the operator steers ("show me the redirect requirements"). Breadth-first by default; depth is never pushed.
  - Three moves at every stage, in the operator's control: **confirm** (recorded as evidence — see F-2), **correct** (operator states what it should say — covers merges, splits, and rewording; the derivation absorbs the correction), **add** (operator names behavior the derivation missed). Plus **drop** and **defer**. *(The proposal's six structural dispositions — `tighten-prose`, `merge-with-related-REQ`, `split-into-multiple-REQs`, etc. — are folded into **correct**; per-attribute disposition taxonomy was inspection-tool ceremony for an MVP.)*
- **Elicitation content:** questions drawn from the 34 catching questions in `Reviews/Requirements_Miss_Archeology.md` (highest-yield five first: artifact-category fit, artifact-shape, judgment-vs-comparison, self-encoding, operator-vs-gate success) and the four worked-example question classes (outcome verification, terminology disambiguation, identity/independence, dependency tracing) — mapped to stages: category/shape questions belong to Stage 1, dependency/identity questions to Stages 2-3.
- **Write-back is the point:** corrections and additions land in the **manifest** (not just the render) as new/updated REQ records carrying `source_type: operator-confirmation` (F-2), then the Feature C renderer re-renders — so the spec absorbs corrections coherently instead of accreting patch notes. A surgical re-derivation of a corrected REQ (the proposal's iterate-until-clean, Dimension 3) is in scope only as "re-run derivation for this REQ with the operator's correction as evidence"; full loop tooling waits.
- **Renumber is the interview's terminal step, not a deferral** *(added 2026-07-21).* An `add` move inserts a REQ into an existing section; keeping document-order IDs sequential (the §5.3 contract) would then renumber REQs the operator just confirmed *by ID*, mid-conversation. The resolution is **not** to defer the renumber (a 2026-07-21 test showed all three targets deferred it and shipped out-of-order IDs — e.g. express rendered `…013, 035, 014…`): it is to run the Phase E.6 renumber **once, as the final step after the operator finishes all moves**, atomically updating every id-carrying cross-reference in the manifest in the same pass — `use_cases[]`, UC `requirements[]`, BUG `requirement` fields. The operator never sees IDs shift during the conversation; the final document is sequential. **`operator_confirmations.jsonl` is deliberately NOT touched** — per §8 F-2a it is append-only and content-keyed (`req_title` + conditions), not id-keyed, precisely so a renumber cannot invalidate it; a confirmation resolves to its REQ by content after the renumber. (Correction 2026-07-21: an earlier draft of this bullet said to update the confirmations' `req_id` fields; the record has no such field and rewriting it would break the append-only invariant — the content-keying is what makes the renumber safe. Caught by instruction 007's Council.)
- **Artifacts:** `quality/REQUIREMENTS_REVIEW.md` defect log (by Wiegers attribute + disposition); transcript preserved to `quality/review_sessions/<TIMESTAMP>-<topic>.md` behind an explicit operator save-gate (the proposal's privacy concern). Inspection metrics (Dimension 8) and the QI-loop synthesis (lessons-learned → calibration hypotheses) stay in the later slice, as the proposal already sequenced.
- **Deferred from the proposal to post-v1.6.0:** Dimension 5's informal-source corpus + `informal-spec` role tag, Dimension 8 metrics, the QI-loop closure. *(Dimension 2, the multi-perspective lens, was deferred here but is pulled forward 2026-07-22 as Feature H, §8b.)*
- **Supersession:** the interview replaces `REVIEW_REQUIREMENTS.md`/`REFINE_REQUIREMENTS.md` generation (one system, not two); their guided/self-guided/cross-model modes are preserved as interview entry modes.
- **Placement — offered after Phase 2, before Phase 3** *(operator decision 2026-07-21; reverses the earlier "playbook-end summary offers it" placement).* The requirements are complete at the end of Phase 2. Phases 3–6 then *consume* them — tests, code review focus, spec audit, and TDD are all derived from the requirements. Offering validation only at the end (the slot inherited from the superseded v1.5.7 walkthrough, which was a review-*after*-the-run tool) means every downstream artifact was built on unvalidated requirements, so an operator correction at the end leaves them stale. Validation is a fitness-for-purpose gate on the spec, and a spec is validated *before* you build on it. So the playbook offers the interview at the Phase 2 → Phase 3 boundary, with explicit operator-facing messaging: the requirements are done, they can be validated now before the rest of the run depends on them, and the offer is opt-in (never auto-started). A run that declines is reminded once at playbook-end that validation is still available — discoverability is preserved without moving the primary offer back to the end. *Why this is safe for the fitness-for-purpose purpose:* the interview validates the requirement text (Complete / Consistent / Verifiable), which needs no downstream evidence; the only thing an early offer forgoes is REQ→BUG context in the traceability appendix (bugs are found in Phases 3–5), which is not load-bearing for "are these the right requirements."

**Verification.** Fixture session against the QPB self-derivation: a scripted operator (test double) issues one confirm, one correct, one add, one merge; acceptance = manifest updated with correctly-shaped records, re-render passes the Feature C contract, defect log and transcript artifacts present and gate-validated. The 2026-05-02 worked example is re-run as a semi-scripted acceptance walkthrough. Mutation: a correction that never reaches the manifest must fail the fixture.

**Dependencies.** Feature C (renders the interview's input and output; without it the interview walks a jumbled document). Feature A optional but valuable (NFR sections get interviewed too). Delivery shape resolved (Decision Record #7): **skill-protocol chat** — a protocol reference (`references/requirements_interview.md` or equivalent) the agent follows in a normal session, writing session artifacts to `quality/`; no new interactive Python surface; the shipped walkthrough's guided/self-guided/cross-model modes carry over as entry modes.

## 8. Feature F — New in this rewrite

### F-1 — Coverage-and-gaps statement (slimmed 2026-07-19)

**Problem.** "Skimpy" is invisible: express ships 8 product REQs and passes every gate (RM-007's degenerate-output blindness, at the spec level), and the operator has no rendered signal of what the derivation chose not to cover.
**Design (slim).** The derivation emits an honest **"coverage and known gaps" statement** into the Overview (Feature C §5.2 item 2): what the derivation covered, what it deliberately or knowingly did not (areas explored but not REQ'd, files skimmed, surfaces out of reach), stated in prose by the pass that knows. Advisory, never a gate FAIL. Its consumer is interview Stage 1, which plays it back: "here's what I believe I did not cover — intentional?" The mechanical version — per-language public-surface enumerators joined against REQ References ("41 of 87 exported symbols") — is **deferred as later hardening**, not designed here.
**Verification.** Render-contract check: Overview contains a non-empty gaps statement. Interview fixture (Feature D) exercises the Stage-1 gap question against it. Honesty of the statement is a Phase 4 Council rubric item (LLM judgment, not regex).
**Dependencies.** Feature C (render slot); Feature D (consumer).

### F-2 — Operator confirmation as first-class evidence (grounded; makes Feature D durable)

**Problem.** Interview outcomes have nowhere to live in the evidence model: `source_type` today covers formal docs, code, informal docs, inference — not "the owner said so."
**Design.** New evidence shape `operator-confirmation`: records the session, the operator's statement, and the date; attachable as the citation-equivalent for REQs confirmed/corrected/added in a Feature D session. Resolved (Decision Record #7): **transcript-as-citable-source** — the preserved session transcript is the citable document (`source_type: operator-confirmation` + a citation into the transcript file/line range), so the existing §5.4 byte-citation machinery applies nearly unchanged and no new tier is invented.
**Verification.** Gate validates the new evidence shape; a Feature D fixture correction round-trips into a citable record.
**Dependencies.** Feature D; `schemas.md` extension.

#### F-2a — Cross-run durability of operator confirmations *(added 2026-07-20)*

**The hazard, stated plainly.** Interview corrections land in `requirements_manifest.json`. QPB re-derives that manifest on every run. With F-3 dropped, the only surviving obligation is that a re-derivation must not discard an `operator-confirmation`-backed REQ **within the same run** — across runs, nothing protects it. Concretely: an operator spends thirty minutes correcting a spec, re-runs QPB the following week, and the corrections are silently gone. That is a bad product outcome sitting inside the release's headline feature, and the Design should not ship it unremarked.

**Decision (operator, 2026-07-20): persist without resolving identity.** Losing the operator's work and solving cross-run REQ identity are *different problems*, and only the first needs solving now.

- **Artifact:** `quality/operator_confirmations.jsonl` — **append-only**. Derivation never rewrites it; a run that would delete or truncate it fails the gate.
- **Each record carries** the REQ's *content* at time of confirmation (title + conditions of satisfaction, not merely an identifier), the operator's statement verbatim, an ISO date, and a citation into the preserved session transcript per F-2's transcript-as-citable-source machinery.
- **Deliberately not keyed on REQ id.** Phase E.6 renumbers every run, so an id is meaningless across runs — this run's REQ-005 is not last run's REQ-005. Any later matching is content-based and **advisory**.
- **Read path:** where a later run finalizes the manifest, it reads the file and reports — *"N operator-confirmed requirements from prior sessions; K appear absent from this derivation"* — quoting the operator's original words.
- **Surface, never auto-merge.** Automatic re-application would require exactly the cross-run identity resolution this defers. The goal is to convert **silent data loss into a prompt**.

**What this explicitly does not solve.** Cross-run REQ identity (RM-008's cardinality-loss problem) stays deferred with F-3, and needs its own design doc. This is the cheap 80%: the operator's work survives and is surfaced, but re-applying it is a human decision.

**Verification.** A fixture run that confirms a REQ, then re-derives, must (a) still have the `.jsonl` intact and (b) report the prior confirmation. Mutation: a derivation path that truncates or overwrites the file fails the fixture.

**Consequence for Feature D's build:** this changes *where the interview writes* — manifest **and** the append-only artifact — so it is in scope for the Feature D slice, not a later retrofit.

### F-3 — Re-run spec diff (**dropped from v1.6.0**, 2026-07-19)

Dropped per the simplicity pass (resolves former OD-6). The problem is real — re-runs can silently drop operator-confirmed REQs — but REQ identity across runs is its own hard design problem (RM-008's cardinality-loss lesson applies) and serves neither organization nor validation directly. One narrow obligation survives into Feature D's scope: **a re-derivation must not silently discard an `operator-confirmation`-backed REQ within the same run** (the interview's write-back is durable for the run that produced it). Cross-run protection waits for its own design doc; sketch preserved in the 2026-07-18 revision (git history).

## 8a. Feature G — Dump-and-go gathered-documentation ingest *(added 2026-07-22)*

**Problem.** A requirement's tier — whether it is grounded in an authoritative spec (Tier 1/2, citable, byte-verified) or merely inferred from code (Tier 3) — is only as good as which documents the pipeline treats as authoritative. Today that decision is made by **folder placement**: `reference_docs/cite/` → citable; `reference_docs/` top level → Tier 4 background. The classification into those folders happens at *gather time* (the doc-gathering prompt asks an AI to sort files) or by hand. Two failures follow:

1. **A user who just dumps documentation gets no Tier 1.** The 2026-07-22 three-repo test proved it — chi and express came out **all Tier 3** despite having authoritative docs in `docs_gathered/`, because nothing had sorted those docs into `cite/`. virtio came out Tier 1 only because its agent happened to copy the spec into `cite/`. Same docs, three agent decisions, three tier outcomes.
2. **The determinism the folder scheme promises is illusory.** The classification is *already* an AI judgment (the gather-time prompt decides `cite/` vs not); folder placement just freezes it. When the gather step is skipped or done by different agents, the "deterministic flag" produces the inconsistency above.

**Design — one folder, AI-classified at ingest, reviewable.** The operator dumps *any* documentation into a single input folder (no required `cite/` split, no pre-sorting). At ingest, the derivation AI **classifies each file by content** — an authoritative contract the code must conform to (spec, RFC, published API reference, formal standard → citable Tier 1/2) versus background context (CVE advisory, chat log, design note, retrospective, issue-tracker export → Tier 4). It writes a **reviewable classification manifest** (per file: assigned tier + a one-line reason), which the operator can eyeball or override. Default is dump-and-go; an optional operator sidecar gives explicit deterministic control when wanted.

**The safety architecture — a deterministic mechanical floor *under* the LLM classifier, not soft instructions to it.** *(Revised 2026-07-22 after Council review: the first draft guarded advisory-poisoning only with an instruction to the LLM and an optional manifest review — a rhetorical guard where a mechanical one is required. The danger the Council named: a security bulletin or hardening guide written in MUST/SHALL normative language reads *like* a contract, and genre-misclassifying an advisory as normative is the exact error that produced the OpenFGA 0/3 failure.)*

- **Deterministic advisory floor (mechanical, the LLM cannot override).** Before the classifier runs, a deterministic pass forces **Tier 4** on documents matching advisory signatures — a `CVE-`/`GHSA-` identifier, a `nvd.nist.gov` / `cve.org` / vendor security-advisory URL, a "Security Advisory" / "vulnerability" header, or **security-genre markers beyond the identifier set** (a hardening-guide / best-practices / benchmark title, or high MUST/SHALL-density prose whose subject is *how to configure/harden* rather than *what the system contracts to do*). The LLM classifier can only tier the *remaining* documents, and only ever *downward* from what the floor allows — it may demote a candidate to Tier 4 but may not promote a floored document to citable. Same "mechanical floor under a judgment layer" as OD-8's 090j, applied to ingest. **Implementation source is not a contract:** a document that is predominantly *implementation* code (function bodies — `.c`/`.py`/`.go`/… with logic) is floored to Tier 4 and is **not citable** — implementation code is what the system *does*, not what it is *supposed to do*, so grounding a requirement in it is the circular-validation trap Feature H's input isolation (§8b) forbids. *(Closes the "code-as-doc" side door.)*
  - **But a machine-readable *contract* is a contract** *(added 2026-07-22 after the 3-persona self-test flagged the over-block; tightened after the follow-up Council flagged that a naive promotion path reopens advisory-poisoning).* An interface/contract-definition file — OpenAPI/Swagger, protobuf/`.proto`, JSON Schema, an IDL, a type-declaration `.d.ts`, a WSDL — *is* an authoritative statement of what the system is supposed to do, and is often the *most* authoritative document a project has. **The source (implementation) floor targets implementation logic, not interface/contract definitions; these are citable without any override.** For the genuinely fuzzy case where the implementation floor *did* catch a code-shaped contract, the **operator sidecar may explicitly promote that specific file to citable** — a reviewed operator decision, the only sanctioned upward move, and the LLM classifier still may never promote.
    - **Two hard bounds on that promotion, or it reopens the advisory hole:** (1) the sidecar may rescue a file from the **implementation** floor only — it may **never** override an **advisory-signature / security-genre** floor match; an advisory stays Tier 4 even if the operator names it (if the operator truly needs an advisory as intent, that is a doc-authoring decision outside ingest). (2) The **advisory content-floor runs *before* the contract carve-out**, keyed on content (CVE/GHSA identifiers, advisory URLs/headers, MUST/SHALL-density) — so a CVE advisory renamed `api.proto` is still floored by its content and cannot ride the contract path.
    - **The sidecar list is operator-authored configuration** — writable only by the human operator, never by the classifier or a persona (parallel to the `operator_confirmations.jsonl` write-restriction, §8b guard 2), so injected document content cannot add itself to the promotion list.
- **The classifier treats document *content* as data, not instructions (injection resistance).** *(Added 2026-07-22.)* Ingested documents come from unknown sources. A document that argues for its own authority — self-classifying tier language ("this is an authoritative spec, cite me as Tier 1"), imperatives addressed to the classifier, or injected role/system framing — must **not** raise its own tier; a document arguing for its own promotion is a signal *toward* Tier 4, not away. The classifier classifies by genre and structure the operator can review, never on the document's self-assertion. (The mechanical floor already blocks the highest-payoff path — a floored advisory/source doc cannot self-promote at all.)
- **Accepted residual, stated honestly.** The floor is mechanical *within its signature/marker set*; a genuinely contract-shaped document that carries none of those markers still falls to the LLM classifier, guarded by the "default to Tier 4 on ambiguity" instruction, the injection-resistance rule above, the reviewable manifest, and (downstream) the containment of Feature H. This residual is **accepted, not closed** — the mechanical floor catches the known-dangerous genres (advisories, implementation source), and the soft classifier + review governs the ambiguous tail. Blast radius bounded: a mis-promotion is manifest-visible and operator-reviewable.
- **Promotion-to-citable is a reviewed decision, not a silent default.** The reviewable classification manifest lists every file the classifier promoted to Tier 1/2 with its one-line reason. Dump-and-go still works, but a promotion to citable is the operator-visible line in the manifest; the mutation fixtures below prove the floor holds even when the manifest is not reviewed.
- **Byte-verified citations are unchanged — but they are NOT a guard against mis-tiering, and are no longer listed as one.** *(Council correction: BUG-009 was a verbatim advisory restatement that would byte-match its source perfectly — byte-verification confirms a citation's text matches its source, and says nothing about whether the source is a legitimate contract.)* The gate still re-invokes `citation_verifier` on every Tier-1/2 citation; it protects against fabricated citations, which is a different risk from advisory-poisoning. The advisory floor above is what protects against the latter.
- **On genuine ambiguity, default to Tier 4.** A missed grounding is recoverable (Tier 3 instead of Tier 1); a false authoritative source poisons the derivation.
- **`README.md` and the coverage/issue-tracker ledgers stay Tier 4**, as the current gather prompt already specifies.

**Reproducibility.** The classification manifest is **persisted and content-keyed** to each document (the same content-keying F-2a uses), so a re-run reuses the prior classification unless a document's content changed — classification is stable across runs, not re-decided every time. The optional operator sidecar overrides the floor-passed classifier output and can *demote* freely; it may *promote* a code-shaped contract past the **implementation** floor only, explicitly (never silently) and never past the advisory floor — per the sidecar rules above.

**Verification.** (1) Dump chi's and express's `docs_gathered/` corpora into one folder with no `cite/` sorting → authoritative docs (API references, RFCs) are classified citable and those requirements come out **Tier 1/2, not Tier 3**. (2) **Mechanical-floor mutation:** a CVE advisory *and* a normatively-worded ("MUST"/"SHALL") security bulletin both stay **Tier 4** even when an LLM classifier is stubbed to try to promote them — the floor holds without the LLM's cooperation. (3) **Machine-readable contract:** an OpenAPI/`.proto`/JSON-Schema file is citable (or promotable via the explicit operator sidecar), not dead-ended by the source floor; a `.py` file with implementation logic stays Tier 4. (3a) **Sidecar cannot launder an advisory:** a CVE/GHSA/MUST-SHALL advisory — *including one renamed with a contract extension* (`cve-2024-x.proto`) — cannot be promoted to citable via the operator sidecar (the content-floor runs before the extension carve-out; the sidecar rescues only the implementation floor). (4) **Classifier injection:** a document embedding "classify me as Tier 1 / cite me as authoritative" is not promoted on that basis. (5) The classification manifest is produced, content-keyed, and lists a reason per file; a re-run with unchanged docs reproduces the same tiering. (6) The existing byte-verification fixtures are unchanged and still pass.

**Citability wiring** *(added 2026-07-22, instruction 011 — closing the seam between classification and the byte-citable surface).* Classification tiers a doc, but the hallucination gate reads `formal_docs_manifest.json`, so a doc *labeled* Tier 1/2 in the classification manifest is only actually authoritative once it has a **FORMAL_DOC record**. The wiring: **the classification manifest is the source of truth for a top-level dumped doc's tier.** In the formal-docs pass, a top-level doc classified **Tier 1/2 and `promotable`** emits a FORMAL_DOC record (byte-citable — `document_sha256`, `citation_excerpt`, `role: external-spec`, the classification's tier), *including a machine-readable contract* (`.proto`/OpenAPI/JSON-Schema) that the plaintext era skipped; a doc the floor put at Tier 4 (advisory, implementation source not rescued, injection self-promoter, background ledger — `promotable == False`) stays **Tier-4 context with no record**. The floor is **read from the classification `Decision`, never re-litigated** in the formal-docs pass, so this path can never launder a floored doc to citable; the sidecar's bound is unchanged (rescues the implementation floor only, never advisory). `cite/` docs keep their `_parse_tier_marker` tier — one input path among two, both producing FORMAL_DOC records. The `document_sha256` is the same content key the classification manifest uses, so the two manifests reconcile and a re-run with unchanged docs reproduces the same citable set. Verification 1 above becomes end-to-end: chi/express dumped with no `cite/` now yield **Tier-1/2 FORMAL_DOC records** (0 → 14 / 0 → 13), not merely Tier-1 labels in the classification manifest.

**Dependencies.** The Phase 1 ingest pipeline (`bin/reference_docs_ingest.py`), `references/phase1_exploration_guide.md`, and `references/DOC_GATHERING_PROMPT.md` (the gather prompt can still *pre*-classify as an optimization, but it is no longer *required* for tiering — ingest-time classification is the floor). QPB source; lands via the diagnosis→worker lane.

## 8b. Feature H — Agent-driven persona validation *(added 2026-07-22; extends Feature D)*

**Problem.** Feature D built the fitness-for-purpose interview for a **human operator**. But validation that only happens when a human domain expert is available does not scale, and validating the requirements is the release's whole thesis — "make sure the requirements are the *right* requirements" (§0 #4, the Juran link). The insight: *if a human domain expert can read this spec and judge whether it captures what the system is supposed to do, a domain-expert agent can do the same.* The 2026-07-22 three-repo test already demonstrated a weak form of this — informed sub-agents ramped on `docs_gathered/` and each **autonomously added a real missing requirement** (chi's regexp params, express's `req.range`, virtio's indirect-descriptor constraints). Feature H formalizes that.

**Design — fresh-context domain-expert personas run the Feature D interview as the operator, under strict input isolation.** Each persona is a **fresh-context sub-agent** that ramps on its inputs, adopts the role, and descends the Feature D interview (Stage 1 narrative + organizing principle → Stage 2 sections → Stage 3 per-REQ), exercising the five moves as that expert would.

**Persona selection — chosen from a catalog, with anchors** *(revised 2026-07-22 per operator, mirroring the organizing-principle "choose from a menu" pattern; validated by the 3-persona self-test).* The derivation does not impose one fixed set — it **selects the lenses that fit *this* system from a persona catalog, and justifies the choice**, exactly as it chooses an organizing principle. But two lenses are **anchored** (always included), because a system's own author is the worst judge of whether they matter:
- **Domain expert** — derived per system from the Phase 1 domain + gathered docs (e.g. *"you are an expert in Java serialization and the JVM object model"*).
- **Security reviewer** — anchored because security gaps are cross-cutting and chronically under-weighted. *(The self-test is the proof: the domain persona filed prompt-injection as a mere candidate — outside its lens — while an anchored security persona grounded it. Without the anchor, an AI choosing lenses for "just a requirements tool" would have skipped it.)*
- **AI-selected additional lenses** from the catalog, per system with a stated reason — e.g. API/consumer or integrator (libraries), operator/SRE (services), data-privacy/compliance (regulated data), accessibility (user-facing UI), performance (hot-path), reliability/failure-mode (distributed), adopter/end-user. The catalog is a menu with selection criteria, not a fixed roster.

Each selected persona then runs as above, in its own fresh context.

**Input isolation — load-bearing, and the discipline Feature H actually shares with v1.6.1's FP-audit** *(added 2026-07-22 after Council review — the first draft borrowed only multi-seat independence and left this out, the exact hole that would collapse validation into circularity).* A persona receives **only the gathered documentation + the rendered spec + the rubric. It is denied the implementation tree.** This is what keeps validation *fitness-for-purpose* (against documented intent) rather than *fitness-to-implementation* (against what the code happens to do — the circular trap the ground-truth rule forbids). A persona that reads source is a **fabrication tell**, exactly as a writeup-fed auditor is for Feature B, and the acceptance oracle checks for it. The isolation covers **every** move including `confirm` — a persona confirming a requirement because "the code does this" is circular validation wearing a validated stamp; a `confirm` must rest on the docs/intent, not observed code behavior.

**Isolation is least-privilege, not merely impl-tree denial** *(added 2026-07-22 after the 3-persona self-test — a security lens flagged that fencing one directory while feeding an agent untrusted documents leaves every other authority open).* Because a persona ingests untrusted documents from unknown sources, its authority is confined to **its declared inputs (gathered docs + rendered spec + rubric) and its declared write target (a candidate diff-set for the manifest)**. It has **no outbound network access** and **no filesystem read access beyond its declared inputs** — in particular it cannot read secrets, credentials, `operator_confirmations.jsonl`, or paths outside the run. An isolated-by-topic agent fed attacker-influenced content but holding unbounded tool/network authority is an exfiltration/SSRF vector; least-privilege closes it. **Enforcement mechanism (scoped for v1.6.0):** the persona sub-agent is spawned with a **tool allowlist** — Read confined to its declared input paths, no shell, no network/fetch tools — so out-of-bounds access is *prevented*, not merely detected; the fabrication-tell (Verification 3) is the backstop, not the primary control. A from-scratch OS/network sandbox is **not** in scope for this release — if genuine kernel/network-level confinement is wanted beyond tool-allowlisting, it belongs to the v1.8.0 security line (§9), not here. This keeps H a coherent v1.6.0 finish rather than a sandbox sub-project.

**The ceiling, not the floor.** Within that isolation the persona does **fitness-for-purpose judgment**, not a doc-to-requirements diff. It uses domain expertise *beyond* the gathered docs to catch what an expert *expects* — a serialization library should handle circular references, custom adapters, null semantics — and flags their absence. But expertise-driven expectation is disciplined by the next two guards so it does not become a spurious-requirement generator.

**Guards — the load-bearing part, because an agent that rewrites requirements can also hallucinate one:**

1. **Grounded, and fit-for-*this*-system.** Every `add`/`correct` a persona writes must (a) **cite the documentation that justifies it**, byte-verified through the citation gate — and (b) **justify why *this* system needs it**, not merely that some document mentions it. A domain expectation the gathered docs do not cover, or that the persona cannot tie to this system's purpose, is surfaced as a **candidate/uncertain finding for human attention — never written in as a grounded REQ.** (This is the false-positive discipline: "a serializer should handle circular refs" is a candidate finding, not an auto-added requirement, unless the docs establish it as this library's contract.) **Byte-verification is not an injection guard** *(added 2026-07-22 — the security lens caught this)*: it proves only that the cited text exists in the source document, so an `add` citing attacker-injected text in an untrusted doc byte-verifies perfectly. Grounding must not rest *solely* on content the ingested document controls; a change traceable to injection-shaped content (imperatives to the derivation/persona, self-authorizing tier claims) is recorded candidate-only, never grounded.
2. **Honest provenance, with a schema home.** Persona-written changes carry **`source_type: agent-validation`** in the manifest — a first-class `schemas.md` shape parallel to F-2's `operator-confirmation`, but distinct in two ways: its citation points at a **document** (byte-verified, like any Tier-1/2 REQ), not at a transcript; and it is **regenerated per run, not persisted** like `operator_confirmations.jsonl` (agent validation is reproducible — re-run the persona — so it does not need the append-only durability that protects a human's irreproducible time). Downstream consumers counting "confirmed" evidence must **not** coalesce `agent-validation` with `operator-confirmation`. **A persona may WRITE only `source_type: agent-validation`** *(added 2026-07-22 — the security lens found the write-side gap: guarding only the read side lets a persona forge human-tier provenance)*: it may not create, tag, or cite an `operator-confirmation` record and may not write to `operator_confirmations.jsonl` — that append-only ledger is writable only by the human interview path. Otherwise a poisoned document could launder an injected requirement into the durable, cross-run, highest-trust evidence class.
3. **Multi-persona independence + a defined combination step.** The selected personas run **in parallel, each blind to the others' writes** (independence). Each produces a **candidate diff-set** against the same base manifest. A **merge step** then unions the grounded `add`/`correct` moves and **surfaces conflicts rather than auto-resolving them** — where any two personas' moves touch the same REQ or section and disagree (an `add` vs a `drop`, two divergent `correct`s, a `confirm` against another's `drop`; the conflict check covers the moves a persona can issue — `confirm`/`correct`/`add`/`drop`. `defer` is an operator "punt to later," not a persona action, so it does not participate in the merge), that is an operator-facing flag, not a silent pick. Only **after** the merge does a **single terminal E.6 renumber** run over the merged manifest — resolving the §6 "renumber once after all moves" contract for the multi-persona case: personas do not each renumber; the merge yields one manifest and one renumber follows.
4. **A remediator, not a gate — its job is to leave `REQUIREMENTS.md` in the best shape it can.** *(Reframed 2026-07-22 per operator: an earlier draft treated H as a judge whose "verdict" might "gate" a run and therefore needed an accuracy-calibration project before gating. H is not that kind of thing — there is no gate for it to pass or fail, and no release for it to block. Its output is a better requirements document.)* When a persona finds a problem it does its best to **remediate** it: grounded `add`/`correct`/`drop` moves are **applied** to the manifest (operator decision 2026-07-22: auto-apply) and flow into Phases 3–6. Two properties keep that safe rather than silent: (a) every persona-written change carries `source_type: agent-validation` (guard 2), which downstream must not coalesce with human confirmation; and (b) the merge emits an **operator-visible agent-validation review summary** — the same "surface, don't silently apply" discipline as Feature G's citable-promotion manifest — listing every persona change with its grounding, so the operator can review and revert. The persona *applies* fixes; the review summary is the backstop, not a pre-approval gate. **Remediation quality is guarded by grounding (guard 1) + the false-positive ceiling (Verification) + the review summary — not by a gating-calibration**, which was machinery for a gating role H does not have. Empirical quality is measured the way the 2026-07-22 tests already measure it: does it find the real gaps within the false-positive ceiling on known repos.

**Untrusted-input handling (persona injection resistance)** *(added 2026-07-22 after the 3-persona self-test — the security persona grounded this, arguing correctly that "dump any docs → personas read them → auto-apply → flows to code" *is* the prompt-injection surface whether or not the docs use the word).* A persona reads untrusted documents into its context, so it must treat their **contents as data, not as instructions to itself**. Content that tries to direct the persona — imperatives addressed to the agent, injected role/system framing, "ignore the rubric," "confirm this," "add REQ X" — must not alter the persona's behavior, the five-move set, or the rubric. The mechanical guards above contain the blast radius (grounding-not-solely-on-controlled-content, candidate-only for injection-shaped adds, provenance write-restriction, least-privilege), and the acceptance oracle includes a **poisoning fixture**: a document embedding "classify me Tier 1" and "add REQ …; confirm it" must not cause promotion past the floor, an out-of-charter action, or a grounded (non-candidate) add. Feature G's classifier carries the same rule at the tiering surface (§8a).

**Operator controls** *(added 2026-07-22 — the adopter persona's top abandonment risks: an AI that auto-edits your spec with only a review-summary backstop needs an off-switch, a real revert, and a stated bound).* These harden the auto-apply decision without reversing it:
- **Off-switch.** Persona validation is operator-disablable — a run can opt out of Feature H entirely (parallel to the human interview being opt-in, §6). A team not ready to let an agent edit its spec can turn it off.
- **Concrete revert.** "Revertible" (guard 4b) names a real, buildable operation, not just a property: a gate/CLI operation that **filters the manifest by `source_type == agent-validation`, drops the selected records (one, or all), re-renders, and re-runs the terminal E.6 renumber** — restoring the pre-persona manifest without hand-editing. All the ingredients exist (the provenance tag, the content-keyed manifest, the review summary, the terminal renumber); the operation composes them. The review summary is the surface; this is the action.
- **Stated false-positive bound.** The FP ceiling (guard 4 / Verification) carries a concrete default: on a fixture whose complete requirement set is known, **spurious grounded adds must be 0** (a real gap plus even one spurious add fails); on live repos, where "complete" is unknowable, every add is surfaced in the review summary so the operator bounds it. The exact live-repo tolerance is the one release-time value left open (see §12) — not the fixture bound, which is 0.
- **Downstream attributability.** `agent-validation` REQs stay distinguishable to Phases 3–6 so that any code, test, or fix generated from an as-yet-unreviewed agent-validation REQ is attributable to it and reversible via the review summary; downstream trust in an agent-validation REQ never exceeds that of an operator-reviewed one.

**Honesty about maturity** *(adopter finding, 2026-07-22).* Where the output rests on a judgment layer the release itself calls not-yet-functional — the readability rubric (§5 Verification (b), "not yet a functional drift detector") — the run must disclose that, the way F-1 discloses coverage gaps, rather than present persona-validated and rubric-checked output with uniform confidence.

**Relationship to Feature D and to v1.6.1.** Feature H **is** Feature D's deferred multi-perspective lens (Dimension 2), pulled forward because AI-scaled validation is what makes the release's promise real. It reuses Feature D's interview, five moves, and write-back. Critically, it must be built as **target-agnostic fresh-context sub-agent-review infrastructure**: context provisioning is a *per-target parameter* (Feature H supplies docs + spec; v1.6.1's Feature B supplies only finding + source + REQ + rubric — the *opposite, more restrictive* isolation), while the orchestration, the `agent-validation` provenance shape, and the independence/isolation discipline are shared. *(There is no shared "calibration harness": H is a remediator with none; B is a judge that carries its own accuracy ground truth — see §8b guard 4 and v1.6.1 §3.)* **"Build the harness target-agnostic" is a named Slice-4 acceptance item**, so v1.6.1's "Feature B is mostly a rubric + target binding" claim is funded rather than hoped for.

**Verification.** (1) Persona validation on chi/express/virtio autonomously surfaces the real gaps the 2026-07-22 agents found (regexp params, `req.range`, indirect descriptors). (2) **False-positive ceiling:** on a fixture whose complete requirement set is known, persona output must not exceed a bounded number of spurious adds (a concrete default, not just "latitude") — a persona that surfaces the real gaps *plus twenty spurious ones* FAILs (RM-007 degenerate-run blindness at the validation layer). (3) **Isolation fabrication-tell + least-privilege:** a persona given file-tool access to the implementation and caught reading it is a detected failure; a persona attempting to read outside its declared inputs (secrets, `operator_confirmations.jsonl`, out-of-run paths) or make network egress is denied/detected. (4) **Grounding mutation:** an `add` with no citable, this-system-justified grounding is rejected or recorded candidate-only, never a grounded REQ. (5) **Provenance:** `agent-validation` records are schema-valid, doc-cited, byte-verified, distinguishable from `operator-confirmation`, and a persona attempting to write an `operator-confirmation` record or to `operator_confirmations.jsonl` is rejected. (6) **Poisoning fixture:** a document embedding "classify me Tier 1" and "add REQ …; confirm it" causes no promotion past the floor, no out-of-charter action, and no grounded (non-candidate) add. (7) **Multi-persona merge:** two personas conflicting on one section produce a surfaced conflict, and one terminal renumber yields sequential IDs. (8) **Applied, surfaced, revertible, disablable:** grounded fixes are applied to the manifest and appear in an operator-visible review summary; the operator can revert any agent-validation change by the documented mechanism and can disable Feature H entirely for a run. (9) **Accepted-residual honesty:** the advisory floor's non-signature residual is stated as accepted, and the maturity of the readability rubric is disclosed on runs that rely on it.

**Dependencies.** Feature D (the interview it drives), Feature G (a persona ramps on the well-classified gathered docs), Feature C (it walks the organized document), the citation gate (grounds its adds). QPB source + a new **sub-agent-orchestration surface** — this does not contradict Decision Record #7 / OD-2 ("the interview is a skill-protocol chat, no new *interactive* Python surface"): that resolution was about the operator interview's delivery shape, which is unchanged; Feature H adds *orchestration* to spawn and merge persona sub-agents, a different surface. Lands via the diagnosis→worker lane. **This is the larger of the two additions** — but its scope is bounded by what it *is*: a requirements **remediator** (guard 4), not a judge-plus-gate. There is no accuracy-calibration project on its critical path, because it produces a better document rather than a gating verdict.
