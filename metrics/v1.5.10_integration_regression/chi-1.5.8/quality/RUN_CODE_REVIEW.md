# Code Review Protocol: go-chi/chi v1.5.8

> Generated by [Quality Playbook](https://github.com/andrewstellman/quality-playbook) v1.5.3 — Andrew Stellman
> Date: 2026-06-19 · Project: go-chi/chi v1.5.8

This protocol runs a three-pass review. **Each pass is mandatory** and runs in a fresh
session whose only shared context is `quality/REQUIREMENTS.md`. A pass that finds nothing
must explain what was checked — an unexplained empty pass is treated as a pass that did not run.

## Bootstrap (Read First)

Read, in order: `quality/QUALITY.md`, `quality/REQUIREMENTS.md`, `quality/CONTRACTS.md`,
`quality/EXPLORATION.md` (architecture map + candidate bugs). Then review the source:
`mux.go`, `tree.go`, `context.go`, `chain.go`, `chi.go`, and the middleware named in the REQs
(`middleware/compress.go`, `realip.go`, `content_charset.go`, `supress_notfound.go`,
`page_route.go`, `path_rewrite.go`, plus the reference cohort `strip.go`, `get_head.go`,
`url_format.go`).

**Requirements-density note (artifact dependency rule).** REQUIREMENTS.md carries 8 behavioral
REQs (REQ-001..008) plus 8 artifact-location REQs across ~6 core files — roughly 1.3 behavioral
REQs per core module. This is adequate for the FULL-pattern seams but thin for the ~30
out-of-scope middleware; Pass 2 below is scoped to the behavioral REQs and notes where a
module has no requirement coverage.

Write each pass's output to `quality/code_reviews/YYYY-MM-DD-pass1.md`, `-pass2.md`, `-pass3.md`
(or one combined `YYYY-MM-DD-code-review.md` with the three passes as sections). Each confirmed
BUG must carry a `REGRESSION TEST:` line or an `EXEMPTION:` line.

## Pass 1: Structural Review

Read the code and flag anomalies from your own knowledge of correctness. No requirements lens.

### Guardrails
- **Line numbers mandatory** — no line number, no finding.
- Read function bodies, not just signatures.
- If unsure: flag as **QUESTION**, not BUG.
- **Grep before claiming missing.**
- Do NOT suggest style or refactor changes — only flag things that are incorrect.

### Output format
```
#### filename.go
- **Line NNN:** [BUG / QUESTION / INCOMPLETE] Description. Expected vs. actual. Why it matters.
```

### Mandatory Pass 1 scrutiny areas (address each explicitly)

1. **Input validation and boundary handling.** Every trust boundary where caller/external
   data enters: `Accept-Encoding` parsing (`compress.go:212-246`), `X-Forwarded-For` cut
   (`realip.go:50`), `Content-Type`/charset split (`content_charset.go:29-45`, `content_type.go`),
   pattern parsing (`tree.go:patNextSegment`). For each parser ask: does it reject input that
   shares a valid prefix/substring with a valid token but contains extra characters?
   (`matchAcceptEncoding` does NOT — it substring-matches.)

2. **Resource lifecycle.** chi pools routing `Context` objects (`context.go`) and compression
   encoders (`compress.go` `sync.Pool`). Check the encoder pool Get/Put pairing in
   `selectEncoder` (`compress.go:218-232`) and the `Context` recycle path. Every acquired
   pooled object must be returned on every exit path.

3. **Concurrency and state management.** chi mutates the shared method maps via
   `RegisterMethod` (`tree.go:61-77`) — is this safe relative to concurrent routing? The
   live-context-mutation hazard: `Match`/`Find` mutate the passed `*Context` (`mux.go:353-368`),
   and `SupressNotFound` passes the LIVE `rctx` (`supress_notfound.go:19`). Flag any probe
   that writes into a context the real walk then reads.

4. **Unit and encoding correctness.** The `q`-value in Accept-Encoding has defined semantics
   (`q=0` = reject); the code never reads it. Charset parameter quoting (RFC 2046) is defined;
   the code never strips quotes. Flag fields with defined units/grammar consumed without parsing.

5. **Enumeration and whitelist completeness (mechanical check required).** For the HTTP-method
   bitmask trio (`tree.go:32-57`):
   - **List A (code extraction):** Use the authoritative mechanical artifact —
     `quality/mechanical/methodMap_cases.txt` (do NOT re-extract by hand; it exists).
     Cross-check against `reverseMethodMap_cases.txt` and `mALL_cases.txt`.
   - **List B (spec extraction):** the `net/http.Method*` constants the maps mirror
     (`tree.go:36-44`): Connect, Delete, Get, Head, Options, Patch, Post, Put, Trace.
   - **Diff:** For each constant, mark FOUND (line NNN) or NOT IN CODE. The mechanical receipt
     already proves all three structures enumerate the identical 9-method set — cite
     `quality/mechanical/verify_receipt.txt` rather than re-asserting from memory.

   Apply the same two-list check to `defaultCompressibleContentTypes` (`compress.go:16-27`)
   vs the set of content types a router commonly serves (note silently-missing types like
   `application/ld+json`, `text/csv` — REQ-006).

   **Do not assert a whitelist "covers all values" without the two-list comparison.**

These five areas must appear as labeled subsections. chi has limited concurrency surface
beyond `RegisterMethod` and pooling — say so explicitly rather than omitting area 3.

## Pass 2: Requirement Verification

For each behavioral requirement (REQ-001..REQ-008), determine SATISFIED / VIOLATED /
PARTIALLY SATISFIED / NOT ASSESSABLE. **Cite at least one file:line per requirement.** No
requirement ranges — each REQ gets its own verdict and evidence.

### Output format
```
#### REQ-NNN: [requirement text]
**Status**: SATISFIED | VIOLATED | PARTIALLY SATISFIED | NOT ASSESSABLE
**Evidence**: [file:line] — [code quote]
**Analysis**: why the code does / does not satisfy the conditions of satisfaction
[If VIOLATED] **Severity**: HIGH | MEDIUM | LOW
```

**Enumeration claims require mechanical proof.** REQ-003 and REQ-006 are whitelist REQs — use
the `quality/mechanical/*_cases.txt` receipts as the code-side list. Do NOT reuse the list
from REQUIREMENTS.md or CONTRACTS.md as if it were extracted from code.

Expected outcomes from Phase 1 (the reviewer confirms or refutes these — do not take them as
given): REQ-001 likely VIOLATED at `supress_notfound.go:19` / `page_route.go:13` /
`path_rewrite.go:11-12`; REQ-002 likely VIOLATED at `compress.go:240-246`, `realip.go:50`,
`content_charset.go:29-45`; REQ-004 likely VIOLATED at `mux.go:383` (missing URLParam reset);
REQ-005 likely VIOLATED at `context.go:136-144`; REQ-003 likely SATISFIED (mechanical receipt).

## Pass 3: Cross-Requirement Consistency

Compare pairs of requirements that reference the same field/constant/policy and verify their
constraints agree.

### Output format
```
#### Shared Concept: [name]
**Requirements**: REQ-X, REQ-Y
**What REQ-X claims** / **What REQ-Y claims**
**Consistency**: CONSISTENT | INCONSISTENT
**Code evidence**: [file:line]
**Analysis**: ...
[If INCONSISTENT] **Impact**: ...
```

Mandatory pairs for chi:
- **REQ-002 ↔ REQ-007** (Accept-Encoding parsing ↔ Content-Encoding declaration): a false-accept
  in `matchAcceptEncoding` propagates to a wrong `Content-Encoding` header in `WriteHeader`. Are
  the two requirements' constraints mutually reinforcing? (They should be: fixing REQ-002 closes
  REQ-007's surface.)
- **REQ-001 ↔ REQ-004** (canonical path in middleware ↔ canonical path in Find/Match): both turn
  on `rctx.RoutePath` being the single source of truth under Mount. Do they agree on which
  representation is canonical?
- **REQ-003 ↔ REQ-006** (two whitelist REQs): do both rely on a single closed-set source of truth?

### Closure mandate
Every confirmed BUG → an executable regression test in `quality/test_regression*.go` (a real
Go test file, not Markdown) asserting the **desired correct** behavior under a skip guard:
`t.Skip("BUG-NNN: <desc> — unskip after applying quality/patches/BUG-NNN-fix.patch")` as the
first line of the test body (Go's earliest-syntactic guard; note Go `t.Skip` reports SKIP, not
FAIL — a known weaker-evidence limitation). The red phase still runs by removing the guard.
Each BUG row in the summary must carry a `REGRESSION TEST:` line or an `EXEMPTION:` line.
Sidecar results use `schema_version: "1.1"`; per-bug writeups at `quality/writeups/BUG-NNN.md`.

### Self-check (5 items)
1. Does every confirmed BUG have a regression test function? (count BUGs vs test functions)
2. Does every BUG row carry `REGRESSION TEST:` or `EXEMPTION:`?
3. Do all enumeration claims cite `quality/mechanical/*_cases.txt`, not a copied list?
4. Did all three passes run, each with explained findings (or explained emptiness)?
5. Do all VIOLATED verdicts cite a specific file:line with a code quote?
