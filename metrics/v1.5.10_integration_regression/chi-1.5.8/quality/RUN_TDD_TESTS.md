# TDD Verification Protocol: go-chi/chi v1.5.8

> Generated by [Quality Playbook](https://github.com/andrewstellman/quality-playbook) v1.5.3 — Andrew Stellman
> Date: 2026-06-19 · Project: go-chi/chi v1.5.8

This protocol runs the red-green TDD cycle for each confirmed bug: the regression test FAILS
on unpatched code (red), then PASSES after the fix patch is applied (green). It runs AFTER the
code review (`RUN_CODE_REVIEW.md`) and spec audit (`RUN_SPEC_AUDIT.md`) confirm bugs and emit
fix patches. The claim it produces — "here is a test that fails without the patch and passes
with it" — is stronger than "we found a bug."

## Framework adaptation

chi is a Go project with an established `testing`-package suite (~90 `func Test*` across 21
`_test.go` files). Write regression tests in Go, in the package matching the code under test:
- Core router internals (`mux`, `tree`, `context`) → `package chi`, file `regression_chi_test.go`.
- Middleware → `package middleware`, file `middleware/regression_test.go`.

Use the project's native runner. Probe it first (`go version`) and capture stdout+stderr+exit
to `quality/results/phase5_env.log`. If the probe SUCCEEDS, you MUST actually run the tests —
a `RED`/`GREEN` first-line tag asserts real execution; a by-inspection prediction under a
`RED`/`GREEN` tag FAILs the gate. Run online (plain `go test`); chi has no third-party deps so
it also runs offline, but do not pass `-mod=vendor`/offline flags by default.

### Skip guard (Go limitation noted)
Each regression test's first body line:
```go
t.Skip("BUG-NNN: <desc> — unskip after applying quality/patches/BUG-NNN-fix.patch")
```
Go's `t.Skip` reports SKIP (not FAIL), weaker evidence than Python's xfail — this is a Go
test-primitive limitation. The red/green cycle below temporarily removes the guard to execute.
Source-inspection regression tests (e.g. asserting `strings.TrimSpace` appears in `realIP`)
must EXECUTE — never `run=false`/inert.

## Spec-grounded test requirements

For each confirmed BUG, read its **spec basis** from `quality/BUGS.md` and write assertions
using the spec's language. Each test carries a comment block citing: the REQ id, the BUG id,
and the spec passage (RFC name + section + ≤15-word quote). Example for the Accept-Encoding bug:
```go
// REQ-002 · BUG-NNN · RFC 7231 §5.3.4: "a qvalue of 0 means 'not acceptable'"
// Desired: Accept-Encoding "gzip;q=0" must NOT select the gzip encoder.
```

## Red-green execution steps

For every confirmed BUG with a fix patch (adapt the `-run` selector per package):

```bash
# ── Probe the runner (required when confirmed bugs exist) ──
go version > quality/results/phase5_env.log 2>&1; echo "exit=$?" >> quality/results/phase5_env.log

# ── Red phase: revert fix, run test, expect FAIL ──
git apply -R quality/patches/BUG-NNN-fix.patch 2>/dev/null || true
TEST_CMD="go test -v -run TestBugNNN ./..."   # or ./middleware for middleware bugs
OUTPUT=$($TEST_CMD 2>&1); EXIT=$?
printf 'RED\n--- Test output for BUG-NNN red phase ---\nCommand: %s\nExit code: %d\n%s\n' \
  "$TEST_CMD" "$EXIT" "$OUTPUT" > quality/results/BUG-NNN.red.log

# ── Green phase: apply fix, run test, expect PASS ──
git apply quality/patches/BUG-NNN-fix.patch
OUTPUT=$($TEST_CMD 2>&1); EXIT=$?
printf 'GREEN\n--- Test output for BUG-NNN green phase ---\nCommand: %s\nExit code: %d\n%s\n' \
  "$TEST_CMD" "$EXIT" "$OUTPUT" > quality/results/BUG-NNN.green.log
```

The red phase is **mandatory for every confirmed bug** even without a fix patch (record
`green_phase: "skipped"`, `red_phase: "fail"`). Each `BUG-NNN.red.log` first line is a
machine-readable status tag: `RED` / `GREEN` / `NOT_RUN` / `ERROR`. `NOT_RUN` is permitted
ONLY if the `go version` probe itself exited non-zero (quote that output).

## JUnit XML (optional)

If `gotestsum` is available: `gotestsum --junitxml quality/results/tdd-red-BUG-NNN.xml --
-run TestBugNNN ./...`. Otherwise set `"junit_available": false` — do not fail the run over
missing XML tooling.

## Sidecar JSON (strict schema — copy verbatim, fill values)

Write `quality/results/tdd-results.json`:
```json
{
  "schema_version": "1.1",
  "skill_version": "1.5.8",
  "date": "2026-06-19",
  "project": "go-chi/chi v1.5.8",
  "bugs": [
    {
      "id": "BUG-001",
      "requirement": "REQ-002",
      "red_phase": "fail",
      "green_phase": "pass",
      "verdict": "TDD verified",
      "regression_patch": "quality/patches/BUG-001-regression-test.patch",
      "fix_patch": "quality/patches/BUG-001-fix.patch",
      "fix_patch_present": true,
      "patch_gate_passed": true,
      "writeup_path": "quality/writeups/BUG-001.md",
      "junit_red": "tdd-red-BUG-001.xml",
      "junit_green": "tdd-green-BUG-001.xml",
      "junit_available": false,
      "notes": ""
    }
  ],
  "summary": { "total": 0, "verified": 0, "confirmed_open": 0, "red_failed": 0, "green_failed": 0 }
}
```
**Required top-level:** `schema_version`, `skill_version`, `date`, `project`, `bugs`, `summary`.
**Required per-bug:** `id`, `requirement`, `red_phase`, `green_phase`, `verdict`,
`fix_patch_present`, `writeup_path`. **Required summary keys:** `total`, `verified`,
`confirmed_open`, `red_failed`, `green_failed` (all five).
Valid `verdict`: `TDD verified` / `red failed` / `green failed` / `confirmed open` / `deferred`
(never `skipped`). Valid `red_phase`/`green_phase`: `fail` / `pass` / `error` / `skipped`
(red never skipped). Patch names: `BUG-NNN-regression-test.patch`, `BUG-NNN-fix.patch` exactly.
Use the real session date; no placeholder/future dates.

**Post-write validation:** reopen the file; confirm all required fields, legal enum values,
and no extra root keys.

## Traceability table

Produce `quality/TDD_TRACEABILITY.md`:

| Bug ID | Requirement ID | Spec Doc | Spec Section | Behavioral Contract | Test File:Function | Red Result | Green Result |
|--------|---------------|----------|-------------|--------------------|--------------------|------------|--------------|

Every row fully populated. A bug whose spec doc is an RFC (not a repo file) is still a spec
violation; a bug grounded only in chi's own comments is a code inconsistency — note which.

## Bug writeup generation (every confirmed bug)

After each red→green cycle (or confirmed-open), write `quality/writeups/BUG-NNN.md` using the
numbered template (1 Summary, 2 Spec reference, 3 The code, 4 Observable consequence,
5 Depth judgment *(when warranted)*, 6 The fix *(always an inline ```diff block — gate-enforced)*,
7 The test, 8 Related issues *(when applicable)*). Include the version stamp at the top. A
writeup without a ` ```diff ` block FAILs the gate — paste the actual diff inline, never
"see patch file."

## Execution UX
1. Show the plan: a numbered table of bugs to verify.
2. One-line progress per red-green cycle: `FAIL ✓ → PASS ✓` or `FAIL ✗ — passes unpatched, rewriting`.
3. Summary table: verified / confirmed-open / rewritten counts.

## TDD artifact closure gate
If `quality/BUGS.md` has any confirmed bug, `quality/results/tdd-results.json` is mandatory; if
any bug has a red-phase result, `quality/TDD_TRACEABILITY.md` is mandatory; every confirmed bug
needs a `quality/results/BUG-NNN.red.log`. A zero-bug run may omit all three.
