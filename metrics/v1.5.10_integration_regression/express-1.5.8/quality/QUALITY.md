# Quality Constitution: Express v5.2.1

> Generated by [Quality Playbook](https://github.com/andrewstellman/quality-playbook) v1.5.8 — Andrew Stellman
> Date: 2026-06-19 · Project: Express (v5.2.1)

## Purpose

Express is the request handler that sits between untrusted HTTP input and an application's
business logic. "Quality" for Express is not "the 70 mocha files pass" — it is **the
framework deriving correct, consistent values from hostile input and shaping responses that
say exactly what the application meant**.

- **Deming — quality is built in, not inspected.** The bar for Express lives in this
  constitution and the requirements, so every future session inherits the same definition of
  "correct" before touching `lib/response.js` or `lib/request.js`. The most fragile code
  (`res.send` charset handling, `X-Forwarded-*` parsing) is re-derived from untrusted bytes
  on every request; the invariants must be written down, not rediscovered.
- **Juran — fitness for use.** Fitness for Express means: a request behind a trusted proxy
  resolves the *real* scheme and host; a response advertises the *intended* charset
  regardless of whether the body is a `String` or a `Buffer`; a redirect to any accepted
  status code produces a human-readable body, never the literal text `undefined`; a cookie
  set with a short `maxAge` actually lives that long. Not "200 OK" — the *right* headers and
  body.
- **Crosby — quality is free.** A two-line `setCharset` asymmetry or a missing
  `statuses.message` fallback costs nothing to specify now and a production incident
  (silently-downgraded `req.secure`, instantly-dropped cookies, `undefined` in a redirect
  page) to discover later. Writing the invariant down is cheaper than the incident.

**Environment note (this run).** `node_modules` is absent from the audited checkout — Express's
own runtime deps (`router`, `finalhandler`, `send`, `accepts`, …) and the test deps
(`mocha`, `supertest`) are not installed. The functional tests in `quality/test_functional.js`
are written in the canonical Express idiom (`require('..')` + `supertest`) so they run once
`npm install` populates `node_modules`. Phase 5 TDD/integration execution depends on that
install; the protocols below probe for it before claiming a runner is unavailable.

## Coverage Theater Prevention

A test for Express is **theater** if it does any of the following — these are the patterns
seen in AI-padded HTTP-framework suites:

- **Asserting status only.** `request(app).get('/').expect(200)` with no body/header
  assertion. For Express the *header and body shape* is the contract — a redirect can be
  `302` and still carry `undefined` in its body (REQ-003).
- **Asserting a header exists without its value.** `expect('Content-Type', /text/)` passes
  for both `charset=utf-8` and `charset=iso-8859-1` — the exact charset is the entire point
  of REQ-006. Assert the *full* header value.
- **Testing only the happy `X-Forwarded-*` value.** A test that sends `X-Forwarded-Proto:
  https` and asserts `req.secure === true` proves nothing about the empty/leading-comma
  cases (`""`, `", https"`) that REQ-001 actually targets. Edge inputs are the requirement.
- **Asserting `typeof res.send === 'function'`** or that an app object has a `.use` method —
  surface-existence checks that never exercise behavior.
- **Mock-echo.** Stubbing `statuses.message` or `mime.contentType` to return a value and
  asserting the stub returned it. Use the real dependencies; the bug lives in how Express
  *uses* them.
- **Single-variant cross-cutting tests.** Testing charset on a string body but never on a
  Buffer body — the asymmetry between the two IS the bug (REQ-006).

## Fitness-to-Purpose Scenarios

Each scenario maps 1:1 to a test in `quality/test_functional.js` (matching name) and to a
REQ. Every "How to verify" is a concrete supertest assertion.

### Scenario 1: The silently-downgraded secure request

**Requirement tag:** [Req: inferred — REQ-001, code-is-the-spec]

**What happened:** `req.protocol` (`lib/request.js:309-314`) *always* comma-splits the
`X-Forwarded-Proto` value: `index = header.indexOf(',')` then `header.substring(0,
index).trim()`. A trusted proxy that concatenates an empty element — sending
`X-Forwarded-Proto: ", https"` — makes `index = 1`, so the getter returns
`substring(0,1).trim()` = `''`. `req.secure` (`:326-328`) then evaluates `'' === 'https'` →
`false`. An HTTPS request is reported as insecure. HTTPS-only middleware
(`if (!req.secure) res.redirect(...)`) now redirect-loops or 403s a legitimately-secure
client — a self-inflicted outage triggered by a single stray comma in a proxy config.

**The requirement:** For every trusted `X-Forwarded-Proto` value in `{"", ",", ", https",
"https,", "http, https"}`, `req.protocol` must be a non-empty member of `{http, https}` and
`req.secure` must reflect the real scheme.

**How to verify:** `test_scenario_1_xforwarded_proto_empty_element` — `app.set('trust proxy',
true)`, send each header value, assert `req.protocol` is non-empty and `req.secure` matches.

### Scenario 2: The cookie that expires the instant it is set

**Requirement tag:** [Req: inferred — REQ-002, code-is-the-spec]

**What happened:** `res.cookie` (`lib/response.js:759-766`) sets `opts.expires = new
Date(Date.now() + maxAge)` (ms-accurate) but `opts.maxAge = Math.floor(maxAge / 1000)`
(seconds). For any `maxAge < 1000` (a 250ms flash cookie, a 500ms CSRF nonce), `Max-Age`
floors to `0`. Per RFC 6265 §5.2.2 a `Max-Age=0` directive expires the cookie *immediately*,
and UAs that prefer `Max-Age` over `Expires` drop it on receipt — even though `Expires` is
~500ms in the future. The author clearly knows the two directives interact:
`res.clearCookie` (`:709-716`) deliberately *deletes* `maxAge` to avoid exactly this
collision.

**The requirement:** A sub-second `maxAge` must not serialize `Max-Age=0` alongside a future
`Expires`. `res.clearCookie` remains the only path that sets an immediate expiry.

**How to verify:** `test_scenario_2_subsecond_maxage_not_zero` — `res.cookie('x','1',
{maxAge:500})`, assert the `Set-Cookie` header does not contain `Max-Age=0`.

### Scenario 3: `undefined` printed in a redirect page

**Requirement tag:** [Req: inferred — REQ-003, code-is-the-spec]

**What happened:** `res.redirect` accepts any number as the status (`response.js:818-821`) and
builds the body from `statuses.message[status]` (`:841`, `:846-847`) with no fallback. For an
unassigned 3xx (`res.redirect(310, '/x')` — 310 is unassigned), `statuses.message[310]` is
`undefined`, so the text body becomes `"undefined. Redirecting to /x"` and the HTML body
`<title>undefined</title>`. `res.status(310)` (`:856`) passes the 100–999 range guard
(`:70`), so nothing rejects it. The end user sees the literal word `undefined` in their
browser.

**The requirement:** For a status with no `statuses.message` entry, the redirect body and
HTML `<title>` must not contain the literal string `undefined`.

**How to verify:** `test_scenario_3_redirect_unknown_status_no_undefined` — `res.redirect(310,
'/x')`, assert the body does not contain `undefined`.

### Scenario 4: Member-access chains reflected into an executable body

**Requirement tag:** [Req: inferred — REQ-004, code-is-the-spec]

**What happened:** `res.jsonp` filters the callback with `callback.replace(/[^\[\]\w$.]/g,
'')` (`response.js:286`), then reflects it into a `text/javascript` body (`:283`, `:300`).
The whitelist intentionally allows `[`, `]`, `$`, `.` to support `?callback=foo.bar` and
`?callback=ns['fn']`. As a result `a.constructor.constructor` survives the filter unchanged
and is reflected into the response. The `/**/` prefix + `typeof … === 'function'` guard
(`:298-300`) blocks *execution* of non-functions, but the whitelist is broader than a
bare-identifier check — the response still echoes attacker-influenced property chains into an
executable content type.

**The requirement:** Only callback strings matching the intended grammar reach the body;
member-access chains are either rejected or proven safe by the guard. `X-Content-Type-Options:
nosniff` is always set on jsonp responses (`response.js:271,282`).

**How to verify:** `test_scenario_4_jsonp_callback_whitelist` — request
`?callback=alert(1)//` (filters to `alert1`) and `?callback=a.constructor` (survives), assert
the `nosniff` header is present and inspect what reaches the body.

### Scenario 5: The same route advertising two different charsets

**Requirement tag:** [Req: inferred — REQ-006 (Pattern: parity), code-is-the-spec]

**What happened:** For a *string* body, `res.send` reads the existing Content-Type and
rewrites it with `setCharset(type, 'utf-8')` (`response.js:140`), overwriting any caller-set
charset. For a *Buffer* body, the charset is left untouched (`:150-153`). So
`res.set('Content-Type', 'text/plain; charset=iso-8859-1').send('x')` emits `charset=utf-8`,
but the identical handler sending `Buffer.from('x')` emits `charset=iso-8859-1`. The declared
charset depends on the body's JS *type*, not the app's intent — the same logical response
advertises two different charsets. The test suite pins both today
(`test/res.send.js:112-121` vs `:125-134`), confirming the divergence is real and
load-bearing. Separately, `res.set` injects charset via `mime.contentType` while `res.send`
injects via `setCharset` — two code paths reaching the "type has a charset" state
(`History.md:15` records a v5 fix for duplicate processing here).

**The requirement:** Charset handling must be consistent across `res.send` body types and the
`res.set`/`res.type`/`res.json`/`res.jsonp` surfaces, or the divergence must be explicitly
specified per UC-06.a/b/c.

**How to verify:** `test_scenario_5_charset_string_vs_buffer_parity` — set
`text/plain; charset=iso-8859-1`, send `'é'` as a string vs `Buffer.from('é','latin1')`, and
compare the emitted Content-Type headers.

### Scenario 6: `undefined` hostname from a leading-comma forwarded host

**Requirement tag:** [Req: inferred — REQ-007 (Pattern: parity), code-is-the-spec]

**What happened:** `req.host` (`request.js:418-431`) comma-trims XFH only inside the trusted
branch (`else if (val.indexOf(',') !== -1)`) and uses the deprecated `.trimRight()`. A
trusted XFH of `",a.com"` returns `val.substring(0, val.indexOf(',')).trimRight()` = `""`.
`req.hostname` (`:444-458`) then derives from an empty host and returns `undefined`, so
`req.subdomains` (`:383-394`) returns `[]`. Subdomain-based routing / tenant resolution
silently breaks for a present-but-comma-prefixed host. Note this is the *opposite* discipline
from `req.protocol`, which always splits — the two `X-Forwarded-*` getters disagree on how to
parse the same list shape (the cross-implementation asymmetry promoted to REQ-007).

**The requirement:** For trusted XFH values `"a.com"`, `",a.com"`, `"a.com,"`, `"a.com:8080"`,
`"[::1]:8080"`, each of `host`/`hostname`/`subdomains` returns the value implied by the
leading authority, never `undefined` for a syntactically present host.

**How to verify:** `test_scenario_6_xforwarded_host_leading_comma` — `app.set('trust proxy',
true)`, send each XFH value, assert `req.hostname` is not `undefined` when an authority is
present.

### Scenario 7: Quoted media-type parameters split mid-value

**Requirement tag:** [Req: inferred — REQ-005, code-is-the-spec]

**What happened:** `acceptParams` (`utils.js:89-120`) scans for `=` and the bounding `;` with
no quoted-string awareness. RFC 7231 §3.1.1.1 permits quoted parameter values, so a legal
media type `text/html;x="a;b";q=0.5` is split at the inner `;` inside the quotes,
mis-parsing `params.x` and possibly `q`. `q` is parsed with `parseFloat` (`:111`) and never
clamped to `[0,1]`, so `q=5` or `q=-1` flows through unbounded.

**The requirement:** Quoted parameter values containing `;` are not split mid-value; `q` is
parsed and clamped to `[0,1]`; the `splitIndex > endIndex` recovery branch (`utils.js:102-104`)
does not drop valid params.

**How to verify:** `test_scenario_7_acceptparams_quoted_value` — exercise via `req.accepts` /
`res.format` with `Accept: text/html;x="a;b";q=0.5` and inspect the negotiated result.

### Scenario 8: Invalid config that fails at request time instead of boot

**Requirement tag:** [Req: inferred — REQ-008, code-is-the-spec]

**What happened:** `app.set` compiles `etag`/`query parser`/`trust proxy` eagerly via
`compile*` (`utils.js:130-214`), each with a `default: throw new TypeError(...)`. This is the
*good* defensive pattern — an invalid `app.set('etag', 'bogus')` throws at config time, not on
the first request. The scenario locks the invariant in so a future refactor that defers
compilation to request time would regress it.

**The requirement:** Invalid values for `etag`/`query parser`/`trust proxy` throw a
`TypeError` at `app.set` time, not at request time.

**How to verify:** `test_scenario_8_invalid_setting_fails_fast` — `assert.throws(() =>
app.set('etag', {}))` (a value no compiler accepts) at config time.

## AI Session Quality Discipline

1. Read this `QUALITY.md` and `REQUIREMENTS.md` before changing any file under `lib/`.
2. Run the full mocha suite (`npm test`) before marking any task complete; if `node_modules`
   is absent, `npm install` first.
3. Add tests for new behavior — and for every public response/request method, include the
   edge-input case (empty/comma forwarded headers, sub-second `maxAge`, non-standard status),
   not just the happy path.
4. When touching charset or `X-Forwarded-*` parsing, test **both** sides of every parity pair
   (string AND Buffer; protocol AND host) — single-variant tests miss the asymmetry.
5. Never assert a header *exists* without asserting its full value.
6. Update this file when a new failure mode is discovered. Never delete a scenario; only add.
7. Output a Quality Compliance Checklist before ending a session.

## The Human Gate

- Whether the string-vs-Buffer charset asymmetry (REQ-006) is intended v5 behavior or a bug —
  requires a maintainer/changelog judgment (`History.md:15` is the strongest evidence of
  intent). Phase 4 triage, not an automated check, decides disposition.
- Whether the JSONP whitelist (REQ-004) is "safe enough" given the `typeof` guard, or should
  be tightened to a bare-identifier check — a security-vs-compatibility tradeoff.
- Backward-compatibility of any change to `req.protocol`/`req.host` parsing — these are
  observable to every app behind a proxy.
- Security review of any change touching trust-proxy derivation or jsonp callback handling.
