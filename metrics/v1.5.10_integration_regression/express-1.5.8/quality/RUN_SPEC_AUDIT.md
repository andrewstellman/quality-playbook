## Running the Audit

Run all three auditors, then triage. Save each report to
`quality/spec_audits/auditor_{A,B,C}.md`.

## Triage Process

Merge findings by confidence. **Minority-finding rule:** any finding flagged by only one of
three auditors requires re-investigation — read the code location and make an explicit
CONFIRMED / FALSE-POSITIVE call; do not discard by default. Triage **confirms or rejects** —
it does not raise the bar to runtime evidence. A code-path-traced finding is confirmed, not
demoted to "candidate."

**Verification probes must produce executable evidence**, written to
`quality/spec_audits/triage_probes.sh` (an executable file, not prose):

- **Reject** a finding by writing an assertion that **passes**, proving the finding wrong (cite
  the exact line). Example — rejecting "redirect has a fallback":
  ```sh
  # Reject proof would PASS only if a fallback exists:
  grep -nE "statuses\.message\[.*\] *\|\|" lib/response.js   # expect a match if guarded
  ```
- **Confirm** a finding by writing an assertion that **fails** (expected-failure), proving the
  bug. Example — confirming REQ-003:
  ```sh
  # Confirmation: there is NO `|| ...` fallback after statuses.message[status]:
  ! grep -nE "statuses\.message\[status\] *\|\|" lib/response.js   # exits 0 -> bug present
  ```

Every probe assertion cites an exact line and quotes what that line contains. A triage report
that says "the probe confirms…" with no assertion in `triage_probes.sh` is non-conformant.

## Code review vs spec audit conflicts

If the code review and a spec auditor disagree on the same finding, the spec audit is not
automatically correct — deploy a verification probe and record the resolution in the BUG
tracker.

## Output

`quality/spec_audits/triage.md`: a Council Status table (finding · auditors who flagged it ·
probe result · CONFIRMED/REJECTED · severity · REQ · disposition). Confirmed bugs flow into
`quality/bugs_manifest.json` (with `divergence_type` populated: these are `code-spec` when the
intent is a single REQ/`History.md` line) and `quality/BUGS.md`, then into the Phase 5 TDD
cycle.

## The Four Guardrails (all auditors)

1. File:line on every finding — no line, no finding.
2. Read bodies, not signatures.
3. If unsure → QUESTION, not BUG.
4. Grep before claiming "missing."
