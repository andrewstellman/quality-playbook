# Code Review Protocol: Express v5.2.1

> Generated by [Quality Playbook](https://github.com/andrewstellman/quality-playbook) v1.5.8 — Andrew Stellman
> Date: 2026-06-19 · Project: Express (v5.2.1)

## Bootstrap (Read First)

- **Scope:** `lib/` only (`response.js`, `request.js`, `application.js`, `utils.js`,
  `view.js`, `express.js`). Routing/mounting is `router@2.2.0` — out of scope, treated as a
  behavioral boundary; cite the call sites in `lib/`, not router internals.
- **Inputs:** `quality/REQUIREMENTS.md` (REQ-001..016), `quality/CONTRACTS.md` (C-1..C-8),
  `quality/EXPLORATION.md`. Each pass runs in a fresh session sharing only `REQUIREMENTS.md`.
- **Source boundary:** never modify files outside `quality/`. All source changes are expressed
  as `git diff` patches under `quality/patches/`.
- **Output location:** write pass reports under `quality/code_reviews/` (REQ-012).
- **Confirmation standard:** a code-path trace showing a behavioral violation with file:line is
  sufficient to confirm a bug. Do NOT demand runtime evidence before confirming — TDD (Phase 5)
  provides runtime proof AFTER confirmation.

## Pass 1 — Structural Review

Read function bodies (not just signatures) and flag anomalies from the model's own knowledge of
correctness. Guardrails: **line numbers mandatory** (no line, no finding); if unsure, file a
QUESTION not a BUG; grep before claiming "missing"; do NOT suggest style changes.

Address each of these five scrutiny areas as a labeled subsection:

1. **Input validation and boundary handling.** Every trust boundary where caller/external data
   enters: `X-Forwarded-Proto` / `X-Forwarded-Host` parsing (`request.js:309-314`, `:424-427`),
   the jsonp callback filter (`response.js:286`), `acceptParams` (`utils.js:89-120`), redirect
   status acceptance (`response.js:70`, `:818-821`). Check that each parser rejects — or safely
   handles — inputs that share a valid prefix with a valid token (empty list elements, leading
   commas, quoted `;`).
2. **Resource lifecycle.** `res.sendFile`/`sendfile` streaming state machine
   (`response.js:921-1009`): `done`/`streaming` flags, abort/error/finish handlers, the
   `streaming !== false && !done` guard at `:971`. Verify every stream path ends or aborts
   exactly once.
3. **Concurrency and state management.** Express is single-threaded per request; explicit
   document this. The one shared-state concern is `req.ips` mutating `proxyaddr.all`'s array
   in place (`request.js:363`) — latent only because the dependency returns a fresh array.
4. **Unit and encoding correctness.** `res.send` Content-Length: `chunk.length` (UTF-16 code
   units) gates the `< 1000` small-chunk branch while `Buffer.byteLength` supplies the value
   (`response.js:170-177`); `res.cookie` `maxAge` ms→s floor (`:764`); charset injection paths
   (`setCharset` vs `mime.contentType`).
5. **Enumeration and whitelist completeness.** **NOT APPLICABLE — document why.** Express
   `lib/` has no `switch`/`case` over a closed set of named constants (the `compile*` switches
   are over JS setting-name *strings*, not C-style enums; status/MIME sets are owned by the
   `statuses`/`accepts` dependencies). There is no `quality/mechanical/*_cases.txt` witness this
   run. State this explicitly rather than omitting the section. The jsonp whitelist is a
   *character-class regex*, not a constant enumeration — review it under area 1, not here.

Pass 1 catches ~65% of defects. Write findings to `quality/code_reviews/pass1_structural.md`.

## Pass 2 — Requirement Verification

For each REQ-001..008 (the artifact-layout REQ-009..016 are gate-verified, not code-reviewed),
show the code that satisfies it or explain specifically why it does not. **Minimum evidence:
cite ≥1 file:line per REQ.** Each REQ gets its own SATISFIED / VIOLATED verdict — no
unverified ranges, no group of >3 REQs under one citation.

The requirement count (8 behavioral REQs) is healthy for 6 source files (~1.3 behavioral REQ
per module, concentrated on the two highest-risk modules) — Pass 2 should be substantive, not
thin. Probe especially: REQ-001 (`request.js:309-314` — does `", https"` get guarded?),
REQ-002 (`response.js:764` — is the sub-second floor intended?), REQ-003 (`response.js:841` —
is there a `statuses.message` fallback?), REQ-006 (`response.js:137-153` — string vs Buffer),
REQ-007 (`request.js:418-431` — leading-comma XFH).

No enumeration-completeness REQ exists this run, so the two-list mechanical check does not
apply — do not fabricate one. Write findings to `quality/code_reviews/pass2_requirements.md`.

## Pass 3 — Cross-Requirement Consistency

Compare REQ pairs that touch a shared concept:

- **Shared concept: `X-Forwarded-*` list parsing (REQ-001 ↔ REQ-007).** `req.protocol` always
  comma-splits; `req.host` splits only in the trusted branch and uses `.trimRight()` vs
  `.trim()`. Do the two getters agree on how a leading/trailing comma is handled? (They do
  not — this is the documented cross-implementation asymmetry.)
- **Shared concept: charset injection (REQ-006 internal).** `res.set` injects via
  `mime.contentType`; `res.send` injects via `setCharset`. Do they reach the same final header
  for the same input? (`History.md:15` flags this seam.)
- **Shared concept: status-code range guard (REQ-003).** `res.status` (`response.js:70`) and
  `res.redirect` (`:856`) both accept 100–999; does the redirect body logic agree with what the
  status guard admits?

Write findings to `quality/code_reviews/pass3_cross_requirement.md`.

## Combined Summary

Merge passes into a confirmation table (BUG CONFIRMED / FALSE POSITIVE / NEEDS INVESTIGATION).
For each confirmed bug, immediately generate `quality/patches/BUG-NNN-regression-test.patch`
(mandatory) and `quality/patches/BUG-NNN-fix.patch` (strongly encouraged for the small fixes
here — most candidate bugs are one/two-line changes). Run the patch validation gate
(`git apply --check`; for compile, `node --check` the changed `lib/*.js` and `mocha --dry-run`
the regression test). Regression tests go in `quality/test_regression.js` using Mocha
`it.skip("BUG-NNN: …")` guards (the earliest syntactic guard for Mocha) until a fix lands.

**Severity:** uppercase `HIGH`/`MEDIUM`/`LOW` only. Per EXPLORATION risk ranking: the
secure-request downgrade (REQ-001) and the silently-dropped cookie (REQ-002) are HIGH; the
redirect-`undefined` (REQ-003), jsonp whitelist (REQ-004), charset asymmetry (REQ-006), and
empty-XFH hostname (REQ-007) are MEDIUM. Apply the development-scaffolding exclusion before
confirming any security-class finding (none here carry `change-me`-style placeholders).

**Spec basis (per bug):** cite `History.md` lines where they establish v5 intent (e.g.
`History.md:15` for charset, `:63` for status integer-only). Where no doc covers the behavior,
classify as "code inconsistency" rather than "spec violation" and note it.
