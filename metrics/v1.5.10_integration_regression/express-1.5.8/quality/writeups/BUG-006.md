# BUG-006 — leading-comma `X-Forwarded-Host` yields `undefined`/`[]` host getters

- **Severity:** MEDIUM · **divergence_type:** code-spec · **Requirement:** REQ-007 (parity, C-2, UC-07.a/b/c)
- **Covers:** REQ-007/cell-LEADING_COMMA_AUTHORITY-HOST, -HOSTNAME, -SUBDOMAINS
- **Site:** `lib/request.js:424-427` (`host`), `:444-458` (`hostname`), `:383-394` (`subdomains`)

## What's wrong
In the trusted branch:
```js
} else if (val.indexOf(',') !== -1) {
  val = val.substring(0, val.indexOf(',')).trimRight()
}
return val || undefined;
```
For trusted `",a.com"` the first comma is at index 0, so `substring(0,0)` is `''` → `host` is `undefined`. `hostname` (`if (!host) return;`) → `undefined`; `subdomains` (`if (!hostname) return [];`) → `[]`. A syntactically present authority silently disappears.

## Reachability
No guard. The split is reached unconditionally when trust passes and XFH contains a comma, and always takes `substring(0, firstComma)`. No non-empty-authority selection.

## Cross-getter consistency
This is the same leading-empty-element pattern as BUG-001 (`req.protocol`), in a different getter with a different observable failure (undefined hostname vs secure-downgrade) — see `code_reviews/pass3_cross_requirement.md`.

## Fix
`quality/patches/BUG-006-fix.patch` — select the first **non-empty** trimmed authority from the comma-split XFH value. Consolidated fix at `host`; `hostname`/`subdomains` recover as downstream consumers (all three cells).
