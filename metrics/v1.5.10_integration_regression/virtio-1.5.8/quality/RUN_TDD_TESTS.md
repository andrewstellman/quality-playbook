# TDD Verification Protocol: Linux virtio driver subsystem

> Generated by [Quality Playbook](https://github.com/andrewstellman/quality-playbook) v1.5.8 — Andrew Stellman
> Date: 2026-06-19 · Project: linux-virtio (sparse kernel subsystem checkout @ bfe62a454542)

Run AFTER the code review (Phase 3) and spec audit (Phase 4) confirm bugs and produce fix patches.
For each confirmed bug, run the red→green cycle: the regression test fails on unpatched source,
then passes after the fix patch is applied.

## Framework adaptation (this project)

This is **Linux kernel C with NO userspace test harness**. Per SKILL.md File 7, projects without
test infrastructure use **source-inspection tests**: the regression test reads the target source
file and asserts on the presence/absence of the specific code pattern the bug concerns (a case
label, a poll loop, a captured return value). The tests are written in pytest (matching
`quality/test_functional.py`) and run with the project's available runner — `python3 -m pytest`.
Each regression test's header comment includes the extraction command so it is self-documenting.

There is no kernel build, so the patch-validation "compile check" is replaced by `python -m
py_compile` on the regression test and a `git apply --check` of each patch against the source tree.

## Spec-grounded test requirements

For each bug in `quality/BUGS.md`:
- Read the bug's **spec basis** field (the behavioral-contracts.md section it violates).
- Write test assertions using spec language — e.g., for the MMIO reset bug, name the assertion
  after "wait for status read 0" (spec §5), not after the C variable.
- Include a comment block citing: requirement ID (REQUIREMENTS.md), bug ID (BUGS.md), and the spec
  passage (doc name, section, ≤15-word quote).

## Probe the runner FIRST, then red/green

Before any verdict, probe the runner and capture to `quality/results/phase5_env.log`:

```bash
{ python3 --version; python3 -m pytest --version; } > quality/results/phase5_env.log 2>&1
echo "exit=$?" >> quality/results/phase5_env.log
```

If the probe SUCCEEDS (pytest available — it is, on the operator's machine), you MUST actually
execute the regression tests. A `RED`/`GREEN` first-line tag asserts the test was really run; a
by-inspection prediction under a RED/GREEN tag FAILs the gate. Record `NOT_RUN` only if the probe
itself exits non-zero (quote that output).

## Red-green execution (per confirmed BUG-NNN)

```bash
# ── Red phase: ensure fix NOT applied, run test, expect FAIL (XFAIL) ──
git apply -R quality/patches/BUG-NNN-fix.patch 2>/dev/null   # revert if applied
# Temporarily disable the xfail guard so the failure is visible as a real FAIL:
TEST_CMD="python3 -m pytest -xvs quality/test_regression.py::test_bug_nnn --runxfail"
OUTPUT=$($TEST_CMD 2>&1); EXIT=$?
printf 'RED\n--- Test output for BUG-NNN red phase ---\nCommand: %s\nExit code: %d\n%s\n' \
  "$TEST_CMD" "$EXIT" "$OUTPUT" > quality/results/BUG-NNN.red.log

# ── Green phase: apply fix, run test, expect PASS ──
git apply quality/patches/BUG-NNN-fix.patch
OUTPUT=$($TEST_CMD 2>&1); EXIT=$?
printf 'GREEN\n--- Test output for BUG-NNN green phase ---\nCommand: %s\nExit code: %d\n%s\n' \
  "$TEST_CMD" "$EXIT" "$OUTPUT" > quality/results/BUG-NNN.green.log
git apply -R quality/patches/BUG-NNN-fix.patch   # restore clean tree
```

The fix patches modify `drivers/virtio/*.c`. To honor the source-boundary rule, apply/revert in a
disposable worktree (`git worktree add /tmp/qpb-virtio-tdd HEAD`) and run the red/green there, then
`git worktree remove --force`.

Each `BUG-NNN.red.log` / `BUG-NNN.green.log` first line is a machine-readable status tag: `RED` /
`GREEN` / `NOT_RUN` / `ERROR`.

Required top-level: `schema_version`, `skill_version`, `date`, `project`, `bugs`, `summary`.
Required per-bug: `id`, `requirement`, `red_phase`, `green_phase`, `verdict`, `fix_patch_present`,
`writeup_path`. Required summary keys (all five): `total`, `verified`, `confirmed_open`,
`red_failed`, `green_failed`. Valid `verdict`: `TDD verified` / `red failed` / `green failed` /
`confirmed open` / `deferred`. A `confirmed open` bug must have `red_phase: "fail"` and
`green_phase: "skipped"`. Do NOT use `"skipped"` as a verdict.

**If TDD genuinely cannot execute** (no worktree, no pytest), write tdd-results.json with
`verdict: "deferred"` and `notes` explaining why — never omit the file when confirmed bugs exist.

**Post-write validation:** reopen tdd-results.json; verify all required fields, legal enum values,
no extra root keys.

## Bug writeups (every confirmed bug)

After each red(→green) cycle, write `quality/writeups/BUG-NNN.md` (sections 1–4, 6, 7 required; 5
when depth is warranted; 8 when related bugs exist). Section 6 ("The fix") MUST contain an inline
```diff block — the gate FAILs a writeup without one. For the virtio bugs, the diffs are small
(add a case label or a re-add line, add a poll loop, capture a return value). Example shape for the
RING_RESET-on-MMIO bug:

```diff
--- a/drivers/virtio/virtio_mmio.c
+++ b/drivers/virtio/virtio_mmio.c
@@ vm_finalize_features @@
 	vring_transport_features(vdev);
+	/* Re-preserve transport bits the whitelist cannot enumerate. */
+	if (virtio_has_feature(vdev, ... ) ) __virtio_set_bit(vdev, VIRTIO_F_RING_RESET);
 	writel(..., base + VIRTIO_MMIO_DRIVER_FEATURES);
```

## Execution UX

(1) Show the numbered table of bugs to verify. (2) One line per cycle:
`FAIL ✓ → PASS ✓` or `FAIL ✗ — test passes on unpatched code, rewriting`. (3) Summary table with
verified/failed/rewritten counts.

## Closure gate

If `quality/BUGS.md` has confirmed bugs, `quality/results/tdd-results.json` is mandatory, and every
confirmed bug needs a `quality/results/BUG-NNN.red.log`. Zero-bug runs may omit both. Verify before
declaring Phase 5 complete.
