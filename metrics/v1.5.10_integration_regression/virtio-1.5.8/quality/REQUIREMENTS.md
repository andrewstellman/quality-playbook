## Project overview

This subsystem is the guest-side of Linux's virtio paravirtualized I/O. A transport-abstraction
core (`virtio.c`, `virtio_ring.c`) defines the device lifecycle — probe, feature negotiation,
virtqueue setup, descriptor add/get, interrupt dispatch — and four transport backends bind that
lifecycle to a concrete bus: PCI-modern (`virtio_pci_modern.c`), PCI-legacy
(`virtio_pci_legacy.c`), MMIO (`virtio_mmio.c`), and vDPA (`virtio_vdpa.c`). Each transport
supplies a `config_ops` vtable; the core calls through it. The actors are the guest driver
(this code) and a hypervisor-side device backend (QEMU, vhost, or vDPA hardware) on the other
side of the virtqueue, plus the platform DMA/IOMMU and PCI/MMIO buses.

The central correctness property of this subsystem is **cross-transport contract consistency**:
four parallel implementations of the same lifecycle operations (`finalize_features`, `reset`,
the interrupt handler, `get_features`) must each honor the same spec contracts from
`reference_docs/virtio-spec-behavioral-contracts.md` (§1 feature negotiation, §5 reset, the
interrupt and barrier sections). The most dangerous bug class — and the one Phase 1 found
repeatedly — is a shared filter (`vring_transport_features`) that silently drops feature bits it
does not enumerate, where only one of four transports compensates. Because this is a Tier-3
(code-is-the-spec) run with a Tier-4 behavioral-contracts doc and no `cite/` corpus, every
requirement below is `inferred` or `Tier-4`; there are no Tier 1/2 formal-spec REQs.

The requirements are grouped into five functional sections: **Feature negotiation** (the
transport-bit whitelist and its compensation grid — the highest-yield surface), **Device reset**,
**Interrupt dispatch**, **Virtqueue ring invariants**, and **Artifact location** (canonical
playbook layout, enforced by the Phase 6 gate).

## Section 1: Feature negotiation

Feature negotiation is the heart of this audit. The core preserves every device-offered transport
bit (`virtio.c:319-321`), then `vring_transport_features` (`virtio_ring.c:3505-3532`) runs a
closed-set whitelist that clears any transport bit it does not explicitly enumerate, and finally
each transport's `finalize_features` is expected to re-preserve the bits the whitelist could not
know about. The asymmetry — modern PCI compensates, MMIO and vDPA do not, and bit 39 is
compensated by nobody — is the dominant defect vector. These requirements are `Pattern:`-tagged so
the Phase 3/5 compensation grid has explicit cells.

### REQ-001: All non-legacy transports must preserve device-offered transport feature bits (28..41) that vring_transport_features cannot enumerate
- Tier: inferred — from source (compensation asymmetry across transports)
- References: drivers/virtio/virtio_pci_modern.c, drivers/virtio/virtio_mmio.c, drivers/virtio/virtio_vdpa.c
- Pattern: compensation
- Conditions of satisfaction:
  1. After `vring_transport_features(vdev)` runs, each non-legacy transport's `finalize_features`
     re-adds (via `__virtio_set_bit` or equivalent) every transport bit the device offered that
     the whitelist cleared, before writing/forwarding the negotiated feature set.
  2. PCI-modern's `vp_transport_features` (virtio_pci_modern.c:367-381) is the reference
     compensator: it re-adds SR_IOV(37, capability-guarded), RING_RESET(40), ADMIN_VQ(41).
  3. MMIO `vm_finalize_features` (virtio_mmio.c:109-132) must re-preserve RING_RESET(40) /
     ADMIN_VQ(41) / NOTIF_CONFIG_DATA(39) / SR_IOV(37) before writing
     `VIRTIO_MMIO_DRIVER_FEATURES`. It currently does not (candidate BUG).
  4. vDPA `virtio_vdpa_finalize_features` (virtio_vdpa.c:389-397) must re-preserve those bits
     before `vdpa_set_features`. It currently does not (candidate BUG).
  5. (Asymmetry: "modern PCI compensates via vp_transport_features; MMIO and vDPA rely entirely
     on vring_transport_features and compensate for nothing.")

### REQ-002: vring_transport_features must enumerate or have a compensator for every transport feature bit any transport supports
- Tier: inferred — from source (closed-set enumeration vs authoritative header)
- References: drivers/virtio/virtio_ring.c, include/uapi/linux/virtio_config.h, drivers/virtio/virtio_pci_modern.c
- Pattern: whitelist
- Conditions of satisfaction:
  1. Every transport bit in `[VIRTIO_TRANSPORT_F_START(28), VIRTIO_TRANSPORT_F_END(42))`
     (virtio_config.h:54-55) that any transport supports is either an explicit `case` label in
     `vring_transport_features` (virtio_ring.c:3511-3525) OR re-added by the calling transport's
     compensator.
  2. The mechanically-extracted case set (quality/mechanical/vring_transport_features_cases.txt)
     contains exactly the 8 labels: INDIRECT_DESC, EVENT_IDX, VERSION_1, ACCESS_PLATFORM,
     RING_PACKED, ORDER_PLATFORM, NOTIFICATION_DATA, IN_ORDER.
  3. Bits absent from the case set — SR_IOV(37), NOTIF_CONFIG_DATA(39), RING_RESET(40),
     ADMIN_VQ(41) — hit `default:` (virtio_ring.c:3527) and are cleared
     (`__virtio_clear_bit`, virtio_ring.c:3529); each must therefore be covered by a transport
     compensator. NOTIF_CONFIG_DATA(39) is covered by no compensator (candidate BUG).

### REQ-005: NOTIF_CONFIG_DATA(39) must survive negotiation on any transport whose finalize validates it
- Tier: inferred — from source (compensator/validator disagreement)
- References: drivers/virtio/virtio_pci_modern.c
- Pattern: compensation
- Conditions of satisfaction:
  1. `vp_check_common_size` (virtio_pci_modern.c:405-417) validates the `queue_notify_data`
     config sizing when `VIRTIO_F_NOTIF_CONFIG_DATA` is set; this check is only meaningful if
     bit 39 can survive negotiation.
  2. `vp_transport_features` (virtio_pci_modern.c:367-381) must re-add NOTIF_CONFIG_DATA(39)
     after `vring_transport_features` clears it. It currently does not, so the validator at
     virtio_pci_modern.c:405-417 is dead and the `queue_notify_data` path is unreachable
     (candidate BUG).

### REQ-006: Negotiation acceptance is confirmed for VERSION_1 devices and intentionally absent for legacy
- Tier: Tier-4 — behavioral-contracts.md §1
- References: drivers/virtio/virtio.c
- Conditions of satisfaction:
  1. `virtio_features_ok` (virtio.c:204-235) sets `VIRTIO_CONFIG_S_FEATURES_OK` (line 227),
     re-reads status (line 228), and returns -ENODEV if the bit did not stick (lines 229-232).
  2. For non-VERSION_1 (legacy) devices, `virtio_features_ok` early-returns 0 (lines 224-225)
     before touching FEATURES_OK — the legacy path has no acceptance confirmation by design
     ("no safe failure mechanism"). This is a documented intentional divergence, not a defect.

## Section 2: Device reset

Reset has a single spec contract (§5): write 0 to the device status, then wait until a status
read returns 0 before reinitializing. PCI-modern implements the poll; MMIO omits it entirely; vDPA
delegates to the backend; PCI-legacy uses a single flush-read that is arguably correct for pre-1.0
devices but is undocumented as intentional. The parity requirement makes each divergence explicit.

### REQ-003: Every transport's device-reset path must satisfy the spec §5 "write 0 then wait for status read 0" contract, or document an intentional legacy exemption
- Tier: Tier-4 — behavioral-contracts.md §5
- References: drivers/virtio/virtio_pci_modern.c, drivers/virtio/virtio_mmio.c, drivers/virtio/virtio_pci_legacy.c
- Pattern: parity
- Conditions of satisfaction:
  1. PCI-modern `vp_reset` (virtio_pci_modern.c:546-565): writes 0 (line 552), then polls
     `while (vp_modern_get_status(mdev)) msleep(1);` (lines 558-559). CONFORMANT — reference.
  2. MMIO `vm_reset` (virtio_mmio.c:251-257): must wait for status read 0 after writing 0
     (line 256). It returns immediately with no poll loop (candidate BUG).
  3. vDPA `virtio_vdpa_reset` (virtio_vdpa.c:86-91): delegates to `vdpa_reset`; guest-side reinit
     must not assume synchronous completion (the backend owns the wait).
  4. PCI-legacy `vp_reset` (virtio_pci_legacy.c:93-103): single flush-read (no poll) is acceptable
     ONLY if documented as an intentional pre-1.0 exemption; an undocumented omission is a defect.

## Section 3: Interrupt dispatch

The transport interrupt handlers dispatch over two event types — config-change and vring-activity
— and must return IRQ_HANDLED whenever they consumed a real interrupt. MMIO does this correctly;
PCI discards `vp_config_changed`'s IRQ_HANDLED return and returns the vring result, so a
config-only interrupt is reported to the kernel as spurious. The parity requirement names the
correct (MMIO) reference and the divergent (PCI) site.

### REQ-004: Every transport interrupt handler must return IRQ_HANDLED when it serviced a config-change interrupt, independent of vring activity
- Tier: inferred — from source (dispatcher return-value divergence)
- References: drivers/virtio/virtio_pci_common.c, drivers/virtio/virtio_mmio.c, drivers/virtio/virtio_vdpa.c
- Pattern: parity
- Conditions of satisfaction:
  1. When the handler services a config-change interrupt with no vring activity, it returns
     IRQ_HANDLED — never IRQ_NONE.
  2. MMIO `vm_interrupt` (virtio_mmio.c:285-307) is the reference: it sets `ret = IRQ_HANDLED` on
     the CONFIG bit (lines 296-299) and returns `ret` (line 306). CONFORMANT.
  3. PCI `vp_interrupt` (virtio_pci_common.c:106-124) calls `vp_config_changed` (lines 120-121)
     but discards its IRQ_HANDLED return (vp_config_changed returns IRQ_HANDLED at
     virtio_pci_common.c:79) and returns `vp_vring_interrupt(...)` (line 123), which returns
     IRQ_NONE when no vring callback fires (virtio_pci_common.c:97). So `isr ==
     VIRTIO_PCI_ISR_CONFIG` exactly returns IRQ_NONE (candidate BUG).

## Section 4: Virtqueue ring invariants

The ring code maintains ownership and ordering invariants that are currently correct but
high-blast-radius: the packed-ring wrap counter and avail/used flags must toggle together, and
every descriptor write must be followed by a barrier before the publishing index update. These are
single-site invariants with no cross-check; a future edit that breaks one corrupts the ring
silently on weakly-ordered arches. Driver-requested queue size should also be bounded by the
device maximum (spec §9).

### REQ-007: Packed-ring wrap-counter and avail/used descriptor flags must toggle together on ring wrap
- Tier: inferred — from source (ownership-encoding invariant)
- References: drivers/virtio/virtio_ring.c
- Conditions of satisfaction:
  1. On a packed-ring wrap, `avail_wrap_counter` is XOR-toggled AND both the AVAIL and USED
     descriptor flag bits in `avail_used_flags` are flipped in the same operation
     (virtio_ring.c packed wrap site ~1580-1583).
  2. No code path toggles the wrap counter without flipping the flags, or vice versa — doing so
     gives descriptors the wrong ownership encoding and the device reads stale/unowned
     descriptors.

### REQ-008: Every descriptor write must be ordered before the index update that publishes it
- Tier: Tier-4 — behavioral-contracts.md §6
- References: drivers/virtio/virtio_ring.c
- Conditions of satisfaction:
  1. In both split and packed paths, each `avail`/`used` index update is preceded by the correct
     `virtio_wmb` / `virtio_store_mb` barrier (barrier sites include virtio_ring.c:756, 802, 939,
     964, 1111, 1569, 1743, 1901, 2085, 2125, 2184).
  2. A descriptor published without a preceding write barrier corrupts the ring on weakly-ordered
     architectures (ARM) while remaining invisible on x86.

### REQ-009: Driver-requested virtqueue size must not exceed the device-advertised maximum
- Tier: Tier-4 — behavioral-contracts.md §9
- References: drivers/virtio/virtio_ring.c
- Conditions of satisfaction:
  1. The virtqueue-creation path (`vring_create_virtqueue` family near virtio_ring.c:3505) rejects
     or clamps a requested size larger than the device-advertised `queue_size`/`num_max`.
  2. A driver that requests more descriptors than the device supports does not silently allocate a
     ring the device cannot service.

## Cross-cutting concerns

**Compensation grid.** The dominant architectural invariant is that any feature bit the shared
whitelist (`vring_transport_features`) clears must be re-preserved by every transport that
supports it. REQ-001, REQ-002, and REQ-005 form a grid: REQ-002 is the whitelist's closed set,
REQ-001 is per-transport compensation, REQ-005 is the single-bit (NOTIF_CONFIG_DATA) case where
the validator and the compensator disagree. A reviewer must read these three together — a bit can
be "covered" by REQ-002's compensator clause yet still dropped because the specific transport
(REQ-001) omits it.

**Cross-transport parity.** REQ-003 (reset) and REQ-004 (interrupt return value) are parity
requirements: a single spec contract that all transports must satisfy identically, with one
transport serving as the conformant reference (PCI-modern for reset, MMIO for interrupt return).
The bug is always the transport that diverges from the reference.

**Bit-width boundary.** Legacy (PCI-legacy) is 32-bit-only; transport bits 37-41 are out of its
range. REQ-001's compensation requirement therefore explicitly exempts legacy, and REQ-006
documents that legacy intentionally skips FEATURES_OK confirmation. Any reviewer treating legacy
as "missing compensation" has misread the boundary.

**Tier discipline.** No requirement in this document is Tier 1/2 (formal external spec) — the run
has no `reference_docs/cite/` corpus. Every REQ is `inferred` (from source) or `Tier-4` (the
behavioral-contracts doc). Consequently `citation_semantic_check.json` is not required this run.
