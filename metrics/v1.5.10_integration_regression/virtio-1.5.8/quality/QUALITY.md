# Quality Constitution: Linux virtio driver subsystem

> Generated by [Quality Playbook](https://github.com/andrewstellman/quality-playbook) v1.5.8 — Andrew Stellman
> Date: 2026-06-19 · Project: linux-virtio (sparse kernel subsystem checkout @ bfe62a454542)

## Purpose

Quality for this subsystem is **cross-transport contract fidelity**, not test-pass count. Four
transport backends (PCI-modern, PCI-legacy, MMIO, vDPA) each implement the same device-lifecycle
contracts — feature negotiation, reset, interrupt dispatch — against a shared core. The system is
"fit for use" (Juran) when a feature the device offers and the driver accepts survives negotiation
on *every* transport that supports it, when a reset on *every* transport waits for the device to
acknowledge, and when *every* interrupt handler reports a serviced interrupt as handled. A virtio
guest that silently drops RING_RESET on MMIO, or reports a real config interrupt as spurious on
PCI, is not "95% correct" — it is broken for the workloads that exercise that path, and the
breakage is invisible until a specific hypervisor/transport/feature combination hits it in
production.

Quality is **built in** (Deming): this constitution, the requirements, and the mechanical
enumeration receipt are inherited by every future AI session so the compensation grid cannot be
silently re-opened. The cost of catching a stripped feature bit here — one extracted `case` list
and one diff — is trivially less (Crosby) than debugging a guest that hangs on queue reset because
a backend negotiated RING_RESET that the MMIO finalize quietly cleared.

## Coverage Targets

| Subsystem | Target | Why |
|-----------|--------|-----|
| Feature negotiation (`vring_transport_features` + per-transport `finalize_features`) | 95% | This is where bits are silently dropped. Phase 1 found four bits (37/39/40/41) cleared by a shared whitelist with only one of four transports compensating, and bit 39 compensated by nobody. A single un-enumerated case here disables a real device feature on a whole transport class with no error. |
| Device reset (`*_reset` across transports) | 90% | MMIO `vm_reset` omits the spec §5 status poll; reset that races reinit corrupts a slow device's state machine. The bug is a *missing* loop — invisible to anyone reading only the happy path. |
| Interrupt dispatch (`vp_interrupt` / `vm_interrupt`) | 90% | A config-only interrupt reported IRQ_NONE accrues spurious-IRQ accounting; under a storm the kernel disables the line, killing config-change delivery for the device. |
| Ring invariants (`virtio_ring.c` packed wrap + barriers) | 85% | Single-site, high-blast-radius invariants. A future edit that toggles the wrap counter without the flags, or drops a `virtio_wmb`, corrupts the ring silently on ARM while passing every x86 test. |

The rationale column is the protection against erosion: every target names the specific failure a
lower bar would let through.

## Coverage Theater Prevention

For this codebase, a fake test is one that asserts the *shape* of the code rather than the
*behavior* of negotiation. Specifically, the following are coverage theater and are rejected:

- **Asserting `vring_transport_features` "has a switch statement"** without diffing its case set
  against the authoritative header. AI models reliably hallucinate that a switch "covers all
  values" — see the v1.3.16/v1.3.17 virtio incidents where a reviewer claimed RING_RESET was
  preserved while line 3527 was actually the `default:` branch. The only honest test extracts the
  case labels (List A) and the header bits (List B) and diffs them.
- **Asserting `vp_transport_features` "re-adds transport bits"** without checking *which* bits.
  It re-adds 37/40/41 and NOT 39 — a test that only checks "RING_RESET is re-added" passes while
  bit 39 is still dead.
- **Asserting `vm_reset` "writes 0 to status"** without checking for the *absence* of the poll
  loop. The write is present; the bug is the missing wait.
- **Asserting `vp_interrupt` "calls vp_config_changed"** without checking the *return value* the
  caller propagates. The call happens; the bug is that its IRQ_HANDLED is discarded.
- **Copying the case list from REQUIREMENTS.md or CONTRACTS.md** instead of extracting it from
  `virtio_ring.c`. If the test's expected list is word-for-word the requirements list, it proves
  nothing — it tests the artifact, not the code.

## Fitness-to-Purpose Scenarios

### Scenario 1: MMIO silently drops RING_RESET during negotiation

**Requirement tag:** [Req: inferred — REQ-001 / EXPLORATION.md finding 4]

**What happened:** `vm_finalize_features` (virtio_mmio.c:109-132) calls
`vring_transport_features(vdev)` (line 114), which clears any transport bit not in its 8-case
whitelist — including RING_RESET(40) — then writes the now-stripped `vdev->features` straight to
the `VIRTIO_MMIO_DRIVER_FEATURES` registers (lines 123-129) with no re-preservation step. An MMIO
device that legitimately offers per-queue reset has the bit destroyed even though the core's
preserve loop (virtio.c:319-321) re-added it moments earlier. PCI-modern compensates via
`vp_transport_features`; MMIO has no equivalent. The guest and device both wanted RING_RESET; the
shared filter ate it.

**The requirement:** After `vring_transport_features`, MMIO's finalize must re-add every
device-offered transport bit the whitelist cleared (RING_RESET/ADMIN_VQ/NOTIF_CONFIG_DATA/SR_IOV)
before writing the feature registers.

**How to verify:** Extract the body of `vm_finalize_features` and assert it re-adds RING_RESET
after the `vring_transport_features` call, OR that no such re-add exists (the current bug). Test:
`test_scenario_1_mmio_finalize_preserves_ring_reset`.

### Scenario 2: NOTIF_CONFIG_DATA(39) is validated but never preserved, even on modern PCI

**Requirement tag:** [Req: inferred — REQ-005 / EXPLORATION.md finding 3]

**What happened:** `vp_check_common_size` (virtio_pci_modern.c:405-417) validates the
`queue_notify_data` config-space sizing when `VIRTIO_F_NOTIF_CONFIG_DATA` is set — as though bit 39
could survive negotiation. But `vp_transport_features` (virtio_pci_modern.c:367-381) re-adds only
SR_IOV(37), RING_RESET(40), ADMIN_VQ(41); it never re-adds bit 39. So `vring_transport_features`
clears bit 39, the validator guard is dead code, and the `queue_notify_data` path it gates is
unreachable on every transport. The asymmetry hides because the validator's *presence* looks like
the feature is supported.

**The requirement:** If `vp_check_common_size` validates NOTIF_CONFIG_DATA(39), then
`vp_transport_features` must re-add bit 39 so the validation can ever fire.

**How to verify:** Assert that the set of bits `vp_transport_features` re-adds includes
NOTIF_CONFIG_DATA whenever `vp_check_common_size` references it. Test:
`test_scenario_2_notif_config_data_preserved_if_validated`.

### Scenario 3: MMIO reset races reinitialization

**Requirement tag:** [Req: Tier-4 — REQ-003 / behavioral-contracts.md §5]

**What happened:** `vm_reset` (virtio_mmio.c:251-257) writes 0 to `VIRTIO_MMIO_STATUS` (line 256)
and returns immediately. Spec §5 mandates the driver wait for a status read to return 0 before
reinitializing; `vp_reset` (virtio_pci_modern.c:558-559) implements exactly this with
`while (vp_modern_get_status(mdev)) msleep(1);`. On a slow or busy backend, the next init step
(writing ACKNOWLEDGE/DRIVER) can race a device still tearing down — a corrupted state machine with
no error.

**The requirement:** `vm_reset` must poll the device status until it reads 0 after writing 0.

**How to verify:** Assert `vm_reset`'s body contains a status-poll loop (`while`/`readl` over
`VIRTIO_MMIO_STATUS`), comparing against `vp_reset`'s poll. Test:
`test_scenario_3_mmio_reset_waits_for_status_zero`.

### Scenario 4: A config-only PCI interrupt is reported spurious

**Requirement tag:** [Req: inferred — REQ-004 / EXPLORATION.md finding 7]

**What happened:** `vp_interrupt` (virtio_pci_common.c:106-124) calls `vp_config_changed` on the
CONFIG bit (lines 120-121) but discards its IRQ_HANDLED return, then returns
`vp_vring_interrupt(...)` (line 123), which returns IRQ_NONE when no vring callback fires
(virtio_pci_common.c:97). So when `isr == VIRTIO_PCI_ISR_CONFIG` exactly — a real config-change
with no queue activity — the handler returns IRQ_NONE and the kernel counts the genuine interrupt
as spurious. `vm_interrupt` (MMIO) does this correctly: `ret = IRQ_HANDLED` on the config bit
(virtio_mmio.c:296-299).

**The requirement:** `vp_interrupt` must return IRQ_HANDLED whenever it serviced a config-change
interrupt, regardless of vring activity.

**How to verify:** Assert that `vp_interrupt`'s body captures or returns IRQ_HANDLED on the CONFIG
branch (e.g., `ret = vp_config_changed(...)` or an explicit IRQ_HANDLED), not a discarded call.
Test: `test_scenario_4_pci_config_interrupt_returns_handled`.

### Scenario 5: vDPA forwards a stripped feature set to the backend

**Requirement tag:** [Req: inferred — REQ-001 / EXPLORATION.md finding 5]

**What happened:** `virtio_vdpa_finalize_features` (virtio_vdpa.c:389-397) calls
`vring_transport_features` (line 394) then `vdpa_set_features(vdpa, vdev->features)` (line 396)
with no transport-bit re-add. RING_RESET on vhost-vdpa is real, so any transport bit the vDPA
backend advertised in 37/39/40/41 is stripped before being forwarded to `set_features` — the
backend is told the guest declined a feature both sides support.

**The requirement:** `virtio_vdpa_finalize_features` must re-preserve device-offered transport
bits before `vdpa_set_features`.

**How to verify:** Assert the body re-adds RING_RESET between `vring_transport_features` and
`vdpa_set_features`, OR that it does not (current bug). Test:
`test_scenario_5_vdpa_finalize_preserves_ring_reset`.

### Scenario 6: The whitelist closed set drifts from the authoritative header

**Requirement tag:** [Req: inferred — REQ-002 / EXPLORATION.md finding 1]

**What happened:** `vring_transport_features` enumerates 8 of the transport bits in [28,42); the
header `virtio_config.h` defines 4 more (SR_IOV/NOTIF_CONFIG_DATA/RING_RESET/ADMIN_VQ). A new
transport bit added to the header but not to the switch is silently cleared for every transport
that does not separately compensate — the canonical "feature stripped by a shared filter nobody
updated" class.

**The requirement:** Every transport bit in the authoritative header is either a `case` label in
`vring_transport_features` or re-added by a transport compensator. The mechanical receipt
(`quality/mechanical/vring_transport_features_cases.txt`) is the code-side list of record.

**How to verify:** Diff the extracted case labels against the header transport bits; assert the
only un-enumerated bits are exactly {37, 39, 40, 41} (the known compensation set). A new entry in
this diff means a bit was added to the header without updating the switch. Test:
`test_scenario_6_whitelist_enumeration_matches_known_gap`.

### Scenario 7: Packed-ring ownership encoding desync

**Requirement tag:** [Req: inferred — REQ-007 / EXPLORATION.md finding 10]

**What happened:** The packed path toggles `avail_wrap_counter` and flips the AVAIL/USED flag bits
in `avail_used_flags` together on ring wrap (virtio_ring.c ~1580-1583). If a future edit toggles
the counter without flipping the flags (or vice versa), descriptors carry the wrong ownership
encoding and the device reads stale/unowned descriptors — silent data corruption on the hot path.

**The requirement:** Wrap-counter toggle and flag flip happen together; neither occurs without the
other.

**How to verify:** Assert the wrap site mutates both `avail_wrap_counter` and `avail_used_flags`
in the same region. Test: `test_scenario_7_packed_wrap_toggles_counter_and_flags`.

### Scenario 8: Legacy reset divergence is undocumented

**Requirement tag:** [Req: Tier-4 — REQ-003 / behavioral-contracts.md §5]

**What happened:** PCI-legacy `vp_reset` (virtio_pci_legacy.c:93-103) uses a single flush-read,
not a poll loop. This is arguably correct for pre-1.0 devices (no FEATURES_OK, no guaranteed
wait), but it reads identically to the MMIO *bug* — an accidental omission. Without a documented
intentional-exemption marker, a spec audit flags it blind, and a future refactor might "fix" it by
copying the MMIO bug elsewhere.

**The requirement:** The legacy single-read must be documented as an intentional pre-1.0 exemption
(a comment or a requirement), distinguishing it from the MMIO accidental omission.

**How to verify:** Assert legacy `vp_reset` either has the poll OR is covered by an explicit
intentional-exemption note in REQUIREMENTS.md/code. Test:
`test_scenario_8_legacy_reset_divergence_documented`.

## AI Session Quality Discipline

1. Read QUALITY.md and REQUIREMENTS.md before starting work.
2. Run the full functional test suite (`quality/test_functional.py`) before marking any task
   complete.
3. Re-run `quality/mechanical/verify.py` after any edit to `vring_transport_features` or the
   transport bit `#define`s; the receipt is the source of truth for the enumeration check.
4. Never extract the case list from a generated artifact (REQUIREMENTS.md/CONTRACTS.md) — extract
   it from `virtio_ring.c`. A list that matches the requirements word-for-word was copied, not
   extracted.
5. Add tests for new transport bits and new transports — every new transport inherits the
   compensation requirement (REQ-001).
6. Never remove a fitness-to-purpose scenario. Only add new ones.
7. Output a Quality Compliance Checklist before ending a session.

## The Human Gate

- Whether a given transport bit is *real* on a given backend (e.g., is RING_RESET meaningful on
  this specific vDPA hardware?) — requires hypervisor/hardware domain knowledge.
- Whether the legacy reset divergence is acceptable for a specific deployment's pre-1.0 device
  population — backward-compatibility judgment.
- Memory-ordering correctness on a specific weakly-ordered arch — requires the arch barrier
  semantics, not just code reading.
- Any change to the spec interpretation in `reference_docs/virtio-spec-behavioral-contracts.md`.
