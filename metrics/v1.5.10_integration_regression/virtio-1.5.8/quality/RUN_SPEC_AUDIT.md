# Spec Audit Protocol: Linux virtio driver subsystem (Council of Three)

> Generated by [Quality Playbook](https://github.com/andrewstellman/quality-playbook) v1.5.8 — Andrew Stellman
> Date: 2026-06-19 · Project: linux-virtio (sparse kernel subsystem checkout @ bfe62a454542)

Three independent AI models audit the virtio transport/negotiation code against the spec. Give the
prompt below identically to three strong code-reading models. Each works independently; collect all
three reports; then triage. Save auditor reports to `quality/spec_audits/YYYY-MM-DD-auditor-N.md`
and the triage to `quality/spec_audits/YYYY-MM-DD-triage.md`.

## The Definitive Audit Prompt

---

**Context files to read:**
1. `reference_docs/virtio-spec-behavioral-contracts.md` — Tier-4 spec (§1 negotiation, §5 reset,
   §6 barriers, §9 queue size). MUST/SHOULD extraction from OASIS virtio v1.0–v1.2.
2. `quality/REQUIREMENTS.md` — REQ-001..REQ-017 with `[Req: tier — source]` tags.
3. `quality/CONTRACTS.md` — behavioral contracts with file:line.
4. Source: `drivers/virtio/*.c` + `include/uapi/linux/virtio_config.h`.

**Task:** Act as the Tester. Read the actual code in `drivers/virtio/` and compare it against the
spec and requirements. ONLY list defects.

**Requirement confidence tiers:** This is a Tier-3-primary run. Every REQ is `inferred` (from
source) or `Tier-4` (behavioral-contracts.md). There are NO `formal` (Tier 1/2) external-spec
REQs. Weight `Tier-4` findings as authoritative spec divergences; weight `inferred` findings as
NEEDS REVIEW unless a cross-transport peer demonstrates the contract (e.g., MMIO `vm_interrupt`
proves the config-interrupt-return contract that PCI `vp_interrupt` violates — that elevates the
inferred finding).

**Rules:**
- ONLY list defects. For EVERY defect cite specific file and line number(s).
- Before claiming missing, grep the codebase. Before claiming exists, read the function body.
- Classify each finding: MISSING / DIVERGENT / UNDOCUMENTED / PHANTOM.
- For findings against inferred requirements, add: NEEDS REVIEW.

**Project-specific scrutiny areas:**

1. **Whitelist enumeration (the #1 virtio bug class).** Read `vring_transport_features`
   (virtio_ring.c:3505-3532). Extract every `case` label with its line number — OR use the
   mechanical receipt `quality/mechanical/vring_transport_features_cases.txt` as List A. Then list
   the transport bits defined in virtio_config.h (lines 54-121). Diff them. Which transport bits
   are NOT case labels? For each, which transport (if any) re-adds it in its `finalize_features`?
2. **MMIO compensation.** Read `vm_finalize_features` (virtio_mmio.c:109-132). After it calls
   `vring_transport_features` (line 114), does it re-add ANY transport bit before writing
   `VIRTIO_MMIO_DRIVER_FEATURES` (lines 123-129)? (REQ-001.)
3. **vDPA compensation.** Read `virtio_vdpa_finalize_features` (virtio_vdpa.c:389-397). Does it
   re-add any transport bit between `vring_transport_features` (line 394) and `vdpa_set_features`
   (line 396)? (REQ-001.)
4. **Bit 39 (NOTIF_CONFIG_DATA).** Read `vp_check_common_size` (virtio_pci_modern.c:405-417): does
   it reference NOTIF_CONFIG_DATA? Read `vp_transport_features` (virtio_pci_modern.c:367-381): does
   it re-add bit 39? If the first yes and the second no, the validator is dead code (REQ-005).
5. **MMIO reset.** Read `vm_reset` (virtio_mmio.c:251-257). Is there a `while`/`readl` poll over
   `VIRTIO_MMIO_STATUS` after the write-0 (line 256)? Compare to `vp_reset`
   (virtio_pci_modern.c:558-559). (REQ-003, spec §5.)
6. **PCI config interrupt.** Read `vp_interrupt` (virtio_pci_common.c:106-124). When
   `isr == VIRTIO_PCI_ISR_CONFIG` exactly (no vring activity), what does it return? Trace
   `vp_config_changed` (line 79 returns IRQ_HANDLED — is its return captured?) and
   `vp_vring_interrupt` (line 97 returns IRQ_NONE). Compare to `vm_interrupt` (virtio_mmio.c:296-299).
   (REQ-004.)

**Output format:**

### [filename.ext]
- **Line NNN:** [MISSING / DIVERGENT / UNDOCUMENTED / PHANTOM] [Req: tier — source] Description.
  Spec says: [quote]. Code does: [what actually happens].

## Pre-audit docs validation (required triage section — fires every run)

`reference_docs/` EXISTS but has NO `cite/` subdir (0 FORMAL_DOC records). The factual baseline is
`reference_docs/virtio-spec-behavioral-contracts.md` (Tier-4) plus the code itself. State this in
the triage header: "Tier-3-primary run; auditors relied on the behavioral-contracts doc and the
source. No external-spec cite corpus."

**Spot-check claims about code contents must EXTRACT, not assert.** For every claim of the form
"function X handles constant Y at line Z," the triage must read the cited lines and report what they
literally contain. Format:

```
Claim: "vring_transport_features() preserves VIRTIO_F_RING_RESET at line 3527"
Actual line 3527: `default:`
Result: CLAIM IS FALSE — line 3527 is the default branch, not a RING_RESET case label
```

This is the exact v1.3.16/v1.3.17 contamination vector — a false spot-check accepted without
reading the lines. The mechanical receipt (`quality/mechanical/vring_transport_features_cases.txt`)
is the tiebreaker for any enumeration claim.

## Triage Process

Merge findings. Log the effective council size (e.g., "2/3 — Model C timed out"). Confidence:
all-three = highest; two-of-three = high; one-only = needs verification (deploy a probe).

**Minority finding rule:** any finding flagged by only one auditor requires re-investigation with
an explicit CONFIRMED/FALSE-POSITIVE determination — NOT discard-by-default. The historical
RING_RESET finding was a minority finding that was real.

**Incomplete-council enumeration gate:** if the effective council is < 3/3 AND any enumeration/
whitelist/dispatch claim is in scope, the audit may NOT conclude "no confirmed defect" for that
claim without the mechanical receipt. The receipt exists at
`quality/mechanical/vring_transport_features_cases.txt`; use it.

**Triage must not raise the bar above code-path analysis.** A code-path trace showing a behavioral
violation (file:line, function calls, missing branch, wrong return) is sufficient to confirm. Do
NOT defer findings pending runtime evidence — the TDD protocol provides runtime evidence AFTER
confirmation.

### Verification probes must produce executable evidence (written to disk)

Every probe — confirmation or rejection — must produce a test assertion with an exact line-number
citation, written to `quality/spec_audits/triage_probes.sh` (an executable file). Prose alone is
insufficient.

- **Confirmation example (bit absent → assertion FAILS):**
  ```
  grep -q 'case VIRTIO_F_RING_RESET:' \
    <(awk '/void vring_transport_features/,/^}$/' drivers/virtio/virtio_ring.c) \
    && echo "RING_RESET present" || echo "CONFIRMED: RING_RESET NOT a case label (cleared by default: at line 3527)"
  ```
- **Rejection example (claim wrong → assertion PASSES):** write an assertion that passes only if
  the rejected finding is genuinely absent from the code, citing the exact line.

If you cannot write a passing assertion for a rejection, do NOT reject — escalate to confirmed or
manual review.

## Categorize each confirmed finding

Spec bug / Design decision / Real code bug / Documentation gap / Missing test / Inferred-requirement
wrong. For every "Real code bug," add it to the PROGRESS.md BUG tracker with source "Spec Audit"
and write a regression test in `quality/test_regression.py` (same conventions as code-review
regression tests — xfail(strict), source-inspection, test-finding alignment). Spec-audit bugs are
systematically orphaned otherwise.

## Individual auditor artifacts (mandatory)

Produce one file per auditor at `quality/spec_audits/YYYY-MM-DD-auditor-N.md` (the gate globs
`*auditor*`), recording each auditor's independent findings BEFORE triage reconciliation, plus the
triage synthesis at `quality/spec_audits/YYYY-MM-DD-triage.md`. Phase 4 is not complete until both
exist.
